# EDGE 사이트 공통 개발 지침

## 1. 목적과 해석

이 문서는 EDGE 사이트의 모든 기능과 유지보수에 적용한다. 도서관리, 아카이브, 소개 페이지, 인증, 외부 연동 등에서 소프트웨어공학 방법을 일관되게 사용하기 위한 지침이다.

근거 자료는 건국대학교 유준범 교수의 `Software Engineering` 강의 PDF(2026.08.25 최종수정, 제공본 465쪽)이다. 과제·숙제·실습에서 사용하는 분석과 개발 방법을 우선 채택하고, 유용한 개론 원칙과 CMMI 실무를 규모에 맞게 보완했다. 아래 절차와 웹 프로젝트 적용 방식은 자료를 EDGE에 맞게 조정한 지침이며, 강의 과제를 그대로 수행하라는 뜻이 아니다.

- **필수:** 요구사항 명확화, 분석·설계와 구현의 일치, 변경 범위 통제, 적절한 검증, 결과와 근거 기록.
- **조건부:** 다이어그램, 상세 품질 시나리오, 아키텍처 대안 비교, 상태 모델, 테스트 도구 추가. 해당 변경의 복잡성이나 위험이 필요로 할 때 적용하고, 생략 이유를 간단히 남긴다.
- **참고:** 개론·사례 조사·표준 명칭은 판단 근거로 활용한다. 자료에 나온 모든 방법론을 동시에 적용하거나 표준 전체 준수를 주장하지 않는다.

과제의 RVC 제작, 신문기사·논문 조사, A4/PPT 분량, 테스트 20개, C/C++·CMake·Google Test 지정, 토큰 수 비교는 사이트의 요구사항이 아니다. 실습의 기존 규칙 삭제·프로젝트 재시작도 실제 저장소에 적용하지 않는다. PDF의 예시 수치(예: 5초 응답)를 사이트의 품질 목표로 자동 채택하지 않는다.

이 문서는 절차의 개요이다. 실제 작성 형식과 판정은 [작성·판정 기준](DEVELOPMENT_CRITERIA.md), 방법의 후보·선택 조건·수행 절차는 [방법론 목록](METHOD_CATALOG.md)과 연결된 네 실행 문서에 정의한다. 아래의 "명확하다", "검토한다", "적절하다"는 표현은 그 기준과 절차로 실행한다. 방법을 여러 개 열거한 경우도 선택 조건과 산출물을 함께 적용한다.

이번 구체화는 [전체 감사 기록](GUIDELINE_AUDIT.md)에 `추상 지시 식별 → PDF·공식 자료 조사 및 채택 → 원문·양식 대조` 순으로 남겼다. 감사 기록은 보완의 근거이며 매 개발 작업에서 전체를 다시 감사하라는 지시가 아니다.

## 2. 변경 규모에 맞는 기록

기본 흐름은 **Planning → OOA(분석) → OOD(설계) → 구현·테스트 → QA**이다. 작은 기능 단위로 이 흐름을 반복한다. 전체 요구사항을 한 번에 동결하는 절차로 해석하지 않는다.

| 변경 유형 | 적용 방식 |
| --- | --- |
| 문구·스타일·단순 오류 수정 | 요청 또는 작업 기록에 기대 동작, 영향 범위, 수정 방향, 확인 결과를 짧게 남긴다. 별도 모델 파일은 필요하지 않다. |
| 새 기능·행동 변경·데이터 변경 | `docs/features/<feature>.md`에 요구사항, 분석, 설계, 검증, 추적 정보를 통합해 관리한다. |
| 권한·영속 데이터·동시성·외부 연동·아키텍처 변경 | 기능 기록을 확장해 상태·실패 흐름, 인터페이스, 품질 기준, 필요한 모델과 검증 근거를 명시한다. |

기존 기능 기록이 있으면 갱신한다. 파일명·문서 개수를 늘리는 것보다 내용과 코드가 일치하는 것이 우선이다. 단계별 확인은 개발자가 수행하며, 매 단계 사용자 승인을 요구하지 않는다. 사용자의 별도 승인·검토 요청은 따른다.

이 표의 경계 사례·필수 산출물·축약 판단은 [P02](methods/PLANNING_ANALYSIS.md#p02), 반복 단위는 [P01](methods/PLANNING_ANALYSIS.md#p01)을 따른다. 선택한 방법 ID·실제 이유·산출물 위치를 기록하고, 적용 대상이 없으면 범위 근거로 생략한다.

## 3. Planning: 목적과 요구사항

1. 해결할 문제, 대상 사용자·운영자, 이번 범위, 외부 시스템, 기술·일정 제약을 정리한다.
2. 요구사항에 식별자(예: `FR-01`, `QR-01`)를 붙이고 사용자 요청, 코드, 자료에서 확인한 사실과 가정을 구분한다.
3. 기능 요구사항은 입력, 기대 결과, 실패 조건, 권한과 업무 규칙을 확인 가능한 문장으로 작성한다. 품질 요구사항은 기능과 구분한다.
4. 관련 품질 속성만 선택한다. 응답 성능, 사용성, 접근성, 신뢰성, 보안, 데이터 무결성, 유지보수성 등을 변경 내용에 맞게 검토한다.
5. 품질 기준에 실행 환경·조건·측정 방법·통과 기준을 명시한다. 미정 수치는 제안 또는 미정으로 표시한다.
6. 요구사항의 타당성, 일관성, 누락, 실현 가능성, 검증 가능성을 검토한다. 동작이나 권한을 바꿀 핵심 정보가 없으면 확인하고, 다른 작업은 계속 진행한다.
7. 구현 전에 검증 시나리오를 정한다. 성공 경로 외에 적용되는 경계값, 잘못된 입력, 권한 부족, 실패·복구 경로를 포함한다.

출구 기준: 이번 구현에서 무엇을 만족시켜야 하는지와 어떻게 확인할지가 명확하다.

실행 기준: [요구사항 작성·검토·품질 시나리오](DEVELOPMENT_CRITERIA.md#requirements). 타당성·일관성·누락 등은 검토 항목별로 근거와 결과를 남긴다.

방법 선택·실행: [P03-P09](methods/PLANNING_ANALYSIS.md#p03)의 맥락·요구 수집·원자화·리뷰·미정 처리·품질 분류·측정, [M01-M03](methods/PROJECT_MANAGEMENT.md#m01)의 우선순위·작업 분해·진척을 적용한다.

## 4. OOA: 사용자와 도메인 분석

- 사용자 목표와 시스템 책임으로 유스케이스를 작성한다. UI 클릭 순서나 프레임워크 구현을 초기 분석의 중심으로 삼지 않는다.
- 각 주요 유스케이스의 행위자, 전제조건, 기본 흐름, 대안·예외 흐름, 종료 후 상태를 확인한다.
- 핵심 도메인 개념, 관계, 용어, 데이터 의미와 업무상 불변조건을 정리한다. 도메인 모델은 DB 테이블 설계와 구분한다.
- 시스템 시퀀스 다이어그램(SSD) 또는 간단한 입출력 표로 외부 요청·응답과 시스템 연산을 도출한다. 내부 호출 순서는 설계 단계에서 정한다.
- 데이터 가공이 복잡하면 DFD·데이터 사전을 사용한다. 상태가 중요한 기능은 FSM·상태 전이표로 도달 불가능 상태, 빠진 전이, 충돌하는 조건, 우선순위를 검토한다.
- 구조적 분석(SASD)과 OOAD는 문제에 맞는 관점을 선택한다. 동일 내용을 두 방법으로 중복 작성할 필요는 없다.

출구 기준: 누가 어떤 상황에서 어떤 동작을 요구하는지, 데이터와 상태의 의미가 설명된다.

실행 기준: [유스케이스·도메인·시스템 연산·모델 선택](DEVELOPMENT_CRITERIA.md#analysis). 유스케이스 서술은 강의 p.378에 제시된 Cockburn 기반 Larman Fully Dressed 양식을 사용하고, [실제 작성 양식](templates/USE_CASE.md)을 따른다. UML 다이어그램 표기와 서술 양식은 별도로 구분한다.

방법 선택·실행: [P10-P16](methods/PLANNING_ANALYSIS.md#p10)의 UC 목표·보장, 도메인 도출, SSD/연산 계약, DFD 분해·균형, FSM Guard·도달성, SASD/OOAD와 모델·프로토타입 선택을 따른다.

## 5. OOD: 구조와 인터페이스 설계

- 분석된 연산을 실제 컴포넌트·모듈·서비스의 책임으로 배분한다. 기존 코드의 변경 지점을 먼저 확인한다.
- 화면, 서버 처리, 도메인 규칙, 외부 연동·저장소의 경계를 명확히 한다. 새 계층이나 프레임워크는 필요성이 있을 때만 추가한다.
- 중요한 호출 흐름은 시퀀스 다이어그램이나 단계 표로, 데이터·모듈 관계는 ERD·타입·모듈 관계도로 표현한다. React/TypeScript 코드를 UML 클래스에 억지로 맞추지 않는다.
- 변경하는 인터페이스의 입력·출력·타입·오류·권한·부작용을 정의한다. 필요하면 재시도, 캐시 갱신, 중복 요청, 동시 변경, 데이터 호환성과 복구도 설계한다.
- 아키텍처 스타일과 디자인 패턴의 역할을 구분한다. 선택한 방안의 이유와 중요한 대안의 비용을 간단히 기록한다.
- 정보 은닉, 높은 응집도, 낮은 결합도, SOLID의 필요한 원칙을 적용한다. 추측한 미래 기능을 위한 일반화와 관련 없는 리팩토링을 피한다.

출구 기준: 요구사항을 담당하는 코드 위치와 인터페이스, 주요 실패 처리, 검증 대상이 정해져 있다.

실행 기준: [설계 산출물·인터페이스 계약·설계 리뷰](DEVELOPMENT_CRITERIA.md#design). 모듈·호출·데이터·오류 처리별로 확인할 내용을 적용한다.

방법 선택·실행: [D01-D12](methods/DESIGN_IMPLEMENTATION.md#d01)의 구조·ADR 비교, 표현법, GRASP 책임, 계약·권한, 저장·경합·재시도·캐시, 원칙·재사용·영향 조사 절차를 적용한다. 지침만으로 패턴·새 계층·DB를 설치하거나 확정하지 않는다.

## 6. 구현·테스트

- 설계와 요구사항에 연결된 작은 변경으로 구현한다. 기존 컴포넌트·유틸리티·라이브러리를 우선 활용한다.
- 테스트를 인수 조건에서 도출한다. 결함 재현과 핵심 업무 규칙은 가능하면 수정 전에 실패하는 테스트를 작성하고 통과하도록 고친다. 모든 변경에 형식적인 TDD를 강제하지 않는다.
- 규칙·계산·상태는 단위 테스트, 서버와 저장소·외부 연동은 통합 테스트, 사용자 흐름은 시스템 테스트로 필요한 범위를 확인한다. 실제 서비스 데이터에 영향을 주는 검증은 승인된 범위와 격리된 데이터로 수행한다.
- 실패 사례를 고치면 관련 요구사항과 영향 범위에 대해 재검증한다. 테스트가 통과한 뒤 이유 없이 같은 검사를 반복하지 않는다.
- 구현 방식만 복제하는 테스트나 개수를 채우는 테스트를 피한다. 커버리지는 누락된 조건·경로를 찾는 근거로 사용하며, 높은 비율만으로 품질을 보장하지 않는다.
- 변경에 맞는 타입 검사, 린트, 빌드, 테스트를 실행한다. 새 도구·의존성이 필요하면 현재 스택에서의 역할과 비용을 먼저 설명한다.

출구 기준: 구현이 설계와 맞고 해당 동작을 확인한 증거가 있다. 실행하지 못한 검사는 이유와 남은 확인 사항을 기록한다.

실행 기준: [테스트 선택·케이스 작성·회귀·정적 분석](DEVELOPMENT_CRITERIA.md#testing). 테스트 개수 대신 요구사항·입력 분할·상태·실패 흐름에 대한 검증 범위로 판정한다.

방법 선택·실행: [테스트·QA 실행 방법](methods/TESTING_QA.md)의 기법·수준·도구·자동/수동·대역/실연동·검사 범위 선택을 따른다. 가이드 작성 요청을 구현·앱 테스트 수행 요청으로 확대하지 않는다.

## 7. QA와 완료 판정

**Verification**은 명세·설계대로 구현됐는지, **Validation**은 사용자의 실제 목적을 해결하는지 확인한다.

- 요구사항별로 구현 위치, 검증 시나리오·테스트, 결과를 연결한다. 요구사항 하나가 여러 코드·테스트와 연결될 수 있다.
- 실패·미실행·보류·미정 사항은 통과와 구분한다. 알려진 실패가 있으면 구현 완료와 검증 완료를 구분해 보고한다.
- 변경 주변의 기존 동작에 대해 필요한 회귀 검증을 한다. UI 변경은 관련 화면·기기 조건에서 확인하고, 데이터·권한 변경은 적용되는 경계·실패 조건을 확인한다.
- 정적 분석 결과를 실제 코드와 대조하고 필요한 수정만 반영한다. 같은 문제가 재발하면 재현 조건, 원인, 수정, 방지책을 작업 기록에 남긴다.
- 문서·설계·코드·테스트 간 불일치를 정리한다. 미구현 요구사항이나 요구사항 없이 추가된 동작을 확인한다.
- 사용자가 검증을 제한하면 그 지시를 따르고 검증 범위를 명시한다. 최종 답변은 파일, 변경 요지, 결과, 남은 제약만 짧게 보고한다.

실행 기준: [단계별 통과 조건·추적성·결과 판정](DEVELOPMENT_CRITERIA.md#completion). 미실행, 실패, 판정불가와 통과를 구별한다.

방법 선택·실행: [테스트·QA 실행 방법](methods/TESTING_QA.md)의 대표 시나리오·리뷰·추적 대조와 [M08](methods/PROJECT_MANAGEMENT.md#m08)의 반복·중요 결함 처리를 적용한다.

## 8. 필요한 CMMI 실무만 적용

| 실무 | EDGE에서 남길 최소 근거 |
| --- | --- |
| 요구사항 관리·추적 | 요구사항 ID와 출처, 변경 이유, 설계·코드·검증 연결 |
| 계획·진행 관리 | 기능별 우선순위, 이번 범위, 의존성·장애물, 완료 상태 |
| 형상 관리 | 현재 브랜치와 기존 변경 확인, 목적이 분명한 변경 묶음, 설정·의존성 변경 근거 |
| 품질 보증·검증·확인 | 인수 기준, 적절한 리뷰·검사·테스트와 실행 결과 |
| 위험 관리 | 해당 변경에 실제로 관련된 권한·데이터 손실·동시성·외부 장애·배포 위험과 대응 |
| 원인 분석·개선 | 반복되거나 중요한 결함의 원인과 재발 방지 조치 |

전체 체크리스트 점수화, 성숙도 등급, 조직 프로세스 문서, 통계적 관리, 인증은 의무가 아니다. 진행 기록과 기능 기록에 위 근거가 있으면 별도 CMMI 보고서를 만들지 않는다.

실행 기준: [CMMI 실무·위험·변경 관리](DEVELOPMENT_CRITERIA.md#management). 각 실무의 기록 필드, 갱신 시점, 완료 조건을 따른다.

방법 선택·실행: [M01-M10](methods/PROJECT_MANAGEMENT.md#m01)의 우선순위·작업 분해·진척·Git 기준선·환경·복구·위험·원인 개선·CMMI 증거·결정 수명 관리를 적용한다. 실무와 실제 산출물의 연결은 [M09](methods/PROJECT_MANAGEMENT.md#m09)를 따른다.

## 9. 추가로 채택한 프로젝트 적용 원칙

- **재사용과 변경 비용:** 기존 구조와 검증된 구성요소를 활용하고, 새 패턴·서비스·의존성은 요구사항에 필요한 만큼 도입한다.
- **운영 환경 차이:** 로컬에서 동작하는 것과 배포 환경에서 동작하는 것을 구분한다. 관련 환경변수·권한·캐시·빌드 조건은 변경 시 확인한다. 비밀값은 문서나 로그에 기록하지 않는다.
- **외부 서비스 실패:** 해당 연동을 변경할 때 정상 응답 외에 빈 데이터·오류·지연·부분 실패를 검토한다. 실제로 지원되는 복구·재시도 동작을 설계한다.
- **변경 관리:** 요청 변경이 발생하면 영향을 받는 요구사항·인터페이스·데이터·테스트를 갱신한다. 큰 데이터·배포 변경에는 복구 방법을 명시한다.
- **AI 개발 맥락:** 지속 지침은 `AGENTS.md`, 기능별 결정은 해당 기록에 보관한다. 대화의 유효한 결정을 출처와 함께 작업 기록에 연결하고 제안과 확정을 구분한다. 기록 부재만으로 사용자 지시를 무시하거나 재승인을 요구하지 않는다.

이 항목들은 재사용·형상 관리·품질·유지보수·AI 개발 맥락 관리 내용을 EDGE 웹 환경에 적용한 것이다. 매 작업에 전체 항목을 일괄 수행하는 체크리스트는 아니다.

방법 원본은 재사용 [D11](methods/DESIGN_IMPLEMENTATION.md#d11), 환경 [M05](methods/PROJECT_MANAGEMENT.md#m05), 외부 실패 [D08-D09](methods/DESIGN_IMPLEMENTATION.md#d08), 변경·복구 [M06](methods/PROJECT_MANAGEMENT.md#m06)과 [M10](methods/PROJECT_MANAGEMENT.md#m10)이다. 공통 정책을 기능 기록에 다시 정의하지 않고 해당 ID를 참조한다.
