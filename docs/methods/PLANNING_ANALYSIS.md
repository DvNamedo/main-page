# Planning·요구사항·분석의 실행 방법

이 문서는 [전체 지침 감사](../GUIDELINE_AUDIT.md)의 C01–C14, C36, C39를 구체화한다. 기존 [작성·판정 기준](../DEVELOPMENT_CRITERIA.md)의 필드·검토표·단계 통과 조건과 [Fully Dressed 양식](../templates/USE_CASE.md)을 함께 사용한다. 아래 후보는 EDGE에서 고려할 방법의 목록이다. 모든 후보를 함께 수행하라는 뜻은 아니다.

각 절의 **근거**는 실제 확인한 강의·공식·저자 자료이고, **EDGE 기본 선택·절차·판정**은 그 방법을 이 저장소에서 실행하기 위한 프로젝트 결정이다. 원문 표준의 의무 조항으로 주장하지 않는다. 강의 쪽수는 제공본의 1부터 시작하는 PDF 페이지 번호다. 예시·기준값 후보는 실제 제품 요구사항으로 확정한 것이 아니다.

**판정 단계:** Planning·OOA의 완료는 범위·요구·모델·측정/검증 계획에 필요한 결정·근거가 있는지 판정한다. 아래 실제 실행·측정 결과에 관한 통과 기준은 해당 실행 이후에 적용하며 계획 작성과 구별한다. 가이드·설계 요청에 구현 실행을 추가하거나 미실행을 실제 검증 통과로 기록하지 않는다.

## P01. 반복 단위와 구현 순서

**연결:** C01. **근거:** 강의 pp.36, 84–114, 269의 반복·점증 개발과 분석→설계→구현·검증; [Agile Manifesto 원칙](https://agilemanifesto.org/principles.html)의 사용 가능한 소프트웨어·피드백·조정. 구체적인 범위 우선순위는 [M01](PROJECT_MANAGEMENT.md#m01)을 따른다.

| 후보 | 선택 조건 |
| --- | --- |
| 사용자 시나리오별 수직 분할 | 입력부터 사용자에게 보이는 결과까지 작은 완결 동작을 만들 수 있음. EDGE 기본 |
| 기능별 점증 확장 | 기존에 끝까지 동작하는 기능이 있으며 역할·데이터 종류·규칙을 추가할 때. 각 증분도 확인 가능한 결과를 가져야 함 |
| 제한된 기술 실험·프로토타입 | 연동·성능·데이터 처리 가능성이 미정이라 바로 구현하면 큰 재작업이 예상됨. 먼저 검증할 질문·종료 조건을 지정 |
| 변경 단위 내 선행 분석을 강화 | 되돌리기 어려운 데이터 변경이나 여러 기능의 공유 계약이 동시에 바뀜. 해당 계약을 먼저 정리하고 구현은 단계적으로 적용 |

**EDGE 기본 선택:** 한 사용자 목표의 한 정상 경로와 그 경로에서 발생 가능한 핵심 실패 처리를 함께 묶는다. UI 전체, API 전체, DB 전체처럼 계층만 완성하는 묶음은 작업 하위 항목으로 둘 수 있으나 사용자 기능 완료와 구별한다.

**입력 → 수행 → 산출물:** 목적·범위·요구사항·의존성 → (1) 목표별 시나리오와 인수 기준을 나눈다. (2) 데이터/역할/규칙의 차이가 독립된 결과로 확인되는 지점에서 분할한다. (3) M01의 필수 범위·가치·위험·의존성으로 순서를 정한다. (4) 선택한 단위의 Planning→OOA→OOD→구현·테스트→QA를 진행한다. (5) 실행 결과·사용자 피드백의 차이를 요구사항 변경 또는 결함으로 분류하고 관련 기록·검증을 갱신한다 → `반복 단위 / 목표·인수 기준 / 요구사항 ID / 선행 의존 / 포함·보류 / 결과·다음 조정`.

**판정:** 단위의 기대 결과를 독립적으로 설명·확인할 수 있고 필수 실패 처리가 함께 정의되어 있으면 계획 통과다. 화면이 준비되지 않았는데 API 완료를 사용자 목표 달성으로 기록하거나, 오류 처리를 다음 반복으로 미뤄 성공만 표시하게 만들면 수정 필요다. 기술 실험의 성공은 제품 기능 완료가 아니다.

**경계·축약:** 정적 문구 수정은 기존 화면의 표시 조건 하나를 반복 단위로 삼는다. 구현을 요청하지 않은 가이드 작업은 분석·설계 결과까지가 이번 단위다. 고정 스프린트 기간·Scrum 역할·행사·새 배포를 자동 의무화하지 않는다. 미정 질문 때문에 막힌 단위가 있으면 의존하지 않는 확정 범위부터 진행한다.

## P02. 변경별 문서·모델·검증 적용 범위

**연결:** C02. **근거:** 강의 p.269의 단계별 산출물과 pp.174–180의 목적별 모델; [IREB 공식 syllabus](https://hub.ireb.org/media/pages/resources/cpre-foundation-level-syllabus/9c084b1cfd-1787039954/cpre_foundationlevel_syllabus_en_v.3.3.0.pdf) §3.1·§5의 맥락에 따른 상세도·프로세스 선택. 아래 세 범주는 EDGE 운영 분류다.

| 적용 범주·후보 | 판정 조건 | 남길 내용 |
| --- | --- | --- |
| 짧은 변경 기록 | 문구·정적 스타일·단순 결함이며 외부 계약·업무 규칙·권한·영속 데이터의 의미가 바뀌지 않음 | 목적·기대 결과, 영향 위치, 수정 방향, 해당 검증 결과·제약 |
| 통합 기능 명세 | 새 사용자 동작, 업무 규칙, 화면 상태, 데이터 의미 또는 인터페이스 변화가 있음 | 기능 명세의 요구사항·인수 기준·필요한 분석·설계·검증·추적 |
| 기능 명세에 위험 관련 항목 추가 | 권한, 영속 쓰기, 동시 요청, 외부 부작용, 공유 계약, 데이터 변환·배포 호환에 영향이 있음 | 적용되는 상태·실패·계약·무결성·복구·품질 시나리오와 검증 근거 |

**EDGE 기본 선택:** 줄 수나 수정 파일 수보다 **바뀌는 외부 동작과 실패의 영향**으로 분류한다. 마지막 범주에 해당해도 기능과 관계없는 모델을 전부 작성하지 않는다.

**입력 → 수행 → 산출물:** 요청·현재 변경·호출자·데이터 경계 → (1) 기대 결과가 바뀌는지 확인한다. (2) 쓰기·권한·공유 계약·연동·복구에 영향이 있는지 근거를 적는다. (3) 위 범주를 고른다. (4) P08·P11–P16의 적용 신호에 해당하는 모델·품질 검증만 선택한다. (5) 기존 기록이 있으면 같은 위치를 갱신한다 → `변경 범주 / 판정 근거 / 사용할 기록 / 추가 모델·검증 / 생략 대상·이유`.

**판정:** 선택한 범주에서 바뀌는 동작·적용 위험을 설명하고 검증 대상을 찾을 수 있으면 통과다. 권한 검사 한 줄 삭제를 짧은 스타일 수정으로 분류하거나, 영속 쓰기의 실패 종료 상태를 생략하면 수정 필요다. 영향 자료가 부족하면 먼저 좁은 범위의 호출·계약 확인을 하고 판정 불가를 해소한다.

**경계·축약:** 작은 버그라도 무결성·권한을 깨뜨릴 수 있으면 위험 항목을 추가한다. 화면 변경이라도 읽기 전용 문구라면 별도 UC·DFD·FSM·QAS 파일이 필요하지 않다. 양식의 해당 없는 절은 이유와 참조로 줄일 수 있으나 요구사항 출처·기대 결과·실제 검증 상태는 생략하지 않는다. 작업 진척 상태는 [M03](PROJECT_MANAGEMENT.md#m03)을 따른다.

## P03. 문제·이해관계자·시스템 맥락과 경계

**연결:** C03. **근거:** 강의 pp.141–150의 목표 분석·요구사항 발견, pp.221–227의 목적·맥락도·이벤트 목록, pp.376·388의 행위자·시스템 경계. 실제 경계 표현은 맥락도 또는 책임 표 중 선택한다.

| 후보 | 선택 조건 |
| --- | --- |
| 문제·목표·포함/제외 표 | 작은 변경에서 사용자·외부 시스템 수가 적고 책임을 문장으로 명확히 표현 가능. EDGE 기본 |
| 맥락도 + 외부 이벤트 목록 | 인증·저장소·콘텐츠 소스 등 여러 경계 사이의 책임·입출력이 혼동되거나 연동이 바뀜 |
| Why→How→How else 목표 분석 | 요청된 해결 수단의 목적이 불명확하거나 대안이 사용자 목표를 다른 방식으로 만족시킬 수 있음 |

**EDGE 기본 선택:** `현재 문제 / 영향을 받는 역할 / 원하는 관찰 결과 / 이번 포함 / 이번 제외 / 외부 책임 / 제약·출처`를 먼저 적는다. “DB를 추가한다”처럼 수단만 제시되면 그 수단이 해결할 목표를 연결한다. 사용자가 이미 수단을 명시했다면 제약으로 보존하고 임의로 다른 수단으로 교체하지 않는다.

**입력 → 수행 → 산출물:** 사용자 요청·기존 기능·운영 문서 → (1) 실제 사용·운영·정보 제공·장애 대응 역할을 찾는다. (2) 각 역할의 목표와 불편·손실을 정리한다. (3) 이번 변경이 책임질 기능과 외부 서비스·운영자가 책임질 부분을 분리한다. (4) 경계를 넘는 입력·출력·시간 이벤트·외부 오류를 나열한다. (5) 기술·일정 제약마다 근거와 변동 가능성을 적는다 → 역할·목표 표, 범위 표, 필요한 경우 맥락도·이벤트 목록.

**판정:** 각 경계 입출력에 제공자·소비자·의미가 있고 이번 목표의 처리 주체가 식별되면 통과다. 외부 서비스의 성공·가용성을 사이트 자체 보장으로 쓰거나 데이터·권한 책임자가 비어 있으면 수정 필요다. 요청에 없는 일정·운영 역할은 가정 또는 미정으로 남긴다.

**경계·축약:** 외부 저장소라도 사이트가 수행하는 접근·검증·오류 표시의 책임까지 밖으로 밀어내지 않는다. 기술 의존성이라는 이유만으로 모든 패키지를 행위자로 나열하지 않는다. 단순 수정은 관련 역할·입출력만 적고 기존 사이트 전체 맥락도를 소급 작성하지 않는다.

## P04. 요구사항 수집 방법의 선택과 실행

**연결:** C04. **근거:** 강의 pp.149–150의 워크숍·인터뷰·질문지·시나리오·프로토타입·명세 리뷰; [IREB syllabus](https://hub.ireb.org/media/pages/resources/cpre-foundation-level-syllabus/9c084b1cfd-1787039954/cpre_foundationlevel_syllabus_en_v.3.3.0.pdf) §4.1–4.2의 질문·협업·관찰·자료 분석. 아래는 그 범주를 EDGE에서 실행하는 방식이다.

| 후보 | 선택 조건 | 실제 수행·기록 |
| --- | --- | --- |
| 요청·명세·코드·데이터 자료 분석 | 기존 사이트의 동작·계약·용어를 파악하거나 명시된 요청이 충분함. 기본 시작점 | 출처·버전·확인 위치와 발견한 사실/모순/질문을 분리. 코드의 현재 동작을 원하는 동작으로 자동 확정하지 않음 |
| 목적 중심 인터뷰 | 특정 역할의 규칙·성공·실패 결과가 자료에 없음 | 목표→현재 과정→실제 입력·결과→예외→운영 제약 순서로 질문. 답변 출처·결정·미정을 기록 |
| 워크숍·시나리오 공동 검토 | 사용자·운영자·개발자가 같은 규칙을 다르게 해석함 | 동일 시나리오·대안·충돌을 함께 검토하고 합의/미합의 항목과 결정권을 기록 |
| 작업 관찰 | 말로 설명되지 않는 실제 순서·우회 처리·사용 환경이 중요함 | 목표·대상 과정·관찰 범위를 정하고 입력·행동·실패·수작업 보정을 관찰. 관찰 사실과 해석을 분리 |
| 질문지·설문 | 여러 역할의 빈도·불편·선호를 비교할 근거가 필요함 | 목적·대상·질문·표본 한계를 지정. 응답 수·역할 분포와 결과를 기록; 선호 응답을 업무 규칙으로 자동 확정하지 않음 |
| 스토리보드·와이어프레임·실행 프로토타입 | 화면 흐름·결과의 의미를 문장만으로 합의하기 어려움 | 검증 질문과 시나리오를 지정하고 실행·검토 결과를 FR·BR·QR 또는 미정 질문으로 환원 |

**EDGE 기본 선택:** 먼저 제공된 요청·자료를 분석하고, 남은 질문에 가장 적은 비용으로 답하는 수집 방법을 추가한다. 새 기능이라는 이유만으로 인터뷰·관찰·설문을 전부 진행하지 않는다.

**입력 → 수행 → 산출물:** P03의 역할·목표와 정보 공백 → (1) 각 질문의 답변 출처 후보를 지정한다. (2) 위 선택 조건으로 수집 방법을 고른다. (3) 실제 사례·반례와 실패·품질·제약도 수집한다. (4) 모순을 P06, 미정을 P07로 넘긴다. (5) P05로 표현하고 출처를 연결한다 → `질문 / 수집 방법·선택 이유 / 확인한 자료·응답 / 발견 요구사항 / 미정·충돌`.

**판정:** 이번 동작을 결정하는 주장에 근거 또는 미정 표시가 있으면 수집 기록 통과다. AI가 실제 사용자 인터뷰·관찰을 했다고 가정하거나 프로토타입 예시를 확정 규칙으로 전환하면 수정 필요다.

**경계·축약:** 개발 지침만으로 다른 사람에게 연락하거나 설문을 발송할 권한을 만들지 않는다. 필요한 연락 권한이 없으면 질문·검토용 산출물을 준비하고 현재 사용자의 응답 또는 승인된 자료로 확인한다. 수정 범위에 새 정보가 없으면 기존 요청·명세 참조로 축약한다.

## P05. 원자적 요구사항·EARS·인수 기준

**연결:** C04. **근거:** 강의 pp.121–129·158–161의 사용자/시스템 요구사항·명확성·SRS 오류; [EARS 저자 Alistair Mavin](https://alistairmavin.com/ears/)의 조건·이벤트·상태·오류·선택 기능 문장 패턴. EARS는 표현 후보이며 유스케이스를 대체하지 않는다.

| 후보 | 선택 조건 |
| --- | --- |
| 구조화된 한국어 요구사항 + Given/When/Then | 일반 웹 기능·업무 규칙. 기존 기능 명세의 기본 선택 |
| EARS 패턴을 한국어로 적용 | 반복되는 이벤트/상태/오류 요구사항에서 조건과 결과의 어순을 통일할 필요가 있음 |
| 결정표·상태표 + 요구사항 참조 | 여러 조건의 결합·상태에 따라 결과가 달라 문장만으로 누락·충돌을 찾기 어려움 |
| 사용자 스토리 + 별도 인수 기준 | 목적·우선순위·작업 대화를 간단히 시작할 때. 스토리 한 줄만으로 구현 명세 완료를 판정하지 않음 |

**EDGE 기본 선택:** `[역할·상태·전제]에서 [입력·이벤트]가 발생하면 시스템은 [관찰 가능한 결과·상태]를 제공한다`로 작성하고 출처·ID·실패·금지 부작용·인수 기준을 연결한다. 독립적으로 변경·판정할 결과는 별도 ID로 나누고 원자성을 확보한다. EARS 자체가 여러 응답을 허용한다는 것과 EDGE의 독립 결과 분리 규칙을 구별한다.

**EARS 선택 규칙:** 항상 유지되는 조건은 상시형, 상태가 유지되는 동안의 동작은 상태형, 한 번의 입력 사건에 반응하면 이벤트형, 허용되지 않는 입력·장애에 대한 응답은 오류형, 설정·제품 옵션이 존재할 때만 적용되면 선택 기능형을 쓴다. 복합 조건은 상태/전제→사건→응답 순서로 적되 서로 다른 결과는 분리하거나 결정표로 이동한다. `항상`, `모두`, `빠르게`, `적절히`, `지원한다`는 적용 범위·관찰 결과가 없으면 검토에서 수정 필요다.

**입력 → 수행 → 산출물:** 수집한 목표·규칙·사례 → (1) 용어를 P11의 사전에 맞춘다. (2) 시스템이 해야 하는 결과와 사용자·외부 시스템에 대한 가정을 구분한다. (3) 조건·입력·범위·결과를 작성한다. (4) 독립된 결과/역할/근거가 섞였는지 확인해 분리·참조한다. (5) 정상·적용 실패의 Given/When/Then을 작성한다. (6) 각 예상 결과의 판정 근거를 BR·QR·UC에 연결한다 → FR·BR·QR와 인수 기준.

**판정:** 독립적인 관찰·변경 단위이며 전제·결과·실패가 구별되고 예상값을 얻을 수 있으면 통과다. “조회·수정·삭제를 잘 지원”처럼 독립 결과와 미정 규칙이 섞이면 수정 필요다. 기술 제약이 실제로 주어진 경우에는 구현 수단이 들어 있어도 제약으로 인정하고 출처를 적는다.

**경계·축약:** EARS 어순만 맞아도 타당성·누락·실현 가능성이 자동 충족되지는 않는다. 명확한 기존 요구사항은 ID·변경된 조건·인수 기준만 갱신한다. 선택 기능형은 “이번에 선택 개발” 우선순위와 다르다.

## P06. 요구사항 검토를 실제로 수행하는 방법

**연결:** C05. **근거:** 강의 pp.159–161·168–170의 검토 속성과 요구사항 리뷰·프로토타입·테스트 도출. 속성별 통과·실패 조건은 [기존 판정표 §3.2](../DEVELOPMENT_CRITERIA.md#requirements)를 보존한다.

| 후보 | 선택 조건 | 확인할 증거 |
| --- | --- | --- |
| 출처·규칙·용어 대조 | 명세·기존 동작·요청 사이에 해석 차이가 있거나 작은 변경 | 같은 대상·조건의 근거 문구와 요구사항·사전·인수 기준 |
| 시나리오 워크스루 | 역할·입력·상태·예외가 결합됨. 행동 변경 기본 | 정상/예외 흐름을 따라 얻는 결과·상태·불변조건 |
| 관점별 구조화 리뷰 | 권한·데이터·운영·외부 계약을 동시에 바꿈 | 역할별 허용/거부, 쓰기·복구, 외부 실패, 품질 시나리오의 담당·근거 |
| 프로토타입 검토 | 타당성·사용성·화면 결과의 의미가 불명확 | 정해진 질문·대상·시나리오와 실제 관찰·피드백 |
| 명세에서 테스트 사례 도출 | 검증 가능성·입력군·경계·분기 누락이 의심됨 | 사전조건을 만들 수 있는지, 실행 입력·예상값·관찰 방법이 존재하는지 |
| 제한된 기술 실험 | 예산·기술·연동 제한 때문에 실현 가능성 근거가 부족함 | 검증 질문·환경·실험 결과·지원 한계 |

**EDGE 기본 선택:** 출처 대조와 시나리오 워크스루로 시작하고, 해결되지 않는 판정 항목에 위 방법을 추가한다. 단순히 사람/AI가 “검토했다”는 표시는 증거가 아니다.

**입력 → 수행 → 산출물:** 이번 필수 요구사항·출처·사전·UC·인수 기준 → (1) 검토 대상 ID와 버전을 지정한다. (2) §3.2의 각 속성을 나누어 대상·확인 자료를 고른다. (3) 역할×관련 상태×입력군×외부 실패에서 적용되는 경우를 따라간다. (4) 같은 조건의 결과가 다르면 일관성, 결과가 없으면 누락, 출처·목표와 어긋나면 타당성, 구현·검증 근거가 없으면 실현/검증 가능성 문제로 기록한다. (5) 수정·추가 확인 후 문제 항목을 재판정한다 → `검토 항목 / 대상 ID / 방법·확인 자료 / 결과 / 문제·조치 / 재확인`.

**판정:** 이번 확정 필수 범위에 적용되는 검토 항목별 결과·근거가 있어야 요구사항 리뷰 완료다. 같은 근거를 사용할 수 있으나 타당성·일관성·누락을 한 결과 칸으로 뭉치지 않는다. 서로 다른 목적의 요구사항을 비슷한 문구라는 이유만으로 충돌로 판정하지 않고 조건·대상·시간을 먼저 맞춘다.

**경계·축약:** 유효한 상태·실행 가능한 입력 조합을 범위로 정하고 검토한다. 존재할 수 없는 조합은 왜 불가능한지 남긴다. 모든 미래 경우의 완전성을 주장하지 않는다. 작고 명확한 수정은 짧은 표·문장 대조로 축약하되 발견한 모순·미정은 숨기지 않는다.

## P07. 미정 사항·질문·기술 실험의 처리

**연결:** C06. **근거:** 강의 pp.128·149·170–171의 해석 차이·요구사항 발견·검증·변경 관리. 질문·실험·가정의 아래 분류는 EDGE 작업 권한과 반복 개발에 맞춘 운영 방식이다.

| 후보 | 선택 조건 |
| --- | --- |
| 현재 사용자에게 요구사항 확인 | 권한·업무 규칙·데이터 보존·외부 동작을 바꾸며 기존 요청·근거로 결정할 수 없음 |
| 기존 자료·계약 확인 | 답이 코드·운영 명세·연동 문서에 있을 가능성이 높음. 먼저 필요한 위치만 읽음 |
| 제한된 기술 실험 | 사용자 선호보다 실제 지원 여부·성능·환경 호환이 질문의 핵심 |
| 명시적 가정·제안 + 독립 작업 진행 | 지금 구현을 결정하지 않아도 되는 정보이고 다른 확정 작업을 막지 않음 |
| 개발자 결정 기록 | 이미 승인된 범위 안의 되돌릴 수 있는 내부 구현 선택. 요구사항을 추가·변경하지 않음 |

**EDGE 기본 선택:** 미정 질문을 `요구사항 결정 / 사실 확인 / 기술 가능성 / 내부 구현 선택`으로 나누고, 답이 없는 경우 영향을 받는 동작만 미정으로 유지한다. 이미 확정된 결정을 다시 승인받지 않는다.

**입력 → 수행 → 산출물:** 미정 내용·충돌 자료 → (1) 답에 따라 바뀌는 FR·BR·QR·인터페이스·데이터를 적는다. (2) 질문의 유형·답변 출처·선행 자료 확인을 정한다. (3) 영향이 큰 필수 결정과 다른 작업의 선행조건을 먼저 해결한다. (4) 실험은 질문·사용할 격리 데이터·성공/실패 관찰·종료 조건을 정한 뒤 수행한다. (5) 응답·관찰로 해결되면 근거와 확정 범위를 기록하고 관련 명세·설계·검증을 갱신한다 → `미정 ID / 질문 / 결정 유형 / 영향 ID / 확인 방법 / 상태 / 해소 근거·후속 갱신`.

**판정:** 확정 상태에는 실제 요청·자료·관찰의 근거와 유효 범위가 있어야 한다. “응답이 없으므로 승인”이나 “실험에서 가능했으므로 사용자가 원함”은 수정 필요다. 핵심 동작이 답에 따라 달라지는데 가정을 숨겨 구현하면 Planning을 통과할 수 없다.

**경계·축약:** 확인이 필요한 질문을 보냈다는 이유만으로 독립된 작업을 중단하지 않는다. 연구·조회·가역적인 실험까지 반복 승인 절차로 바꾸지 않는다. 작은 구현 선택은 기존 작업 기록에 결정·근거 한 줄로 통합할 수 있다. 결정의 철회·교체와 인수는 [M10](PROJECT_MANAGEMENT.md#m10)을 따른다.

## P08. 품질 분류와 적용 속성의 선정

**연결:** C07. **근거:** 강의 pp.130–145·172의 품질 속성과 **ISO/IEC 25010:2011** 그림; [Eclipse OpenUP FURPS+ 체크리스트](https://archive.eclipse.org/epf/downloads/OpenUP/published/openup_published_1.5.1.5_20121212/openup/core.tech.common.extend_supp/guidances/checklists/system_wide_rqmts_furps_3158BF2F.html)의 기능·사용성·신뢰성·성능·지원성·제약·인터페이스. 현재 [ISO/IEC 25010:2023 공식 소개](https://www.iso.org/standard/78176.html)는 제품 품질을 9개 특성으로 설명한다. 강의의 2011판 8개 분류와 같은 판이라고 기록하지 않는다.

| 후보 | 선택 조건 |
| --- | --- |
| FURPS+로 속성·제약을 빠르게 분류 | 작은 기능에서 기능 외 기대·실패·성능·유지보수·환경 제약을 찾을 때. EDGE 시작점 |
| 강의의 ISO/IEC 25010:2011 분류로 누락 대조 | 보안·호환성·이식성·사용성 하위 속성 등을 FURPS+의 넓은 분류에서 놓치기 쉬움 |
| 이해관계자 목표→QAS 도출 | 실제 품질 문제가 구체적으로 알려져 있어 분류명보다 상황·응답이 먼저 존재 |
| 현재 판의 표준을 직접 사용 | 사용자가 그 판을 지정하거나 계약·공유 조직 기준에 필요함. 원문 접근 범위와 적용 항목을 확인한 후 사용 |

**EDGE 기본 선택:** FURPS+로 기능·품질·제약을 구분하고 다음 강의 분류표를 **관련 누락 점검**에 사용한다. 명칭만 골라 “보안성이 높다”로 끝내지 않고 채택한 속성은 P09의 시나리오 또는 구체적인 BR·인수 기준으로 연결한다.

| 강의 2011판 제품 품질 범주 | 이번 변경에서 선택할 신호·확인 질문 |
| --- | --- |
| 기능 적합성 | 조회·계산·규칙 결과가 변함: 요청한 정보·값·동작이 정확하고 목표에 충분한가 |
| 성능 효율성 | 데이터량·네트워크·렌더링·캐시·빈번한 요청이 변함: 어떤 부하에서 지연·처리량·자원을 확인할 것인가 |
| 신뢰성 | 영속 쓰기·외부 실패·재시작·부분 처리가 있음: 장애 시 상태와 복구·가용 동작이 무엇인가 |
| 사용성 | 사용자 작업·표시·입력·오류 흐름이 바뀜: 학습·완료·실수 방지·접근성의 해당 문제를 무엇으로 확인할 것인가 |
| 보안 | 역할·인증·쓰기·개인/비밀 정보·외부 입력이 변함: 허용·거부·노출 방지·변조 방지를 어디서 검사하는가 |
| 유지보수성 | 공유 규칙·의존성·경계가 변함: 영향 파악·수정·테스트·분석이 가능하고 책임이 모이지 않는가 |
| 호환성 | 외부 응답·공유 API·이전 데이터·여러 구성요소가 공존함: 소비자·버전·형식 간 계약이 맞는가 |
| 이식성 | 실행·배포·설정·서비스 교체 조건이 변함: 해당 환경의 적응·설치·대체 조건을 충족하는가 |

`+`에서는 주어진 구현·환경·인터페이스·설계 제약을 기록한다. 데이터 무결성은 정합성 업무 규칙(BR), 기능 정확성, 보안의 무결성, 실패 후 신뢰성 중 실제 목표에 연결한다. 별도 이름만으로 중복 QR을 만들지 않는다. 강의의 사용 품질(효과성·효율성·만족 등)은 사람의 작업 결과가 필요할 때 P09로 선택하며 제품 검사만으로 사용자 만족을 측정했다고 주장하지 않는다.

**입력 → 수행 → 산출물:** 사용자 목표·변경·실패 위험 → (1) 위 신호에 해당하는 범주를 선택한다. (2) 목표·대상·상황을 붙인다. (3) 서로 충돌할 수 있는 목표를 동일 상황에서 비교한다. (4) 필수 조건을 먼저 보존하고 나머지 대안의 품질 영향을 설계 결정으로 기록한다 → `분류 체계·판 / 선택 속성 / 적용 근거 / QR·BR / 미적용 이유 / 충돌·결정`.

**판정:** 선택 속성에 상황·목표·확인 방법이 있으며 미선택 이유가 변경 범위와 맞으면 선정 통과다. 관련된 권한·데이터 실패를 “보안은 이번에 안 함”으로 제외하거나 성능을 개선하려고 확정 무결성 규칙을 낮추면 수정 필요다.

**경계·축약:** 정적 문구 수정은 관련 표시·사용성·접근성 결과 확인으로 충분할 수 있다. 판마다 특성·하위특성이 다르므로 2011판의 그림을 2023판 전체 준수 근거로 사용하지 않는다. 이 지침은 새 품질 목표 수치나 표준 인증을 확정하지 않는다.

## P09. QAS·속성별 측정·목표 도출

**연결:** C08. **근거:** 강의 pp.133·139·172·269의 환경 의존 품질·검증 가능한 목표; [SEI의 CMU/SEI-2004-TR-011 §2.2.1](https://sei.cmu.edu/documents/734/2004_005_001_14396.pdf)의 6요소 QAS; [SEI QAW 공식 절차](https://sei.cmu.edu/library/quality-attribute-workshop-collection/)의 목표·시나리오 수집·통합·우선순위·구체화.

| 후보 | 선택 조건 |
| --- | --- |
| QR별 6요소 QAS + 단일 속성의 실행 검증 | 이번 변경의 성능·실패·보안·유지보수 목표를 상황으로 확인해야 함. EDGE 기본 |
| QAW를 축약한 품질 대화 | 사용자·운영·개발 관점이 달라 품질 속성·상황·우선순위가 미정 |
| 정식 QAW | 여러 이해관계자의 아키텍처 주요 품질을 함께 도출해야 하고 참여·진행 자원이 실제 확보됨 |
| 기존 QAS의 조건·결과 갱신 | 목표·환경·대상은 유효하고 측정할 동작만 변경됨 |

**EDGE 기본 선택:** 자극원·자극·대상·환경·응답·응답 측정에 `목표 출처 / 도구·관찰 방법 / 데이터·표본 / 비교 조건 / 상태`를 추가한다. 축약 QAW는 목표·기술 제약 공유→상황 수집→중복 통합→M01 우선순위→선택 상황의 6요소 구체화로 수행하고 정식 QAW 개최로 표시하지 않는다.

| 속성 | 지표·측정 후보 | 후보 선택과 비교 조건 |
| --- | --- | --- |
| 응답 성능 | 사용자 이벤트→표시 완료 지연, API 지연 분포, 처리량·오류율, 메모리·CPU | UI 목표면 사용자에게 결과가 보이는 구간; API 목표면 서버/왕복 구간을 구분. 같은 데이터량·기기·네트워크·동시 요청·캐시 상태에서 비교 |
| 신뢰성·복구 | 성공/실패 비율, 장애 탐지·복구 소요, 실패 전후 상태·손실, 허용 중단 | 복구 규칙 변경이면 장애 주입 후 최종 상태·복구 경로; 장기 가용성 목표면 관측 기간·장애 정의가 있는 운영 기록. 짧은 로컬 실행을 장기 가용성으로 대체하지 않음 |
| 보안·무결성 | 역할×연산 허용/거부, 비밀/데이터 노출, 금지 부작용, 불변조건 위반 | 목표에 해당하는 실제 서버 경계·저장소 전후 상태를 관찰. 화면 버튼 숨김이나 빌드 성공만으로 판정하지 않음 |
| 사용성·사용 품질 | 목표 완료·실수·도움 필요·작업시간·피드백 | 사람이 이해·수행하는 목표면 대표 역할·과제·도움 조건을 정한 관찰. 개발자 수동 실행은 흐름 확인으로 기록하고 사용자 학습·만족 자료와 구분 |
| 접근성 | 선택한 성공 기준별 자동 탐지·키보드/보조기술 수동 결과 | 관련 화면·내용·입력 상태에서 검사. 자동 검사만으로 전체 접근성 준수를 주장하지 않음 |
| 유지보수성 | 대표 변경의 영향 위치·인터페이스·수정/검증 절차, 분석·테스트 가능성 | 실제 예상되는 변경 시나리오를 주고 수정 책임을 찾아 검토. 시간 목표가 있으면 시작·종료·작업자·범위를 고정; 코드 줄 수 감소만으로 판정하지 않음 |
| 호환성·이식성 | 입력/출력·소비자 계약 결과, 환경별 실행/빌드·설정·기능 결과 | 지원 대상으로 확정된 버전·환경·소비자를 비교. 새 환경을 임의로 지원 요구사항에 추가하지 않음 |

**입력 → 수행 → 산출물:** 선택 QR·목표·현실 제약 → (1) 6요소로 상황을 고정한다. (2) 목표값은 명시된 사용자/운영 기준→기존 확정 계약→현행 기준선과 실제 허용 저하/개선 논의 순으로 도출한다. 근거가 없으면 제안·미정이다. (3) 위 표에서 관찰 구간·지표·방법을 고른다. (4) 결정적인 불변조건은 관련 상태·입력별 결과로, 변동하는 성능은 데이터량·부하·캐시 상태별 표본과 요약 통계로 측정 계획을 정한다. (5) 예비 실행으로 변동·환경 왜곡을 확인하고 비교 전에 표본수·실행횟수·요약 방식·재실행 조건을 기록한다. (6) 정해진 조건으로 실행한 원자료·결과·차이·제약을 남긴다 → QR/QAS와 측정 계획·실제 결과.

**판정:** 기준값·환경·관찰 방법이 정해지고 그 조건의 결과가 기준을 만족해야 QR 통과다. 평균만 제시해 꼬리 지연 기준을 대신하거나 서로 다른 부하·캐시·환경 결과를 직접 비교하면 수정 필요다. 관측이 부족하거나 환경 차이·표본 변동이 기준과의 차이보다 커 결론을 못 내리면 판정 불가와 추가 확인 조건을 기록한다. 소규모 사용성 관찰은 해당 과제·표본 결과로 한정하고 일반 사용자 전체의 성향으로 확장하지 않는다.

**변동 자료에서 선택할 방법:** [NIST 평균의 신뢰구간](https://www.itl.nist.gov/div898/handbook/eda/section3/eda352.htm), [대응 관측](https://www.itl.nist.gov/div898/handbook/prc/section3/prc311.htm), [Bootstrap](https://www.itl.nist.gov/div898/handbook/eda/section3/bootplot.htm)을 근거로 아래 중 주장에 맞는 방법을 선택한다.

| 후보 | 사용할 주장·수행 | 한계·판정 |
| --- | --- | --- |
| 기술 통계 | “이번 조건·표본에서 어떤 결과였는가”: 표본수·실패 수·중앙값·분포·요구된 백분위수를 원자료와 함께 보고 | 모집단 일반화·유의성·개선 확률을 주장하지 않음. 결정적 규칙 또는 해당 실행 결과 확인의 기본 |
| 반복 측정 대조 | “같은 조건에서 변경 전후가 어떻게 달랐는가”: 입력·기기·부하·캐시 조건을 맞춰 전후 실행을 반복하고 조건별 차이·변동을 보고. 실제 같은 대상끼리 대응되면 쌍별 차이를 사용 | 시간·환경 변화가 결과를 섞지 않도록 전후 순서를 교차/무작위 배치하고 순서·초기화·워밍업을 기록. 원래 대응되지 않는 자료를 임의로 짝짓지 않음. 관측한 차이와 모집단 평균 개선 주장은 구별 |
| 신뢰구간 추정 | “모집단 평균 또는 평균 차이의 불확실성은 어느 범위인가”: 독립·대표 표본과 근사 정규성 근거가 있으면 평균에 `평균 ± t값 × 표준편차/√표본수`를 적용; 대응 자료는 쌍별 차이의 평균에 적용. 중앙값 등 공식을 직접 쓰기 어려운 통계량은 독립 관측 단위를 복원추출→통계량 재계산→반복 분포의 구간으로 얻는 Bootstrap 후보를 비교 | 추정 대상·신뢰수준·단측/양측·유효 가정을 실행 전에 적음. 평균 구간을 백분위수/개별 요청의 상한으로 쓰지 않음. Bootstrap도 빠진 꼬리 자료·편향을 복구하지 않으며 극값 의존 통계량에 자동 적용하지 않음. 가정·정밀도가 부족하면 판정 불가 |

표본 단위는 사용자·독립 실행·요청 중 주장에 맞게 지정한다. 같은 세션·부하 실행의 연속 요청이 상관되면 각각을 독립 표본으로 세지 않고 실행/세션 단위로 분석하거나 독립 수집을 다시 설계한다([NIST 자기상관](https://www.itl.nist.gov/div898/handbook/eda/section3/eda35c.htm)). 표본수·반복수는 예비 변동과 필요한 구간 정밀도·시간 예산을 기록해 선택한다. 평균 추정은 예비 표준편차 `s`, 요구 반폭 `E`, 선택 신뢰수준의 `t`로 `n ≈ (t×s/E)²`를 출발 추정치로 삼아 자유도와 함께 조정할 수 있다. 예산 부족으로 요구 정밀도를 못 얻으면 일반화 통과를 선언하지 않는다. 원하는 결과가 나온 시점에 임의로 중단·불리한 실행 삭제를 하지 않는다.

**경계·축약:** 소규모 결정적 규칙 검증에 통계적 신뢰구간을 강제하지 않는다. QR가 해당 실행 결과만 요구하면 기술 통계·반복 대조로 충분하다. 원문의 5초·워크숍 인원·상위 시나리오 개수·반복 횟수 등을 EDGE 목표로 복사하지 않는다. 기존 명세가 충분한 간단 수정은 해당 조건과 실제 확인 결과를 참조한다.

| 후보 | 선택 조건 |
| --- | --- |
| Fully Dressed | 이번에 구현할 주요 사용자 목표·업무 규칙, 권한·쓰기·외부 실패·상태 변화가 있는 UC. EDGE 기본 |
| brief | 초기 목표 목록·보류 범위를 빠르게 찾을 때; 구현 직전에는 필요한 상세를 보완 |
| casual 또는 기존 필드의 축약 | 단순 조회·명확한 기존 동작 수정이며 실패·보장을 짧게 표현 가능. 기존 기준의 축약 필드는 유지 |
| 행위자/시스템 2열 흐름 | 대화 주체·응답의 대응이 혼동됨. Fully Dressed의 기본/확장 흐름 안에 사용 가능 |
| 공통 하위기능 UC | 여러 목표에서 같은 하위 흐름을 재사용하며 독립한 규칙이 있음. 호출 목표·종료 결과를 연결 |

**EDGE 기본 선택:** 목표 목록을 먼저 만들고 이번 구현·위험에 해당하는 UC부터 Fully Dressed로 상세화한다. 사용자 목표는 완료 결과가 그 역할에게 가치가 있고 시스템·데이터가 안정된 종료 상태에 이르는 작업이다. 한 클릭·필드 입력은 대개 하위기능, 여러 독립 목표를 장기간 묶는 것은 상위 요약 목표다. Larman의 가치(업무 설명), EBP(한 작업의 완결), 크기(한 단계로 축소됐는지) 질문을 판별에 활용하되 페이지 수·시간 길이를 강제 기준으로 쓰지 않는다.

**입력 → 수행 → 산출물:** P03의 경계·역할·목표, FR·BR·QR → (1) 역할마다 목표·성공 결과를 나열한다. (2) 목표 수준을 판정하고 동사+목적어 이름을 붙인다. (3) 주행위자·지원 행위자·직접 참여하지 않지만 이해관계가 있는 역할을 구분한다. (4) 각 이해관계자의 관심사를 사용자 결과·데이터·권한·외부 책임에 연결한다. (5) 정상 흐름은 의도·책임·관찰 결과 중심으로 번호를 붙인다. (6) 각 단계에 관련된 잘못된 입력·거부·실패·취소·대안을 번호로 연결하고 복귀 또는 종료를 적는다. (7) 성공 흐름들의 사후조건을 모아 성공 보장을, 실패 경로에서도 지켜야 하는 BR·보존 상태를 모아 최소 보장을 작성한다. (8) 관련 QR·미정·추적 ID를 붙인다 → UC와 역할·관심사→보장·흐름의 대응.

**판정:** 이번 목표의 관심사가 흐름·보장·관련 규칙에 연결되고 기본/확장 흐름의 종료 상태가 명시되어야 통과다. 최소 보장에 지원하지 않는 자동 복구·기록 기능을 새로 넣거나, 시스템 내부 DB 호출을 초기 사용자 흐름으로 적으면 수정 필요다. `로그인 완료`를 전제로 둔 UC라도 실제 구현의 서버 권한 검사를 생략할 수 없다. 전제조건은 분석의 가정이며 경계 검증을 대체하지 않는다.

**경계·축약:** 인증 같은 하위 목표가 핵심 권한·실패 규칙을 가지면 별도 상세 UC로 작성할 수 있다. CRUD를 하나의 “관리” UC로 합칠 수 있으나 연산마다 권한·실패·보장이 다르면 분리 또는 명확한 하위 흐름이 필요하다. 변경하지 않는 기존 흐름은 참조하고 새 위험·확장·보장만 갱신한다. 소급 전체 UC 목록·그림·include/extend 관계를 강제하지 않는다.

## P11. 도메인 개념·관계·데이터 사전과 정규화

**연결:** C10 및 C12의 데이터 의미. **근거:** 강의 pp.71–75·151–156·238–241의 도메인/데이터 모델·사전; [Larman의 개념 식별 공개 미리보기](https://www.oreilly.com/library/view/applying-uml-and/0130925691/0130925691_ch10lev1sec3.html)의 현재 시나리오에 제한한 점진적 모델링; [Microsoft 데이터 설계 공식 설명](https://support.microsoft.com/en-us/access/database-design-basics)의 논리 관계·1–3 정규형. 아래 후보 추출 절차는 EDGE에서 이 모델을 만드는 운영 방법이다.

| 후보 | 선택 조건 |
| --- | --- |
| 시나리오의 대상·역할·사건·규칙에서 개념 추출 | 사용자 흐름과 업무 규칙이 있음. EDGE 기본 |
| 명사·명사구 후보 목록 | 요구사항·운영 문장에 여러 개념이 흩어져 누락 점검이 필요함. 명사를 자동 클래스로 확정하지 않음 |
| 개념 범주로 보완 | 역할·거래/활동·기록·항목·분류·장소·정책·상태 등의 빠진 개념을 점검해야 함 |
| 개념·관계·규칙 표 | 관계 수가 적고 의미·다중성을 표로 명확히 표현 가능 |
| UML 도메인 개념도 | 여러 개념·관계·다중성이 얽혀 한눈에 대조해야 함. 구현 메서드·DB 외래키 중심 그림과 구분 |
| 논리 ERD·관계형 정규화 | 영속 데이터의 구조·키·종속성이 변경됨. OOA 개념 모델을 저장 모델로 변환하는 설계 작업 |

**EDGE 기본 선택:** 현재 UC에 필요한 개념·관계·불변조건을 표로 만들고 데이터가 경계를 넘거나 저장 의미가 바뀌면 사전 항목을 추가한다. 저장 구조의 결정은 분석 의미를 확인한 후 설계에서 한다.

**입력 → 수행 → 산출물:** UC·BR·입출력 사례 → (1) 시나리오가 다루는 대상·역할·사건·기록을 후보로 모은다. (2) 같은 뜻은 합치고 다른 뜻의 동음어는 범위를 구분한다. (3) 독립된 정체성·관계·수명/규칙이 있는 것은 개념, 다른 개념을 설명하는 값은 속성, 화면·컨트롤러·라이브러리는 구현 요소로 분류한다. (4) UC가 기억·연결해야 할 관계에 양쪽 역할·다중성·필수/선택 조건을 적는다. (5) 관련 상태에서 항상 지켜야 할 규칙을 BR로 적고 정상·실패·동시 요청에서 유지되어야 하는 조건을 확인한다. (6) 경계 데이터·규칙 해석을 사전에 고정한다 → 개념/관계/속성 표 또는 개념도, BR·데이터 사전.

**사전의 실제 항목:** `이름·별칭 / 업무 의미 / 논리 타입·형식 / 허용값·범위 / 단위·시간대·정렬·대소문자 의미 / 필수·null·빈 값 / 식별·유일성 / 제공자·소비자 / 입력 변환·검증 / 관련 FR·BR`. 적용되지 않는 필드는 이유를 적는다. 외부 문자열과 내부 값이 다르면 `원본 형식→내부 형식 / 변환 책임 / 오류 결과 / 정보 손실 여부`를 별도 적는다.

**입력 정규화와 DB 정규화의 구분:** 문자열 공백·대소문자·Unicode·날짜·코드 변환은 입력의 동등성·표현 계약이다. 손실 없이 허용할 변환, 거부할 입력, 변환 전후 동등 의미를 명세에서 정하고 수행한다. 관계형 정규화는 저장 속성의 종속성·갱신 이상을 줄이는 구조 설계다. **후보 키·함수 종속·1–3NF의 정확한 판정 원본은 [D06 영속 데이터 모델](DESIGN_IMPLEMENTATION.md#d06)의 수행 1–3이다.** 여기서는 그 결과를 분석의 데이터 의미와 연결한다. 반복 그룹/원자 도메인, 부분 종속, 전이 종속을 살피는 실무 요약만으로 여러 후보 키가 있는 구조의 정규화 완료를 판정하지 않는다. 분리한 관계를 다시 결합해 필요한 정보가 보존되는지도 확인한다. 성능 때문에 중복·읽기 모델을 유지하는 대안은 실제 측정 근거·정본 데이터·동기화·오래된 값 정책이 있을 때 비교한다.

**판정:** 같은 용어·데이터의 의미가 UC·BR·사전·연산에서 같고 관계·불변조건을 사례로 판별할 수 있어야 통과다. 제목처럼 설명 값만으로 같은 객체 여부를 단정하거나, `null`·빈 값·삭제·시간대의 의미가 호출자마다 다르면 수정 필요다. 정규화된 테이블이라고 사용자·도메인 정보가 충분하다고 판정하지 않는다.

**경계·축약:** 모든 명사를 개념으로 만들거나 현재 UC와 무관한 업무 전체 모델을 작성하지 않는다. 사전은 바뀌는 필드와 해석에 필요한 기존 필드만 적을 수 있다. 중첩 문서·배열이 허용된 저장소에 관계형 1NF를 그대로 강제하지 않고 해당 저장 모델의 계약을 정한다. 단순 값 변환과 도메인 자체 규칙을 같은 “정규화”라는 말로 혼동하지 않는다.

## P12. UC→SSD·입출력 표→시스템 연산·계약

**연결:** C11. **근거:** 강의 pp.387–391의 외부 이벤트·블랙박스 시스템·의도 중심 연산; [Larman의 연산 계약 공개 예](https://www.oreilly.com/library/view/applying-uml-and/0130925691/0130925691_ch13lev1sec3.html)의 연산·UC 참조·전제·인스턴스/속성/관계 사후조건; [계약 사용 범위 설명](https://www.oreilly.com/library/view/applying-uml-and/0130925691/0130925691_ch13lev1sec13.html)의 복잡한 연산에 대한 상세화. UML 그림 표기는 [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/) §17.3.4·17.4.4·17.6.4·17.8의 생명선·메시지·복합 구간·시퀀스 표기를 사용한다.

| 후보 | 선택 조건 |
| --- | --- |
| 입출력·연산 표 | 한 번의 요청/응답 또는 순서·반복·외부 응답을 표로 명확히 표현 가능. EDGE 기본 |
| SSD | 여러 행위자·이벤트 순서·반복·대안·외부 시스템 응답을 시각적으로 대조해야 함 |
| 전제·사후조건 연산 계약 | 하나의 연산이 여러 개념/상태를 갱신하거나 결과·무결성·실패 상태가 미묘함 |
| 인수 기준·기존 계약 참조 | 단순 조회·단일 값 변경이고 중복 서술 없이 결과를 충분히 설명 가능 |

**EDGE 기본 선택:** UC의 경계 이벤트마다 OP를 표로 도출하고 복잡한 쓰기·상태 변화는 계약을 상세화한다. SSD는 UML의 별도 다이어그램 종류가 아니라 시스템을 블랙박스로 둔 시퀀스 다이어그램의 사용 방식이다.

**입력 → 수행 → 산출물:** UC의 한 정상/예외 시나리오·사전·BR → (1) 행위자가 시스템 경계로 보내는 의도·입력을 표시한다. (2) 외부 이벤트마다 `OP-ID / 이름·매개변수 / UC 단계 / 요청자 / 결과·오류 / 상태 영향`을 적는다. (3) 내부 함수 호출·UI 클릭 장치를 연산 이름으로 바꾸지 않고 의도를 표현한다. (4) 필요하면 행위자와 시스템 생명선, 위→아래 순서, 메시지·응답, 반복/대안 조건으로 SSD를 그린다. (5) 복잡한 OP는 전제·성공·실패 후 상태·관련 불변조건을 작성한다. (6) 이벤트가 사라진 UC 단계 또는 근거 UC가 없는 OP를 대조한다 → OP 목록·필요 SSD·연산 계약.

**계약 작성:** `연산·입력·UC 참조 / 전제조건 / 출력 / 생성·삭제된 개념 인스턴스 / 달라진 속성 / 생긴·해제된 관계 / 실패 후 상태 / 유지할 BR`. 사후조건은 끝난 후 참이어야 하는 상태를 적고, SQL·컴포넌트 호출 알고리즘으로 대체하지 않는다. 조회는 반환 범위·순서·없는 결과와 저장 상태 변경 없음 여부를 명세에 맞게 적는다. API·오류 스키마 같은 실제 인터페이스 계약은 설계 문서에서 구체화한다.

**SSD 실제 표기:** 이름을 적은 생명선 머리와 수직 점선에 관련 행위자·블랙박스 시스템을 배치하고 외부 사건을 `연산명(입력)` 메시지로 연결한다. 동기 호출은 채운 화살촉, 비동기 전달은 열린 화살촉, 회신은 점선 화살표로 구별한다. 위→아래 순서는 해당 생명선의 사건 순서이며 선 사이 간격은 실제 시간 길이가 아니다. 대안은 `alt` 구간의 `[조건]`·`[else]`와 점선 구분선, 반복은 `loop` 구간의 실행 조건·필요한 반복 상한/종료 조건으로 표시한다. 대안·반복이 없는 단순 요청에는 구간을 추가하지 않는다. 동기/비동기·메시지 순서가 아직 결정되지 않았으면 가정으로 표시하고 실제 API·연동 계약에서 확정한다.

**판정:** 범위 내 외부 이벤트에 응답 연산과 예상 결과가 있고 OP의 성공·실패 상태가 UC 보장·BR과 일치하면 통과다. 한 사용자 입력으로 여러 내부 함수를 호출한다는 이유만으로 여러 시스템 연산을 만들거나, 연산은 성공인데 UC 성공 보장이 깨지면 수정 필요다.

**경계·축약:** 복잡하지 않은 연산은 명확한 인수 기준을 참조해 계약 중복을 줄인다. UC의 전제조건을 외부 호출자에게 검증 없이 신뢰하는 구현은 허용하지 않는다. 권한·입력·상태 거부는 실제 경계에서 설계하고 검증한다. SSD에서 메시지 순서를 그렸다는 것만으로 동시 요청의 원자성이 증명되는 것은 아니다.

## P13. DFD·분해·균형 검사·처리 명세

**연결:** C12. **근거:** 강의 pp.217–238·244–245의 SASD, 계층적 DFD·데이터/제어 표기·처리 명세·사전. **표기는 p.228의 CDFD 계열 범례**를 선택하고 일반 데이터 흐름과 제어 흐름을 구별한다. 아래 입출력 대조·금지 연결은 EDGE에서 이 분석을 일관되게 적용하는 검토 규칙이다.

| 후보 | 선택 조건 |
| --- | --- |
| 입출력→변환→출력 표 | 외부 데이터 하나의 단순 필터·매핑·검증이면 충분. 기본 축약 |
| 데이터 DFD + 사전·처리 명세 | 여러 입력·변환 단계·저장·집계·재사용 데이터가 있어 데이터가 어디서 생기고 없어지는지 확인해야 함 |
| 제어 흐름 확장 + FSM | 시간 이벤트·외부 제어 신호에 따라 처리 활성화·상태가 변함 |
| 활동/단계 흐름 표 | 핵심 질문이 데이터의 이동보다 작업 순서·분기·병렬 처리임. DFD에 시간 순서를 억지로 넣지 않음 |

**EDGE 기본 선택:** 데이터 가공 질문은 DFD, 작업 순서 질문은 단계/활동 표현으로 답한다. “복잡함”은 둘 이상의 출처·변환·저장 단계 사이에서 데이터 의미·생성 책임·오류 분기·분해 경계가 문장만으로 불명확한 경우로 판정한다.

**실제 표기:** 데이터 처리=실선 타원(`번호+동사 목적어`), 외부 종단=직사각형(`역할/외부 시스템`), 저장소=평행선(`저장 데이터`), 데이터 흐름=이름 있는 실선 화살표, 제어 처리=점선 타원, 제어 흐름=점선 화살표. 자체 블록도를 쓰면 UML/표준 DFD로 부르지 않고 이 범례에 대응하는 의미를 적는다. EDGE 번호는 맥락 프로세스 `0`→주요 처리 `1,2,…`→처리 `1`의 분해 `1.1,1.2,…`로 기록하며 수준 명칭·번호를 문서 안에서 통일한다.

**입력 → 수행 → 산출물:** 시스템 경계·이벤트·사전 → (1) 맥락 프로세스와 경계를 넘는 데이터를 그린다. (2) 입력을 어떤 출력/저장으로 변환하는지 주요 처리로 나눈다. (3) 처리 의미가 사전·알고리즘/표로 설명될 때까지 필요한 부분만 분해한다. (4) 부모 처리에 들어오고 나가는 데이터와 자식 그림 전체 경계의 데이터를 비교한다. 합성 데이터를 나누면 사전에 구성요소를 정의하고 의미가 보존되는지 확인한다. (5) 각 흐름·저장소를 사전에 연결한다. (6) 실제 변환을 담당하는 말단 처리의 명세를 작성하고 상위 처리는 분해·조정의 역할과 하위 참조를 적는다 → 필요한 DFD 계층·사전·처리 명세·균형 검사 결과.

**균형·구조 판정:** 외부 엔티티→외부 엔티티, 외부 엔티티↔저장소, 저장소↔저장소 직접 연결로 사이트의 처리 책임을 생략하지 않는다. 그런 외부 관계는 맥락 설명으로 구분한다. 처리에는 필요한 입력·출력·의미 변환 근거가 있어야 하며 입력 없이 새로운 업무 데이터를 생성하는 처리, 필요한 결과가 없는 처리, 입력에 근거하지 않는 결과는 검토 대상이다. 생성기·이벤트·기록 전용 처리가 실제 요구사항이면 출처/이벤트·최종 저장을 명시해 예외 이유를 설명한다. 부모와 자식의 외부 데이터 의미가 달라지면 수정 필요다. 새 내부 중간 데이터·내부 저장소는 허용하되 외부 계약이 바뀌면 부모·요구사항도 갱신한다.

**처리 명세의 실제 필드:** `처리 ID·이름 / 부모·하위 참조 / 입력·출력·사전 ID / 적용 BR / 전제·검증 / 변환·오류·종료 결과 / 관련 TC`. 순서·반복·변환은 구조화된 의사코드, 유한한 조건 조합은 결정표, 상태 의존 제어는 P14의 상태표를 선택한다. 의사코드는 읽기·검증·변환·출력/저장의 순서와 오류 결과를 적는다. 결정표는 조건 행·실행 가능한 규칙 열·결과 행을 두고 같은 결과의 다른 조건도 빠뜨리지 않는다. 상위 프로세스마다 하위 알고리즘을 복제하지 않는다.

**판정:** 변경 범위의 흐름·저장 데이터가 정의되고 부모/자식·사전·처리 명세 입출력과 규칙이 일치하면 통과다. DFD를 그렸지만 흐름 타입·오류 결과가 없거나 원본 데이터와 정규화된 값의 관계가 빠지면 수정 필요다. 데이터 처리 도식만으로 FSM·시간 순서·동시성·DB 트랜잭션이 확인되었다고 판정하지 않는다.

**경계·축약:** 단순 변환은 `입력·타입 / 변환·BR / 출력·오류` 표로 충분하다. 과제의 RVC 센서·제어 방향·전체 DFD 깊이를 사이트에 복사하지 않는다. 입력 표현 정규화와 관계형 저장 정규화는 P11의 서로 다른 절차를 적용한다.

## P14. FSM·상태표의 도달성·Guard·복구 검사

**연결:** C13. **근거:** 강의 pp.193·235·244의 FSM·누락 상태·교착·우선순위 문제; [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/) §14.2.3.8–14.2.3.9의 전이·Guard·이벤트 처리. Guard가 동시에 참인 경우 UML이 자동으로 도메인 우선순위를 정해 준다고 가정하지 않는다.

| 후보 | 선택 조건 |
| --- | --- |
| 상태×이벤트 전이표 | 상태 수가 작고 허용/거부·Guard·사후상태를 행별로 확인 가능. EDGE 기본 |
| 단순 FSM 그림 + 동일 전이표 | 경로·도달·반복·복구가 표만으로 잘 보이지 않음 |
| UML StateMachine·계층 상태 | 실제 중첩·병렬 상태가 있고 단일 평면 모델이 의미를 왜곡함. 공식 이벤트·entry/exit·지역 의미를 명시 |
| 상태 모델의 실행·시뮬레이션 | 상태 조합·경로가 많거나 회복·순서 결함을 문서 검토만으로 구분하기 어려움 |

**EDGE 기본 선택:** 상태를 화면 이름 대신 도메인·작업의 의미로 정의하고 `출발 상태 / 이벤트·입력 / Guard / 동작·부작용 / 도착 상태 / 실패 결과 / 관련 BR·TC`를 작성한다. 승인된 동작에 필요한 관련 상태를 범위로 삼는다.

**입력 → 수행 → 산출물:** UC·BR·OP·실패 조건 → (1) 상태의 의미·초기 상태·정상 종료·오류/취소/복구 상태를 정한다. (2) 각 관련 상태에 적용 가능한 이벤트를 목록화하고 허용 전이 또는 거부·무시·지연 결과를 적는다. (3) 동일 상태·이벤트의 Guard들을 결정표로 비교한다. (4) 초기 상태에서 전이를 따라 도달 가능한 상태를 표시하고 실제 경로의 Guard가 만족 가능한지 확인한다. (5) 진행이 필요한 비종료 상태에 성공·실패·취소·복구 중 계약된 종료/진행 경로가 있는지 확인한다. (6) 전이 후의 불변조건·중복 이벤트·저장 전후 상태를 검토한다 → 상태 정의·전이표·필요한 그림·도달/Guard/복구 검토 결과.

**실제 검사 규칙:**

1. Guard `g1`과 `g2`가 동시에 참이 될 실행 가능한 입력이 있는지 찾는다. 다른 결과를 내는데 겹치면 명시된 우선순위를 반영해 조건을 배타적으로 바꾸거나 요구사항 결정을 확인한다. 그림의 화살표 위치·코드 if문 순서만으로 업무 규칙을 만들지 않는다.
2. 허용된 입력 영역에서 어떤 Guard도 참이 아닌 경우를 찾는다. 의도된 거부·무시라면 결과를 적고, 처리해야 하는 입력이면 빠진 전이로 판정한다.
3. 초기 상태부터 그래프 탐색으로 후보 도달 상태를 찾되 Guard가 불가능한 경로는 제외한다. 도달 불가 상태가 요구사항상 필요하면 진입 경로/전제 누락이고, 의도한 미지원 상태면 범위에서 제외한 근거를 적는다.
4. 종료 상태·정상 대기와 교착을 구별한다. 진행·복구가 요구되는데 가능한 전이가 없거나 끝나지 않는 반복만 있으면 수정 필요다. 영구 거부·최종 삭제처럼 명세상 종료인 상태에 무조건 복구 경로를 만들지 않는다.

**판정:** 관련 상태·이벤트의 허용/거부 결과와 실행 가능한 경로·우선순위·보장이 일치하면 통과다. 모델에만 복구가 있고 구현·계약은 지원하지 않거나 Guard 겹침이 미정이면 수정 필요다. 표·그림 검토는 명세 검토이며 실제 동시 요청 안전성·전이 실행 검증과 구별한다.

**경계·축약:** 현재 상태에 따라 같은 이벤트 결과가 달라지지 않는 정적 조회에는 별도 FSM을 만들지 않는다. 같은 결과를 내는 조건을 합칠 때도 허용·거부 입력 영역을 보존한다. 전체 입력값 전수 열거가 어려우면 Guard의 의미상 분할·경계로 검토하고 남은 불확실성을 적는다. 형식 검증 도구는 복잡성과 실제 이익을 확인한 경우 별도 선택한다.

## P15. SASD·OOAD·혼합 분석의 선택

**연결:** C14. **근거:** 강의 pp.67·71·151–156의 기능 분해 관점과 개념·책임·협력 관점. 구현 언어만으로 분석 방법을 결정하지 않는다.

| 후보 | 선택 조건 | 선택한 관점의 산출물 |
| --- | --- | --- |
| OOAD | 역할 목표·도메인 개념·업무 상태·책임 협력이 중심 | UC·도메인/규칙·SSD/OP → 필요한 책임·호출 설계 |
| SASD | 입력→변환→출력·처리 분해·데이터 계보 또는 제어 처리가 핵심 | 맥락·이벤트·DFD·사전·처리 명세·필요 FSM → 처리/모듈 설계 |
| 목적별 혼합 | 사용자 흐름은 OOAD로, 일부 수집·집계·변환의 누락은 SASD로 확인하는 등 서로 다른 질문이 있음 | 동일 FR·BR·용어·데이터 계약을 참조하는 필요한 모델 |
| 짧은 분석 표 | 명확한 기존 동작의 작은 수정 | 역할·입력·결과·상태·수정 책임·검증 대상 |

**EDGE 기본 선택:** 웹 사용자 기능은 목표·UC·개념·OP 중심으로 분석하고, 변환 파이프라인에 한해 DFD·처리 명세를 추가한다. React/TypeScript 함수를 UML 클래스에 억지로 맞추거나 SASD를 썼다는 이유로 C 구현·구조적 차트를 필수로 만들지 않는다.

**입력 → 수행 → 산출물:** 해결할 분석 질문·변경 범주 → (1) 사용자 목표, 데이터 변환, 상태 의존, 책임 협력 중 불확실한 질문을 적는다. (2) 표의 후보로 질문에 답할 최소 모델을 고른다. (3) 모델마다 답할 질문·FR·BR·입출력 참조를 붙인다. (4) 중복된 사실은 하나의 사전·계약에서 정의하고 모델에서 참조한다 → `관점 / 선택 질문·이유 / 모델 / 공통 근거 / 생략한 관점·이유`.

**판정:** 선택 모델이 원래 질문에 답하고 다른 모델·UC·규칙과 모순이 없으면 통과다. 이미 명확한 내용을 형식만 바꿔 두 번 작성하고 추가 검증 목적을 설명하지 못하면 축약한다. 서로 다른 질문을 확인하는 SSD와 DFD는 동일 FR를 참조하더라도 불필요한 중복으로 단정하지 않는다.

**경계·축약:** 사용자 목표가 없는 외부 데이터 변환도 사이트의 입력/결과 계약과 연결해야 한다. 작은 수정은 기존 분석을 참조하고 바뀐 부분만 표로 적을 수 있다.

## P16. 모델·프로토타입·시뮬레이터·디지털 트윈의 효용

**연결:** C36. **근거:** 강의 pp.174–210·211의 목적별 시스템 모델·디지털 트윈 조사; [NIST의 정의·현황](https://www.nist.gov/digital-twins/definitions-and-state-art)은 정의가 맥락별로 다르고 실세계 연결·양방향 교환·수명주기 연결의 의미를 확인해야 함을 설명한다. 이 저장소의 채택은 아래 효용 비교로 결정한다.

| 후보 | 선택 조건 | 한계·유지 비용 |
| --- | --- | --- |
| 설명용 표·정적 모델 | 경계·개념·데이터·전이·책임을 이해·검토할 질문이 있음. EDGE 기본 | 변경 후 실제 명세·코드와 대조해야 함. 실행 결과를 대신하지 않음 |
| 탐색 프로토타입·와이어프레임 | 결과·사용 흐름·개념의 해석을 확인해야 함 | 운영 기능·장애 복구·품질을 보장하는 구현으로 취급하지 않음 |
| 기술 프로토타입 | 제한된 구현·연동·환경의 가능성이 미정 | 검증한 조건 밖으로 결론을 확대하지 않음. 제품 반영 여부 별도 결정 |
| 시뮬레이터·모델 실행 | 상태·외부 장애·부하 등의 실제 재현 비용이 크고 모델로 같은 결정 질문을 확인 가능 | 실제 데이터/관찰로 모델의 규칙·예측이 맞는지 검증해야 함 |
| 디지털 트윈 | 실제 대상의 상태와 지속적으로 연결된 모델로 모니터링·예측·판단을 해야 하는 구체적 요구가 있음 | 대상·동기화 방향/주기·오차·정본·장애 처리·유지 담당·실제 검증 자료가 필요 |

**EDGE 기본 선택:** 표·간단한 모델부터 선택하고 해결되지 않는 질문에만 실행 프로토타입·시뮬레이터를 추가한다. 사이트 기능 명세·상태도·운영 DB 복사본을 이름만 디지털 트윈으로 바꾸지 않는다.

**입력 → 수행 → 산출물:** 결정해야 할 질문·위험·실제 관측 가능성 → (1) 모델로 확인할 주장과 그 결과가 바꿀 결정을 적는다. (2) 가장 단순한 후보부터 실제 재현/검토 비용과 비교한다. (3) 필요한 충실도·입력·관측·유효 조건을 정한다. (4) 실행 모델은 대표 실제 사례와 결과를 비교하고 오차·빠진 행동을 적는다. (5) 동기화·지속 운영이 필요할 때만 트윈 대안을 비교한다 → `질문 / 후보·선택 이유 / 입력·가정 / 검증 근거·오차 / 한계 / 유지·동기화 비용 / 결정 결과`.

**판정:** 모델이 답할 질문이 있고 결과를 실제 근거와 대조할 방법·유효 범위가 있으며 제작·유지 비용보다 확인 이익을 설명하면 채택 가능하다. 실제 대상·동기화·검증 근거가 없는데 트윈 정확성을 주장하거나 설명용 모델을 기능 실행 통과 증거로 쓰면 수정 필요다.

**경계·축약:** 실물·외부 대상이 없는 일반 웹 기능은 우선 정적 모델·프로토타입·테스트로 충분한지 검토한다. NIST의 한 맥락 정의를 모든 분야의 유일한 정의로 강제하지 않는다. 기존 모델 재사용 시 현재 범위에서 가정·버전·계약이 맞는지 확인하고, 불필요한 모델은 제작하지 않은 이유만 남긴다.

## P17. IEEE 830의 역사적 양식과 현재 요구사항 표준

**연결:** C39. **근거:** 강의 pp.160·163–167·245의 IEEE 830-1998 SRS; [IEEE SA의 830-1998 공식 설명](https://standards.ieee.org/ieee/830/1222/)은 ISO/IEC/IEEE 29148:2011에 의해 대체되었음을 명시한다. [ISO의 29148:2018 공식 소개](https://www.iso.org/standard/72089.html)는 요구사항 공학의 수명주기 프로세스·정보 항목·내용/형식 범위를 설명하며, 2026-10-03 확인 시 2018판은 Published, 후속 DIS는 개발 중으로 표시한다.

| 후보 | 선택 조건 |
| --- | --- |
| 강의 SRS 구조를 통합 기능 명세에 적용 | EDGE 일반 개발. 목적·범위·외부 인터페이스·기능·품질·제약·검증을 빠뜨리지 않기 위한 기본 |
| 기존 명세·제품 백로그에 연결 | 동일 기능이 이미 관리되고 있으며 새 파일로 분리하면 내용 불일치·중복이 늘어남 |
| 현행 표준 기반 상세 SRS | 사용자·계약이 특정 판의 적용·제출물·형식을 요구함. 실제 원문과 적용 범위를 확인한 뒤 별도 결정 |

**EDGE 기본 선택:** 강의의 IEEE 830 양식에서 유용한 구조를 차용하고 현재 프로젝트 양식으로 통합한다. 요구사항 수집·작성·검토·추적·변경은 P03–P14와 관리·검증 문서로 실행한다. 문서 제목을 붙인 것만으로 830 또는 29148 전체 준수를 선언하지 않는다.

**입력 → 수행 → 산출물:** 요청·기존 기능 명세·적용 계약 → (1) 특정 표준 판·문서 형식이 실제 지정되었는지 확인한다. (2) 일반 기능이면 기존 양식을 선택하고 목적·범위·역할·외부 계약·FR·BR·QR·제약·인수 기준·추적을 매핑한다. (3) 변경과 관계없는 항목은 이유와 기존 근거 참조로 축약한다. (4) 특정 표준 준수를 요구받으면 원문 접근·적용 조항·산출물·검증 범위를 명시해 프로젝트 절차와 대조한다 → 선택 구조·판/적용 범위·기능 명세·생략/추가 이유.

**판정:** 실제 적용한 양식·판·절차와 주장 범위가 일치하고 기능 요구사항을 작성·검토·갱신할 수 있으면 통과다. 대체된 830을 최신 표준으로 표현하거나 공식 소개만 읽고 유료 표준의 세부 조항 준수를 주장하면 수정 필요다.

**경계·축약:** 여기서는 IEEE/ISO 공식 소개로 판의 관계와 표준 범위를 확인했다. 유료 원문 전체의 조항을 읽었다고 주장하지 않으며, 특정 조항 번호를 임의로 인용하지 않는다. 일반 기능에 전체 조직용 SRS·표준 인증 산출물을 자동 추가하지 않는다. 후속 초안은 공식 발행 판과 구별한다.
