# 설계·구현 방법 선택과 실행 기준

이 문서는 [전체 지침 감사](../GUIDELINE_AUDIT.md)의 C15–C22를 구체화한다. 적용 범위는 EDGE 사이트 전체이다. 아래 **후보**는 사용할 수 있는 방법이며 모두 동시에 도입하라는 지시가 아니다. **EDGE 기본 선택**은 방법의 선택 규칙이지 새 기능·DB·인증 서비스의 선정 또는 기존 코드의 변경 명령이 아니다.

근거 확인일은 2026-10-03이다. `강의 p.N`은 사용자 제공 Software Engineering PDF의 실제 페이지 번호이다. 강의의 과제 #8(p.315)·#9(p.352)·#12(p.462)에서 채택하는 것은 구현 가능한 설계 설명, 스타일·패턴의 비교, 분석 결과와 수정의 연결이다. 지정 예제·분량·도구는 적용하지 않는다. 웹 원전이 설명하는 방법과 이 문서의 EDGE 실행·선택·판정 규칙을 구별한다. 통과 여부는 [작성·판정 기준 §2의 공통 판정 상태](../DEVELOPMENT_CRITERIA.md)에 따라 근거와 함께 남긴다.

현재 환경의 확인 근거는 `game-dev-club-site/package.json`의 Next.js 14.2.3·React·TypeScript와 `game-dev-club-site/src/lib/googleSheet.ts`의 서버 fetch에 있는 `next: { revalidate: 3600 }`이다. 3600은 기존 코드의 값이며 모든 기능에 채택한 신선도 기준이 아니다. 이후 작업에서는 실제 변경 대상과 설치 버전을 다시 확인한다.

**판정 단계:** OOD에서는 계약·책임·저장 기술 지원 근거·실패 처리·검증 계획의 완성을 판정한다. 아래 실제 호출·경합·저장 결과가 계약과 같다는 기준은 구현 후 [T01-T13](TESTING_QA.md)의 실행 검증에 적용한다. 설계만 요청한 작업에서 테스트 결과 부재로 설계 완료를 막거나 실행 통과로 쓰지 않는다.

## D01. 아키텍처 스타일과 대안 결정

**연결:** C19. **읽은 근거:** 강의 pp.283, 293–301, 315, 325, 337, 352; [Microsoft Architecture styles](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/); [AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html). 스타일은 주요 구성과 의존 관계의 제약을 정하고, 디자인 패턴은 그 구조 안의 반복 문제를 해결한다. 두 명칭을 혼용해 선택 이유를 대신하지 않는다.

| 후보 | 선택 조건 | 확인할 비용·제약 |
| --- | --- | --- |
| 기존 Next 앱 안의 모듈 분리·논리적 계층 | 같은 배포 안에서 화면·업무 규칙·연동 책임을 구별하면 현재 요구사항을 충족함 | 호출 단계 증가, 서버/브라우저 경계, 공유 모듈의 영향. 모든 기능에 새 디렉터리 계층을 만들 필요는 없음 |
| MVC의 관심사 분리 | 같은 데이터에 여러 표현·상호작용이 있고 데이터 규칙과 표현 변경을 독립시킬 필요가 있음 | React 컴포넌트와 서버 함수를 Model/View/Controller 클래스에 일대일로 강제하지 않음 |
| Client–Server | 브라우저와 서버/외부 서비스 사이 네트워크·권한·배포 경계를 설명해야 함 | 지연·실패·인증·버전 호환. 논리 계층과 실제 별도 서버 배포는 구별 |
| 공유 저장소 중심 구조 | 여러 구성요소가 같은 영속 정보를 중심으로 협력함 | 스키마 결합, 저장소 장애, 동시 접근. 아키텍처 Repository와 데이터 접근 함수 패턴은 구별 |
| Pipe–Filter | CSV 가공·검증·변환처럼 순차 단계의 입출력 계약이 분명하고 단계별 재사용이 필요함 | 중간 형식·실패 행 처리·순서·메모리 비용. 간단한 배열 변환은 함수 연결만으로 충분 |
| 이벤트·작업 큐 | 독립 소비자/긴 작업/비동기 완료가 실제 요구되고 순서·중복·지연 처리를 운영할 수 있음 | 전달 보장·관측·실패 메시지·최종 일관성. UI 클릭 이벤트만으로 분산 이벤트 구조를 선택하지 않음 |
| Microservices | 기능별 독립 배포·확장·소유권이 필요하고 데이터 경계·분산 실패·운영 역량이 확보됨 | 서비스 통신·일관성·배포·관측 비용. 예상 성장만으로 서비스 분리를 정당화하지 않음 |

**EDGE 기본 선택:** 기존 Next 앱의 배포 경계를 유지하고 변경 기능의 화면, 서버 조정, 순수 업무 규칙, 연동 책임을 필요한 만큼 구분한다. 기존 경계를 넘는 확정 요구사항이 생기면 대안을 비교한다. 이는 현재 사이트의 규모·의존성·배포 변경 비용을 우선하는 운영 선택이다.

**입력 → 수행 → 산출물:** 확정 FR·QR·제약, 기존 구조, 영향받는 실행 환경을 입력으로 삼는다.

1. 결정할 질문을 한 문장으로 쓴다. 예: “이 연산을 기존 서버 모듈에서 처리할 수 있는가?”
2. `기존 구조 유지 / 가장 작은 변경안 / 실제 가능한 구조 대안`을 적는다. 명백히 무관한 스타일은 조건 불충족을 기록해 제외한다.
3. 필수 제약(권한, 원자성, 배포 환경, 필수 응답 기준 등)을 못 지키는 안을 먼저 기각한다. 좋은 점의 합계로 필수 위반을 상쇄하지 않는다.
4. 남은 안을 `관련 QR / 구현·전환 작업 / 의존성·운영 비용 / 실패·복구 / 근거의 확실성`으로 비교한다. 비용은 확인된 작업과 제약으로 설명하고 근거 없는 점수를 만들지 않는다.
5. 근거가 부족해 선택이 달라질 수 있으면 제한된 기술 확인 또는 미정 기록을 남긴다. 결정을 기능 기록에 통합한 ADR로 저장한다.

ADR 최소 필드: `결정 ID·상태 / 맥락·FR·QR / 후보·기각 근거 / 채택안·이유 / 결과·비용·제약 / 확인 근거 / 재검토 조건 / 대체한 결정 ID`. 제안·채택·기각·대체를 구별한다. AWS 자료의 별도 회의·승인 인원·시간을 EDGE의 추가 승인 절차로 채택하지 않는다.

**판정:** 필수 제약 통과, 비교 근거, 구현할 경계·계약·실패 책임이 있으면 통과. 스타일 이름이나 가상의 미래만 있으면 수정 필요. 핵심 지원 여부를 확인하지 못했으면 판정 불가. 단순 문구 수정에는 “기존 구조 유지, 구조 영향 없음” 한 줄로 축약한다.

## D02. C4·UML·ERD·표 중 표현 선택

**연결:** C16. **읽은 근거:** 강의 pp.285, 287, 321–332; [C4 Diagrams](https://c4model.com/diagrams), [C4 Notation](https://c4model.com/diagrams/notation), [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/). C4의 네 수준을 모두 작성하지 않는다. UML이라고 표시한 그림에는 UML의 관계·메시지 의미를 사용한다. 범례를 정한 비공식 블록도는 UML로 표시하지 않는다.

| 해결할 질문 | 우선 표현과 선택 조건 | 반드시 표현할 요소 |
| --- | --- | --- |
| 누가 무엇과 연결되는가 | 경계·인터페이스 표가 기본. 외부 시스템·신뢰 경계의 전체 연결을 이해하기 어려우면 C4 Context | 사람/외부 시스템/EDGE, 역할·목적, 방향 있는 관계, 이동 데이터, 신뢰 경계 |
| 어디에서 실행·저장되는가 | 실행 환경이 여럿이면 C4 Container 또는 배포 표. 실제 노드별 배포가 핵심이면 배포 그림 | 실행 앱·저장소, 책임, 기술·프로토콜, 배포 환경. C4 Container를 반드시 Docker 컨테이너로 해석하지 않음 |
| 어느 모듈이 책임지는가 | 책임·의존 표가 기본. 관계가 많으면 C4 Component 또는 UML package/component | 모듈 이름·경로, 제공/필요 계약, 의존 방향, 소유 책임 |
| 어떤 순서로 협력·실패하는가 | 호출 단계 표가 기본. 분기·병렬·복구 순서가 핵심이면 UML sequence | 참여자 lifeline, 시간 순서, 메시지·인수·응답, `alt` 조건, 반복 한계, 실패·복구. 병렬이면 `par` 및 공유 상태 |
| 어떤 타입과 관계를 구현하는가 | TypeScript 타입·관계 표가 기본. 실제 상속/구성/대체 관계가 중요하면 UML class | 타입·관련 연산, 연관 역할·다중성, 실제 있는 상속/구현 관계. 개념 도메인과 구현 타입을 구분 |
| 데이터가 어떻게 저장·참조되는가 | 관계·키·제약 표가 기본. 관계 전체 검토가 필요하면 ERD | [D06](#d06)의 엔티티·식별·관계·nullable·삭제 정책. Crow’s Foot 등 채택한 표기를 범례에 명시 |

**EDGE 기본 선택:** 변경 범위의 책임·경계·호출·데이터 표를 기능 문서에 통합한다. 표에서 놓치기 쉬운 순서·관계가 있을 때 해당 질문의 그림을 추가한다. 그림과 표를 동시에 만들 경우 같은 ID·용어·경계를 참조하며 독립 명세로 중복 유지하지 않는다.

**입력 → 수행 → 산출물:** FR·UC·OP·도메인 및 기존 호출 관계 → (1) 답할 질문 하나 선택, (2) 적합한 뷰 선택, (3) 그 뷰의 변경 요소와 인접 경계만 작성, (4) 계약·코드와 대조 → 제목·범위·버전·범례·관련 ID가 있는 모델/표와 선택 또는 생략 이유.

**판정:** 요소 유형·책임, 관계 방향·의미, 조건·단위가 있고 관련 명세와 일치하면 통과. 한 그림에서 시스템·실행 앱·함수 수준이 구분 없이 섞이거나, SQL 호출이 분석 SSD를 대신하거나, 관계가 실제 책임과 다르면 수정 필요. 그림이 없어도 표로 필요한 질문을 답하면 통과한다. 새 표기 도구 설치는 필요 조건이 아니다.

## D03. GRASP에 따른 책임 할당

**연결:** C15. **읽은 근거:** 강의 pp.248, 325–332; Craig Larman의 [GRASP 사용을 설명한 저자 본문](https://www.informit.com/articles/article.aspx?p=360440&seqNum=2), [출판사 제공 Chapter 17](https://www.informit.com/content/images/0130925691/samplechapter/0130925691.pdf)의 Controller·Creator·Expert·Low Coupling 사례; [Protected Variations 저자 본문 §22.4](https://www.oreilly.com/library/view/applying-uml-and/0130925691/0130925691_ch22lev1sec5.html). 마지막 자료는 공개 미리보기에서 정의·적용 대상을 확인한 것이며 책 전체를 읽었다고 주장하지 않는다.

| 후보 원칙 | 해당 책임과 선택 조건 | EDGE 구현 후보 |
| --- | --- | --- |
| Information Expert | 규칙 수행에 필요한 정보와 업무 의미를 가진 곳을 찾음 | 필요한 도메인 값을 받는 순수 함수 또는 관련 모듈. DB 세부 형식을 화면에 노출해 정보를 모으는 안은 재검토 |
| Creator | 생성 대상의 수명·구성·초기 정보를 아는 곳에 생성 책임 배치 | 생성 함수·기존 저장 모듈. 단순 객체 리터럴에 Factory 클래스를 강제하지 않음 |
| Controller | 외부 시스템 연산을 받아 흐름을 조정할 비화면 책임 선택 | 서버 진입부나 사용 흐름 함수가 권한·규칙·저장을 조정. 모든 업무를 한 “관리자” 모듈에 모으지 않음 |
| Protected Variations | 실제 변형/외부 형식 변경의 영향을 안정된 계약으로 제한 | 외부 응답을 내부 타입으로 바꾸는 어댑터 함수. 예상만 있는 대체 공급자용 추상 계층은 보류 |
| High Cohesion·Low Coupling | 후보끼리 무관한 책임과 필요한 의존성 수·내용 비교 | 단일 기능 함수 유지, 순수 규칙 분리, 필요한 계약 전달 중 가장 작은 안 |

**EDGE 기본 선택:** 기존 모듈에 책임을 둘 수 있는지 먼저 확인하고 GRASP 질문으로 배치를 설명한다. 함수·모듈·React 컴포넌트에 적용하며 객체/클래스를 새로 만들기 위한 규칙으로 사용하지 않는다.

**입력 → 수행 → 산출물:** OP·사후조건·불변조건·관련 정보 → (1) “누가 X를 알고/검사하고/생성/저장하는가”로 책임을 쪼갬, (2) 현재 정보 소유자·외부 조정자·생성 후보 식별, (3) 각 후보가 새로 알아야 할 정보·외부 의존·변경 이유 비교, (4) 성공·실패에서 책임 없는 단계 확인 → `OP·규칙 / 책임 / 후보 위치 / 채택 위치 / 협력 계약 / 선택 근거` 표.

**판정:** 모든 OP 사후조건·실패 보장에 담당자가 있고, 필요한 정보를 계약으로 얻으며 무관한 정책이 결합되지 않으면 통과. 화면만 불변조건을 검사하거나 조정자가 모든 데이터 변환·표현·저장을 직접 수행하면 수정 필요. 단일 규칙 함수 하나로 충분한 경우 책임 표 한 행이면 된다.

## D04. 타입·스키마·HTTP 인터페이스 계약

**연결:** C17. **읽은 근거:** 강의 p.332; [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)의 Operation·Request Body·Responses·Schema·Security, [JSON Schema object](https://json-schema.org/understanding-json-schema/reference/object), [TypeScript Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html), [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) §§9, 13, 15, [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) §3. 버전은 여기서 참고한 형식이며 새 도구 설치나 최신 버전 주장과 구별한다.

| 후보 | 선택 조건 | 계약 형식 |
| --- | --- | --- |
| TypeScript 함수 타입 + 계약 표 | 같은 앱 안에서 호출하고 별도 API 소비자·문서 생성 필요가 없음 | 입력/반환 타입과 사전·사후조건·실패·부작용 표 |
| JSON Schema 또는 동등한 런타임 검증 | JSON·CSV·폼·환경 등 신뢰 경계에서 실제 값 검사가 필요함 | 자료형, 필수, null 허용, 길이/범위, enum, 추가 필드 정책. 타입 선언과 실제 값 검사는 별개 |
| OpenAPI | 독립 HTTP 소비자·여러 담당자 간 합의·도구 연동이 필요함 | 경로·method·operationId·파라미터·본문·상태별 응답·인증. 내부 함수마다 OpenAPI는 불필요 |
| 기존 오류 형식 / RFC 9457 Problem Details | 전자는 호환 유지가 중요할 때, 후자는 외부 API의 표준 오류 표현이 필요할 때 | 문제 종류·HTTP status·안전한 설명·식별. 내부 stack·비밀값을 공개 응답으로 내보내지 않음 |

**EDGE 기본 선택:** 내부 TypeScript 타입과 계약 표를 사용하고 외부 입력·응답은 서버 경계에서 실제 검증한다. 이미 사용하는 스키마/오류 형식이 있으면 활용한다. 새 검증 라이브러리 또는 OpenAPI 파일이 필요하면 [D11](#d11)로 선택 근거를 남긴다.

**입력 → 수행 → 산출물:** OP·BR·데이터 사전·소비자 목록 → 다음 순서로 제공자와 소비자가 같은 계약을 참조하게 한다.

1. 입력 필드별 위치·타입·필수/null·허용값·정규화 순서를 정의한다. “trim한다”만 쓰지 않고 어느 필드와 저장/검색 의미에 적용하는지 적는다.
2. 성공 응답·빈 결과·사후 상태를 정하고 오류를 입력/인증/권한/대상 없음/상태 충돌/외부/내부로 분류한다.
3. HTTP 경계이면 의미에 맞는 method·상태·헤더를 지정한다. 아래는 선택 사전이며 모든 endpoint가 모두 반환할 필요는 없다.
4. 재시도·캐시·중복·원자성·금지 부작용은 [D07–D09](#d07)로 연결한다. 클라이언트/서버의 필드·단위·오류 처리와 계약을 대조한다.

| 상황 | HTTP 선택 기준 |
| --- | --- |
| 조회/생성/본문 없는 완료 | 의미에 따라 200 / 201(새 자원 식별 제공) / 204(본문 없음) |
| 입력 오류 | 구문·요청 문제는 400, 형식은 이해했으나 지시 내용을 처리할 수 없는 경우 422를 선택할 수 있음 |
| 인증/권한 | 401에는 적용 인증 방식의 challenge 요구를 고려. 인증돼도 허용되지 않으면 403. 존재를 숨기는 404 선택은 명세에 근거 필요 |
| 대상/충돌 | 없는 대상 404, 현재 자원 상태와 충돌 409, `If-Match` 등 명시한 전제 실패 412 |
| 내부/외부 장애 | 내부 예상 밖 실패 500. gateway 역할의 잘못된 upstream 응답 502·upstream timeout 504. 일시 가용성 문제 503. 단순히 모두 200 오류 문자열로 통일하지 않음 |

**판정:** 정상·빈·적용 오류와 null/누락/추가 필드 의미가 일치하고 금지 부작용·보안 경계가 정의되면 통과. `as SomeType`만으로 외부 데이터를 검증했다고 하면 수정 필요. 응답 형식만 있고 저장 상태·실패 의미가 없으면 수정 필요. 정적 문구 수정은 기존 계약 유지로 축약한다.

## D05. 인증과 자원별 권한 강제

**연결:** C17. **읽은 근거:** [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)의 least privilege, deny by default, every request, RBAC/ABAC/ReBAC, enforcement location; [Next 14 Server Actions security](https://nextjs.org/docs/14/app/building-your-application/data-fetching/server-actions-and-mutations#security). 인증은 신원 확인, 인가는 그 주체의 해당 자원·연산 허용 판정이다. Server Action도 외부 호출 가능한 연산으로 보고 서버에서 확인한다.

| 후보 | 선택 조건 |
| --- | --- |
| 역할 기반(RBAC) | 역할×연산으로 현재 규칙을 설명할 수 있고 대상 소유자에 따른 차이가 없음 |
| 역할 + 소유권/관계 확인 | 같은 역할도 자신의 데이터·담당 자원에만 권한이 있음. ID만 바꾼 접근을 구별해야 함 |
| 속성 기반(ABAC) / 관계 기반(ReBAC) | 역할만으로 설명 안 되는 주체·자원·상태·환경 또는 관계 규칙이 실제 존재함. 규칙 출처와 충돌 우선권 필요 |
| 중앙 policy 함수 / 기존 인증·권한 도구 | 전자는 단순 규칙의 일관된 서버 적용, 후자는 실제 지원 규칙·운영·호환이 확인된 경우 |

**EDGE 기본 선택:** 명세에 있는 가장 단순한 권한 모델을 서버 policy 검사로 표현한다. 역할만으로 부족하면 소유권·속성/관계를 추가한다. OWASP의 세밀한 정책 권고를 참고하되 사이트에 없는 권한 조건이나 인증 공급자를 자동 추가하지 않는다.

**입력 → 수행 → 산출물:** 역할·OP·자원·규칙 → (1) `주체 유형×연산×자원 관계/상태` 권한표 작성, (2) 명시적 허용 외 거부, (3) 신뢰된 서버 session/토큰에서 신원 획득, (4) 자원/필드 접근과 쓰기 직전에 서버 확인, (5) 조회 필터·응답 필드에도 같은 정책 적용, (6) 실패 시 노출·변경 없음 확인 → 권한표, 강제 위치·policy 경로, 허용/거부 검증 ID.

**판정:** 직접 호출·다른 자원 ID·미인증·권한 변경의 적용 시나리오에서 계약대로 허용/거부되면 통과. 버튼 숨김·클라이언트가 보낸 role·어려운 ID만 믿으면 수정 필요. 미확정 역할 규칙은 판정 불가. 공개 정적 조회는 “명세상 공개, 추가 인증 없음”으로 축약하되 비공개 필드 노출은 따로 확인한다. 로그에는 신원/결정 식별에 필요한 범위를 정하고 비밀값을 쓰지 않는다.

## D06. 영속 데이터 모델과 저장 제약

**연결:** C16·C18. **읽은 근거:** 강의 pp.321–332의 도메인·설계 구분과 p.307의 transaction-based 정보 시스템; [Microsoft normalization basics](https://learn.microsoft.com/en-us/office/troubleshoot/access/database-normalization-description); Silberschatz·Korth·Sudarshan의 [Relational Database Design 저자 강의](https://www.db-book.com/Previous-editions/db5/slide-dir/ch7.pdf) pp.8–14, 20의 원자 도메인·키·함수 종속·3NF 정의; [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html). PostgreSQL 문서는 제약의 구체 사례이며 채택 DB를 정한 것이 아니다. 실제 DB 선정 후 해당 버전의 지원·null·격리·제약 의미를 확인한다.

| 후보 | 선택 조건 |
| --- | --- |
| 개념 모델 | 업무 객체·식별·관계·수명·규칙을 합의해야 함. SQL 타입·index는 아직 제외 |
| 논리 관계형 모델 | 관계형 저장을 사용/검토함. 엔티티→테이블, 키, 참조, 다중성, 함수 종속·제약을 표현 |
| 물리 모델 | 저장 엔진·버전이 정해졌고 migration/성능·운영 설계가 필요함. 실제 타입·index·제약 지원을 연결 |
| 문서/파일/읽기 전용 외부 모델 | 현재 데이터가 해당 형식이며 요구사항을 충족함. 관계형 정규화를 억지로 적용하지 않고 의미·검증·일관성 한계를 기록 |
| 정규화 / 근거 있는 비정규화 | 업무 데이터는 중복·갱신 이상을 줄이는 정규화 우선. 확정 성능·스냅샷·이력 요구가 있는 비정규화는 원본·동기화·재생성·검증 책임 명시 |

**EDGE 기본 선택:** 영속 데이터가 바뀌면 개념과 논리 규칙을 먼저 표로 작성하고 실제 저장 기술의 제약으로 구현 가능한지 확인한다. 필요한 관계를 충분히 설명하면 별도 ERD는 선택 사항이다. 기존 CSV 읽기는 필드 의미·출처·유효성 사전으로 충분할 수 있다.

**입력 → 수행 → 산출물:** 도메인·BR·OP 사후조건 → 다음 순서로 데이터 사전·키/관계 표·저장 제약·필요한 ERD/물리 정의를 작성한다.

1. 각 값의 업무 의미·식별 안정성·유일성 범위를 정하고 자연키/대리키 후보를 비교한다. 표시 이름을 근거 없이 고유 ID로 사용하지 않는다. 슈퍼키는 행을 유일하게 식별하는 속성 집합이고 후보키는 어느 속성을 빼도 그 식별성이 사라지는 최소 슈퍼키이다.
2. 관계의 양쪽 최소/최대 다중성, 필수/null, 삭제·보존·이력 규칙을 정의한다. N:M이면 관계 자체의 속성과 연결 식별을 검토한다.
3. 관계형이면 `후보키 / X 값이 같으면 Y 값도 항상 같은가(X→Y) / 그 업무 근거`를 적어 함수 종속을 확인한다. 1NF는 반복열·반복 묶음을 분리하고 각 칸이 정의한 도메인의 단일 값인지, 2NF는 1NF 상태에서 어떤 비주요 속성도 복합 후보키의 일부에만 종속하지 않는지 검사한다. 여기서 주요 속성은 어느 후보키에라도 포함되는 속성이다. 3NF는 비자명 종속 `X→A`마다 X가 슈퍼키이거나 A가 주요 속성인지 검사한다. 키·종속을 모르면 정규화 완료로 판정하지 않는다. 현재 원본의 중복과 과거 시점 보존을 위한 복사값은 업무 의미로 구별한다.
4. `BR → 강제 위치`를 적는다. 해당되는 PK/UNIQUE/NOT NULL/FK/CHECK와 transaction/원자적 갱신으로 불변조건을 지킨다. 여러 행의 합계 규칙을 지원 안 되는 CHECK로 선언했다고 주장하지 않는다.
5. 삭제 제한/연쇄 삭제/null 대체 중 업무 수명에 맞게 선택하고, 입력 정규화(trim·대소문자 등)와 관계형 정규화를 구별한다.

**판정:** 성공·실패·삭제·중복·참조 규칙을 표현하고 저장 기술이 이를 강제/검증할 근거가 있으면 통과. 업무상 한 건이어야 하는데 두 요청이 동시에 두 건을 만들 수 있거나 참조 삭제가 이력을 잃으면 수정 필요. DB 미선정은 물리 구현을 판정 불가로 남기되 개념 분석은 진행할 수 있다. 정적 표시 수정에 데이터 재설계는 적용하지 않는다.

## D07. 동시성·원자성·멱등성

**연결:** C18. **읽은 근거:** [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [Explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), [RFC 9110 §§9.2.2, 13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html). 격리 수준과 잠금의 실제 동작은 엔진별로 다르다. HTTP 멱등은 의도한 서버 효과의 동일성이며 모든 호출의 응답 문자열 동일성을 뜻하지 않는다.

| 후보 | 선택 조건 | 남길 계약 |
| --- | --- | --- |
| 저장 제약 + 단일 조건부 갱신 | 하나의 상태/수량/유일성으로 충돌을 표현할 수 있음 | 현재 상태/버전 조건, 영향 행 수, 조건 불일치 결과 |
| 짧은 transaction | 여러 저장 변경이 함께 성공/실패해야 함 | 포함 변경, commit 시점, 실패 rollback 범위, 외부 부작용 분리 |
| 낙관적 제어 | 충돌이 드물고 사용자가 재조회/재시도를 할 수 있음 | version/ETag 등 비교, 경쟁 갱신 거부, 덮어쓰기 방지. HTTP면 `If-Match` 계약 검토 |
| 비관적 잠금 | 같은 자원의 경쟁이 크거나 읽고 결정하는 구간을 보호해야 함 | lock 대상·순서·보유 시간·timeout·deadlock 대응. 네트워크 대기 중 장기 잠금은 재검토 |
| 더 강한 격리/Serializable | 여러 행/범위의 불변조건을 낮은 격리·제약·조건부 갱신으로 보장 못 함 | 엔진 보장, 중단/충돌 시 전체 transaction 재시도 조건. 항상 성공하거나 비용이 없다고 가정하지 않음 |
| 멱등 요청 식별 | 네트워크 재전송·중복 처리로 외부 효과/생성이 반복될 수 있음 | 키의 주체·연산 범위, payload 일치, 유일 저장, 진행/완료/실패 결과, 보존 기간·재사용 규칙 |

**EDGE 기본 선택:** 쓰기가 있으면 불변조건을 먼저 정의하고 저장소가 제공하는 가장 작은 원자적 연산·제약을 선택한다. 필요한 경우 transaction·충돌 제어를 더한다. UI 버튼 비활성화와 단일 서버 프로세스의 메모리 lock은 여러 인스턴스의 저장 일관성 보장으로 사용하지 않는다.

격리 수준 후보는 실제 엔진의 보장과 함께 비교한다. `Read Uncommitted`는 확정 전 값을 읽을 수 있어 권한·업무 불변조건 판단에 사용하지 않는다. `Read Committed`는 commit된 값만 읽되 transaction 안의 반복 조회가 달라질 수 있으므로 단일 조건부 갱신·제약으로 충분한 경우 후보가 된다. `Repeatable Read`는 반복 읽기 보장이 필요한 경우 후보지만 엔진에 따라 phantom·다른 행을 각각 갱신하는 write skew 등 허용 이상 현상이 다르다. `Serializable`은 동시 실행을 순차 실행과 같은 결과로 제한해야 할 때 후보이며 충돌 중단·전체 transaction 재시도 비용을 포함한다. 엔진 기본값을 보장의 근거로 삼지 않고 `보호할 불변조건 / 허용하면 안 되는 교차 순서 / 선택 수준의 공식 보장`을 대조한다. PostgreSQL의 Read Uncommitted는 Read Committed처럼 동작하는 등 명칭만 같다고 동일 구현으로 간주하지 않는다.

**입력 → 수행 → 산출물:** 불변조건·쓰기 집합·중복 원인 → (1) 읽기/판정/쓰기 순서를 적음, (2) 두 요청의 교차 순서를 만들어 규칙 위반 가능성 확인, (3) 제어 방법 선택, (4) commit 이전/이후 응답 손실을 구별, (5) 같은 키·다른 내용/재전송/부분 진행 계약 확인 → 동시성·멱등성 계약과 병렬/실패 검증 시나리오.

**판정:** 중복·경쟁·중간 실패에서도 최소 보장과 최종 불변조건이 지켜지고 충돌 결과가 명세와 같으면 통과. `읽어 확인 → 무조건 쓰기`만으로 경쟁을 막았다고 하면 수정 필요. 전체 요청 성공을 주장할 필요는 없으며 계약된 거부/충돌은 올바른 결과일 수 있다. 외부 효과까지 한 DB transaction으로 rollback할 수 없다면 별도 결과 확인·보상/재처리 책임을 정의한다. 읽기만 있고 공유 상태를 바꾸지 않으면 해당 없음이다.

## D08. 외부 호출의 시간 제한·재시도·격리

**연결:** C18. **읽은 근거:** [AWS bounded retry guidance](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html); [Microsoft Retry](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry), [Circuit Breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker); [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html)의 429·Retry-After. AWS Builders’ Library 웹 본문은 리다이렉트로 정상 열람되지 않아 그 페이지를 읽은 근거로 삼지 않고 위 공식 지침을 사용했다.

| 후보 | 선택 조건 |
| --- | --- |
| 시간 제한 + 오류 반환 | 재시도 이익이 없거나 결과가 불명인 비멱등 쓰기·필수 권한/입력 오류 |
| 한 계층의 제한 재시도 | 공식 연동 계약상 일시 장애이고 재수행 효과가 안전하며 전체 응답 예산 안에서 유용함 |
| exponential backoff + jitter | 여러 호출자가 동시에 재시도해 복구 서비스에 부하를 집중시킬 수 있음 |
| 결과 조회/재조정 | 쓰기가 완료됐는지 응답 손실로 불명. 조회 식별자·멱등 계약이 확보된 경우 |
| Circuit Breaker | 지속 장애·반복 timeout이 다른 요청 자원을 고갈시키며 상태·관측·복구를 운영할 근거가 있음 |

**EDGE 기본 선택:** 외부 호출의 전체 시간 한계와 실패 의미를 먼저 정하고 재시도는 실제 서비스의 안전성·오류 분류로 제한한다. 이미 SDK가 재시도하면 설정을 확인한다. 기본적으로 circuit breaker·큐·대체 공급자를 새로 추가하지 않고 위 선택 조건이 성립할 때 검토한다.

**입력 → 수행 → 산출물:** OP·외부 계약·QR 시간 경계·SDK 설정 → (1) 연결/요청/본문 수신 중 제한 대상 확인, (2) 전체 deadline·attempt당 timeout·최대 attempts를 정의, (3) 오류별 재시도/거부/결과 확인 표 작성, (4) 한 계층에서만 재시도, (5) `대기 = min(상한, 기본간격×2^시도번호)` 안의 무작위 지연 등 선택한 jitter와 종료 조건 기록, (6) UI 결과·보존 상태·진단 로그 연결 → 호출 정책과 시간 초과·재시도 한계·중복 효과 검증 항목.

시간·횟수·간격 숫자는 사용자 기대, 서비스 제한·관측 지연, 배포 실행 한계에서 정한다. 근거가 없으면 미정이다. 429/일시 5xx도 서비스 계약과 전체 시간 예산을 확인하며 모두 자동 재시도하지 않는다. `Retry-After`가 있으면 정책·전체 한계 안에서 존중한다. 취소 신호가 클라이언트 대기를 끝내도 원격 쓰기의 rollback을 보장하지 않는다.

**판정:** 정상·지연·일시/영구 실패·attempt 한계·결과 불명 상태를 구별하고 중복 효과와 자원 대기가 제한되면 통과. 모든 오류를 반복하거나 다층 재시도로 횟수가 증폭되면 수정 필요. circuit breaker를 쓰면 Closed/Open/Half-Open·판별 window·제한 probe·상태 저장 범위·복구 관측을 정해야 한다. 작은 읽기 연동은 시간 제한·오류 처리·재시도 제외 이유만으로 충분할 수 있다.

## D09. 캐시·신선도·무효화

**연결:** C18. **읽은 근거:** [Microsoft Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside); [Next.js 14 Caching](https://nextjs.org/docs/14/app/building-your-application/caching)의 Data Cache·time/on-demand revalidation·Router Cache; [Next 14 Server Actions revalidating data](https://nextjs.org/docs/14/app/building-your-application/data-fetching/server-actions-and-mutations#revalidating-data). 다음 표는 일반 후보와 Next 14 적용을 구별한다.

| 후보 | 선택 조건 | 실패·일관성 확인 |
| --- | --- | --- |
| no-store/매번 원본 확인 | 권한·사용자별 데이터·즉시 상태 확인 등 stale 허용이 어렵거나 비용 이익 없음 | 원본 부하·지연·오류. 캐시 배제가 저장 동시성을 해결하지는 않음 |
| TTL + Cache-Aside | 반복 읽기 비용이 있고 제한된 신선도 지연을 허용함 | key·TTL·갱신 책임, 외부 변경·캐시 miss·동시 refill. 강한 일관성을 보장한다고 하지 않음 |
| validator 기반 확인 | 원본이 ETag/수정 시점 등 변경 확인 계약을 지원함 | 지원 근거·조건부 요청 의미·원본 오류 시 처리. 지원하지 않는 validator를 상상하지 않음 |
| 쓰기 후 invalidation | 앱이 원본 쓰기와 영향받는 캐시를 알고 있음 | commit 성공 뒤 무효화, 관련 목록/상세 범위, 실패 감지·재확인 |
| write-through | 성공 후 즉시 읽기의 신선도가 필요하고 원본/캐시 갱신 정책을 운영할 수 있음 | 이중 갱신·실패·동시 refill. 두 저장 작업이 자동으로 원자적이라고 가정하지 않음 |
| stale 제공·백그라운드 갱신 | 공개 읽기 등 명시적 지연 허용이 있고 이전 값 사용이 사용자/업무 보장을 깨지 않음 | 허용 나이·표시·원본 장애·민감도. 권한 결정과 쓰기 유효성에 stale을 사용하지 않음 |

**EDGE 기본 선택:** 현재 캐시를 우선 활용하되 기능별로 `어떤 값 / 누구에게 / 어느 정도 오래 / 무엇이 갱신시키는가`를 계약으로 정한다. 브라우저 표시용 이전 값이 서버 쓰기 판정의 권위 있는 상태를 대신하지 않는다.

**Next 14 적용 기준:** 서버 Data Cache와 요청 중 memoization, 생성된 route 결과, 브라우저 Router Cache를 구별한다. 해당 서버 fetch의 `next.revalidate`는 시간 기반 재검증이며 0/no-store로 캐시를 배제할 수 있다. Next 14의 시간 기반 재검증은 만료 뒤 요청에 이전 값이 먼저 제공되고 백그라운드 갱신이 실패하면 이전 값이 유지될 수 있으므로 `revalidate: N`을 무조건 “N초보다 오래된 값은 절대 안 보임”으로 해석하지 않는다. 쓰기 후 갱신은 실제 읽기 범위에 맞게 `revalidateTag`/`revalidatePath`를 검토한다. `router.refresh()`만으로 서버 데이터 캐시가 갱신된다고 판정하지 않는다. 이 내용은 v14에 맞춘 것으로 다른 major 버전의 기본 정책을 혼용하지 않는다.

**입력 → 수행 → 산출물:** 데이터 사전·QR 신선도·읽기/쓰기 경로 → (1) 캐시 계층/키/사용자 범위 식별, (2) stale 허용·금지와 원본 확정, (3) 후보 선택·기간 근거, (4) commit→invalidation→다음 읽기 흐름 작성, (5) 외부 변경·갱신 실패·로그아웃·병렬 refill 검토 → 캐시 계약, 영향 캐시 목록, 관련 검증 ID.

**판정:** 다른 사용자 데이터 혼입이 없고 허용 신선도·쓰기 후 결과가 계약대로 유지되면 통과. TTL만 있고 갱신 실패·외부 변경 시 허용 나이가 없거나 쓰기 판정을 오래된 목록에 의존하면 수정 필요. 현재 아카이브의 3600초를 새 기능 기준으로 복사하면 근거 부족이다. 성능/신선도 필요가 없는 작은 변경은 기존 정책 유지 이유만 남긴다.

## D10. 응집도·결합도·SOLID·Clean Code·패턴 리뷰

**연결:** C19·C20. **읽은 근거:** 강의 pp.248, 337–339, 352, 462; Robert C. Martin의 [SRP](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html), [OCP](https://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html), [DIP·ISP 설명](https://blog.cleancoder.com/uncle-bob/2016/01/04/ALittleArchitecture.html); Liskov·Wing의 [behavioral subtyping 저자 초록](https://www.cs.cmu.edu/Groups/venari/subtype-toplas.html). 강의의 Clean Code 과제는 원칙 조사와 실제 개선 근거를 요구한다. 아래 코드 리뷰 항목·축약 규칙은 EDGE에서 정한 실행 방식이다.

| 원칙·후보 | 실제 검사와 반례 | 필요한 범위의 개선 옵션·통과 기준 |
| --- | --- | --- |
| 응집도·SRP | 목적·정책 출처·변경 이유를 적음. CSV 공급자 형식 변경 때문에 화면 정렬 정책을 함께 바꾸는가? | 현재 함수 유지 / 순수 규칙 추출 / 연동 변환 분리. 같은 이유로 변하는 책임은 함께 둘 수 있고 무관한 변경 이유는 경계로 제한 |
| 결합도·정보 은닉 | 호출자가 내부 열 이름·저장 구조·가변 상태를 직접 아는지 소비자 목록 대조 | 필요한 값/계약 반환, 구현 세부 숨김. 외부 형식 변경이 무관한 소비자까지 강요하지 않으면 통과 |
| OCP | 확정된 알고리즘/제공자 변형을 추가할 때 안정 정책을 반복 수정하는가? | 단순 조건 유지 / 함수 전달 / Strategy·다형 대체. 변형이 실제 있고 비용이 줄 때 확장점 선택. 변경 0회라는 기계적 목표는 아님 |
| DIP | 업무 규칙이 구체 SDK·HTTP·저장 형식을 직접 import해야 하는가? 대체/격리가 실제 필요한가? | 인수로 함수·필요 계약 전달 / adapter. 소규모 단일 구현에 DI framework를 강제하지 않음 |
| LSP | 대체 구현이 기존 유효 입력을 거부하거나 보장한 출력·불변조건·오류 의미를 깨는가? | 계약 맞춤 / 같은 인터페이스로 묶지 않기 / 구성으로 변경. 타입 컴파일만 통과해도 동작 계약은 별도 대조 |
| ISP | 읽기 소비자가 불필요한 쓰기·관리 연산을 구현/의존해야 하는가? | 필요한 연산만 타입/함수로 전달 / 소비자별 계약 분리. 미래 소비자를 예상해 미리 잘게 나누지는 않음 |
| Clean Code 실행 리뷰 | 함수 이름·본문·단위 일치, 숨은 부작용, 오류 삼킴, 비밀 로그, 같은 규칙 중복, 깊은 분기로 빠진 결과 확인 | 명세를 깨뜨리는 실제 문제를 최소 수정. 이름/줄 수/취향만으로 무관한 파일 재정리하지 않음. 필요한 주석은 “왜/제약”을 설명 |

패턴 후보는 문제가 있을 때만 적용한다. `직접 함수/기존 구조`가 비교 기준이다. **Adapter**는 실제 외부 계약 차이를 내부 계약으로 바꿀 때, **Strategy/함수 주입**은 실제 규칙 변형이 있을 때, **Factory/생성 함수**는 복잡한 생성·초기 불변조건이 있을 때, **Observer/기존 이벤트 처리**는 여러 실제 소비자에게 상태 변경을 전달할 때, **데이터 접근 모듈**은 여러 호출자가 저장 세부를 중복 알아야 할 때 검토한다. 단순 구현보다 늘어나는 계층·상태·테스트·실패 지점과 줄어드는 변경 비용을 함께 적는다. Serverless의 프로세스 singleton을 전역 일관성 보장으로 선택하지 않는다.

**EDGE 기본 선택:** 변경 경계의 실제 반례를 확인하고 가장 작은 개선을 선택한다. SOLID를 TypeScript 함수·모듈 계약에도 적용할 수 있으나 모든 원칙을 위한 클래스·interface를 추가하지 않는다. 원칙·패턴 준수 자체를 새 제품 요구사항으로 만들지 않는다.

**입력 → 수행 → 산출물:** 변경 함수·호출자·책임·OP 계약 → (1) 한 문장 목적과 정책 출처, (2) 실제 의존·부작용 확인, (3) 해당 원칙 반례 만들기, (4) 유지/작은 추출/패턴 안 비교, (5) 선택 후 계약·검증 연결 대조 → `원칙 / 위치 / 확인 사실·반례 / 결과 / 수정 또는 유지 이유 / 관련 검증` 기록.

**판정:** 필요한 계약·불변조건을 보존하면서 확인한 무관 결합·누락 결과를 해결하면 통과. 패턴 이름만 있고 해결할 문제가 없거나 보장 사항을 깨면 수정 필요. 상속·대체 구현이 없으면 LSP 검토는 해당 없음, 실제 변형이 없으면 OCP 확장점은 보류 가능하다. 줄 수·복잡도 수치는 문제 후보를 찾는 자료이며 단독 실패 기준으로 사용하지 않는다.

## D11. 기존 구현·라이브러리·서비스 재사용 선택

**연결:** C21. **읽은 근거:** 강의 pp.15–16, 283, 342–344의 재사용 수준과 조사·적응·통합 비용; [npm package.json](https://docs.npmjs.com/cli/v10/configuring-npm/package-json/)의 engines·dependencies·peerDependencies·license·scripts, [npm package-lock.json](https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json/)의 설치 트리 기록. “검증된”은 인기도가 아니라 해당 요구사항·환경에서 확인한 지원·계약 근거를 뜻한다.

| 후보 | 선택 조건 |
| --- | --- |
| 기존 모듈 그대로 재사용 | 계약·권한·부작용·환경이 이번 요구와 같음 |
| 기존 모듈 최소 수정/얇은 wrapper | 작은 계약 차이가 있고 기존 소비자 회귀를 통제할 수 있음 |
| 작은 직접 구현 | 범위가 작고 규칙이 분명하며 의존성의 적응/운영 비용이 더 큼 |
| 라이브러리/공식 SDK | 복잡한 공통 문제의 지원·호환이 확인되고 유지·번들·라이선스 비용이 수용 가능 |
| 외부 서비스·기성 시스템 | 기능을 직접 운영할 비용보다 이점이 있으며 접근·데이터·가격·제한·종료/전환 조건이 실제 확보됨 |

**EDGE 기본 선택:** 기존 코드와 설치된 도구부터 확인한다. 기능 지원을 가정하지 않고 실제 사용하는 API·버전·Node/브라우저/서버 환경을 대조한다. 기능 지침을 작성하는 현재 작업에서 새 DB·인증·SDK를 선정하거나 설치하지 않는다.

**입력 → 수행 → 산출물:** FR·QR·환경·기존 의존성 → (1) 기존 지원 위치 검색, (2) 위 후보 중 실제 가능한 것 식별, (3) 필수 지원·runtime/peer 호환·권한·데이터 취급으로 기각, (4) 조사/적응/통합/유지/전환 비용·bundle/운영 영향 비교, (5) 공식 문서·기존 검사·제한된 확인으로 근거 보강 → 선택/기각 기록과 버전·영향 파일·관련 검증.

지원 판단 최소 자료는 `사용할 기능·버전 / 공식 지원 근거 / 현재 runtime·peer 조건 / 유지·보안 문제 확인 시점 / 라이선스·데이터·권한 / 기존 결과 또는 필요한 확인 / 알려진 한계`이다. lockfile이 있으면 의존성 변경의 실제 트리를 함께 검토한다. 잠금만으로 호환·보안을 증명하지 않는다. 비밀값은 근거 자료에 기록하지 않는다.

**판정:** 필수 기능·환경·운영 제약 지원 근거와 비용·영향이 있으면 통과. “많이 쓴다/최신이다”만 있으면 수정 필요. 중요한 지원·접근이 미확인이면 판정 불가. 작은 함수 재사용은 원본 경로·계약 일치·확인 결과로 축약한다.

## D12. 변경 영향 분석과 최소 패치

**연결:** C22. **읽은 근거:** 강의 pp.248, 342–343, 465의 정보 은닉·형상·유지보수 연결; [공통 지침의 진단 우선·변경 범위](../../AGENTS.md). 아래 의존 대조·패치 분할은 EDGE 운영 절차이다. 제공 진단과 코드가 충돌하지 않으면 동일 원인 분석을 다시 시작하지 않는다.

| 후보 | 선택 조건 |
| --- | --- |
| 위치 지정 최소 확인 | 제공 진단이 위치·원인을 특정하고 수정 적용이 가능함 |
| 호출/참조 검색 | 함수·타입·컴포넌트 계약이 바뀌어 소비자 영향이 있음 |
| 데이터·상태·캐시 흐름 추적 | 공유 값·저장·권한·갱신 결과가 바뀜 |
| 설정·환경·의존성 대조 | build/runtime·env 이름·package·배포 조건이 바뀜 |
| 목적별 패치 분할 | 독립적으로 검토·되돌릴 수 있는 목적이 여러 개임. 같은 계약 수정의 필수 호출부는 하나의 일관된 묶음 |

**EDGE 기본 선택:** 진단/요청의 변경 지점에서 시작해 직접 소비자·공유 데이터·설정 영향으로 필요한 범위만 넓힌다. 전 저장소 재분석·포맷팅·이름 변경·파일 재배치를 자동 추가하지 않는다.

**입력 → 수행 → 산출물:** 사용자 요청·제공 진단·현재 branch/diff·관련 명세 → 다음 순서로 실제 파일을 수정한다.

1. 현재 작업 위치·브랜치·기존 사용자 변경을 확인하고 보존한다. 지정 위치·원인·기대 동작·수정 가능성을 최소 대조한다.
2. 변경 심볼의 import/export·호출·type·UI 소비자를 `rg` 등으로 검색한다. 변경 값의 생성/저장/읽기/캐시/권한 경로를 함께 확인한다.
3. `변경 요소 / 소비자·공유 상태 / 바뀌는 계약 / 영향 근거 / 수정 필요/검증만/영향 없음 / 관련 TC`를 기록한다. 영향 없음은 이유가 있어야 한다.
4. 계약을 보존하는 작은 수정 또는 필요한 생산자·호출부 동시 변경을 선택한다. 진단과 명백한 충돌이 있으면 충돌한 부분만 확인하고 기록한다.
5. 각 diff hunk를 FR·결함·필수 계약 변경에 연결한다. 연결되지 않는 정리·스타일 변경은 제거한다. 필요한 명세·테스트/검증 계획도 같은 결정으로 갱신한다.
6. 적용되는 검증을 수행하고 실패·미실행·환경 제약을 남긴다. 새 실패나 변경이 없다면 이유 없이 동일 검사를 반복하지 않는다.

**판정:** 요청/진단의 기대 동작을 해결하고 필수 호출부·데이터·설정 영향이 다뤄지며 사용자 변경과 관련 계약을 보존하면 통과. 대상 함수만 수정해 소비자의 타입·오류·cache 계약을 깨거나 전체 재작성으로 범위를 넓히면 수정 필요. 작은 문구 수정은 실제 소비 화면만 확인할 수 있다. 검색으로 빠진 동적 호출·외부 소비자를 증명할 수 없으면 해당 한계를 명시하고 필요한 확인을 연결한다.

이 절의 완료는 패치와 검증 근거의 준비이다. 커밋·푸시·배포·외부 데이터 변경 권한을 추가하지 않는다.
