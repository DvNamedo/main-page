# 테스트·정적 분석·QA 방법 선택과 실행

이 문서는 [전체 지침 감사](../GUIDELINE_AUDIT.md)의 C23–C29, C38과 C34의 품질 보증 부분을 구체화한다. 제공 PDF의 **방법**을 채택하고, 웹 환경에서 필요한 방법을 공식 자료로 보완했다. 과제의 테스트 20개·보고서 분량·C 도구 지정은 적용하지 않는다. 아래 절차·기본값·축약 기준은 EDGE의 운영 규칙이며 원문 표준 전체를 구현하거나 인증받았다는 뜻이 아니다.

검증 계획과 실행을 구별한다. 설계·가이드만 요청된 작업은 계획까지 작성한다. 구현 작업에서도 사용자의 테스트 금지·검증 범위 지시를 우선하고 미실행 범위를 기록한다. 이 문서 작성으로 테스트 러너를 설치하거나 실제 사이트의 품질 수치·지원 브라우저·저장소를 확정하지 않는다.

**상태·판정은 별도 필드로 구분한다.** TC 실행 상태는 `미실행/실행/차단`이다. 미실행은 아직 수행하지 않음, 실행은 수행 결과가 있음, 차단은 환경·권한·필수 데이터 때문에 실행/완료하지 못함이다. 실행 판정은 `통과/실패/판정 불가`이며 실제 관찰과 예상값을 비교한 경우에만 통과/실패를 기록한다. 미실행·차단이면 그 이유와 판정 불가를 남긴다. 리뷰 결과는 `통과/수정 필요/판정 불가/해당 없음`이다. 수정 필요는 확인한 모순·누락·오류, 판정 불가는 자료·기준 부족을 뜻한다. TC의 차단이 관련 완료 기준을 판정 불가로 만드는 근거일 수 있지만 둘을 같은 필드에 섞지 않는다. 해당 없음은 대상이 범위에 없다는 근거일 때만 사용한다.

## T01. 검증 수준과 자동화 방식 선택

**연결·근거:** C23. PDF pp.397–409, 414–418, 428은 단위·통합·시스템 테스트, 자동화, UC 기반 시스템 케이스, 목적에 맞는 도구 선정을 다룬다. [Next.js 14 Testing](https://nextjs.org/docs/14/app/building-your-application/testing)의 테스트 종류와 async Server Component 안내를 확인했다.

| 후보 | 선택 조건 | 이 방법만으로 판정할 수 없는 것 |
| --- | --- | --- |
| 단위 | 순수 계산·필터·정렬·검증·업무 규칙을 독립 입력/출력으로 확인 | 실제 HTTP·저장소·권한 경계·최종 화면 |
| 컴포넌트 | 클라이언트 컴포넌트의 표시·입력·사용자 이벤트 | 브라우저 실제 배치, 서버 컴포넌트와 배포 환경의 통합 |
| 통합·계약 | 서버 연산↔어댑터, 직렬화, 저장소 제약, 권한 적용 위치를 확인 | 요청한 사용자의 전체 목표 달성 |
| 시스템·E2E | UC 기본/예외 흐름, 서버 렌더링·라우팅·브라우저 연결 확인 | 모든 입력 조합·내부 분기를 전부 검사했다는 증명 |
| 수동 시나리오 | 문구·시각 배치, 사람의 이해, 일회성 확인, 자동화 환경이 없는 경우 | 재현 단계·실제 관찰을 기록하지 않은 추측 |
| 자동화 | 반복할 규칙·회귀 경로, 정확한 예상값, 비용이 큰 반복 작업 | 도구가 확인하지 않는 실제 사용성·접근성 전체 |

**EDGE 기본:** 새 동작은 규칙을 가장 작은 실행 가능한 수준에서 검사하고, 실제로 변경하는 경계를 통합 검증하며, 목표 달성은 UC 대표 흐름으로 확인한다. 자동/수동은 수준과 별개로 선택한다. async Server Component 전체를 지원되지 않는 단위 환경에 억지로 맞추지 않고, 규칙의 독립 테스트와 페이지 E2E를 조합한다. 이미 있는 검증을 재사용해 같은 사실의 중복을 줄인다.

**입력→절차→산출물:** FR·BR·QR·UC·변경 경계 → 각 인수 기준의 관찰 지점 표시 → 위 표에서 이를 관찰할 수준 선택 → 자동/수동 비용·재현성 확인 → [기능 명세](../templates/FEATURE_SPEC.md)에 `TC ID / 대상 ID / 수준 / 관찰할 사실 / 대역·실환경 / 방식 / 선택 이유` 기록. 한 TC가 여러 요구사항을 검증해도 각각의 예상 결과는 구분한다.

**판정:** 선택한 수준에서 예상 출력·사후 상태·금지 부작용을 직접 관찰하면 방법 선택이 통과한다. 모킹된 저장소만 보고 트랜잭션 검증 완료, API만 보고 화면 흐름 완료, 빌드만 보고 사용자 목표 완료로 판정하면 수정 필요이다. 실행 환경이 없으면 계획은 남기고 실행 상태는 미실행/차단으로 둔다.

**축약:** 정적 문구·스타일은 관련 화면의 수동 TC 한 기록으로 가능하다. 상태·권한·쓰기·공유 계약이 바뀌면 해당 경계의 성공·거부·실패 검증을 생략하지 않는다. 자동화 도입 자체가 작은 수정의 필수 산출물은 아니다.

## T02. 동등 분할과 경계값 도출

**연결·근거:** C23. PDF pp.409–413의 정상/비정상 입력, partition testing, 경계 그림을 읽었다. [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) §4.2.1–4.2.2는 동등 분할과 2값/3값 BVA를 구별한다. 아래 분할 표와 자료형 규칙은 EDGE에서 이를 실행하기 위한 채택 기준이다.

| 후보 | 선택 조건 | 제외·추가 조건 |
| --- | --- | --- |
| 동등 분할(EP) | 명세상 처리 방식이 같은 입력군을 나눌 수 있음 | 같은 출력처럼 보여도 권한·부작용·정규화가 다르면 별도 군 |
| 2값 BVA | 순서가 있는 분할 경계의 포함/제외를 확인 | 경계와 인접 분할의 최근접 값 선택. 내부 값도 별도 EP 대표로 확인 |
| 3값 BVA | 비교 연산·범위 제한 변경, 중요 쓰기 규칙, 경계 자체만 허용되는 오류 가능 | 각 경계와 양쪽 최근접 값. 서로 겹치는 값은 한 번 실행해도 연결은 모두 보존 |
| 명시 사례 | 범주·열거·문자열·복합 데이터처럼 순서 경계가 없음 | 숫자 BVA를 억지로 적용하지 않고 값 종류·길이·형식·존재 여부로 분할 |

**EDGE 기본:** 적용되는 각 EP를 대표값으로 검사한다. 순서 범위가 바뀌면 2값 BVA를 기본으로 하고, 비교 로직·핵심 업무 제한에는 3값을 선택한다. 선택 이유를 적는다. 정수 허용 범위 `[L,U]`의 설명 예시는 2값 `L-1,L,U,U+1`, 3값은 추가로 `L+1,U-1`이다. 이는 사이트의 실제 제한값을 정한 것이 아니다. 범위 길이가 짧으면 중복을 제거한다.

**입력→절차→산출물:** 입력 타입·정규화·명세의 허용값 → 정상/빈 값/누락/형식 오류/범위 밖/없는 대상 등의 적용군 도출 → 각 군의 의미와 대표값 기록 → 경계의 포함 여부·자료형 최근접 값 결정 → 입력 하나를 바꾸며 다른 조건은 정상으로 유지 → TC 연결. 산출물은 `입력/규칙 ID / 분할 / 허용·거부 의미 / 대표값 / 경계·이웃 / 예상 결과 / TC` 표이다.

**판정:** 각 적용 분할과 선택한 BVA의 모든 항목에 TC가 있고 결과가 명세와 일치해야 통과한다. `null`, 필드 누락, `""`, 공백 문자열을 명세 없이 같은 군으로 합치거나, 형식 오류 여러 개를 한 입력에 겹쳐 어떤 검증이 실패했는지 숨기면 수정 필요이다. 실수의 최근접 값·시간 최소 단위·문자 길이 측정 기준이 미정이면 판정 불가이며 임의의 epsilon을 정하지 않는다.

**축약:** 범위가 없는 표시 변경에는 BVA가 해당 없음이다. 여러 필드의 동등한 분할은 매개변수화된 TC로 축약하되 필드별 사례를 확인할 수 있어야 한다. 입력 상호작용은 T03·T04로 별도 확인한다.

## T03. 결정표와 상태 전이의 검증 단위

**연결·근거:** C23, C38. PDF pp.407, 413, 415, 417–418은 상태·모델·인터페이스·UC에서 테스트를 도출한다. [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) §4.2.3–4.2.4에서 결정표의 실행 가능한 규칙 열과 상태/전이 커버리지 차이를 확인했다. 기존 지침의 “서로 다른 결과를 발생시키는 조합”은 결정표의 충분한 기준이 아니므로 아래 규칙으로 대체한다.

| 후보 | 선택 조건 | 충분하지 않은 대체 |
| --- | --- | --- |
| 전체 결정표 | 여러 조건의 조합이 허용/거부·오류·부작용을 결정하고 조합 수가 관리 가능 | 성공/실패 출력 한 번씩만 검사 |
| 근거 있는 축약 결정표 | 특정 조건이 결과·부작용·관련 규칙에 영향을 주지 않는다는 명세 근거가 있음 | 출력 문자열이 같다는 이유만으로 합치기 |
| 상태 전이표 | 같은 이벤트가 현재 상태·Guard에 따라 달라짐 | 모든 상태에 한 번 도달했으므로 모든 전이도 통과했다고 주장 |
| 전이 연속쌍·이벤트 순서 | 직전 이력·취소/재시도·재진입·동일 이벤트 반복이 위험을 만듦 | 단일 전이만 검사해 순서 의존 결함이 없다고 주장 |

**EDGE 기본:** 조건 규칙은 **실행 가능한 각 규칙 열**, 업무 상태는 **변경 범위의 각 정의된 전이와 적용되는 금지 이벤트**를 필수 검사 단위로 삼는다. 같은 출력인 두 규칙도 조건의 독립 오류를 노출할 수 있으므로 각각 검사한다. 축약을 선택하면 원래 열→축약 열 연결과 무관 조건의 이유를 남긴다. 역할별 쓰기 거부·데이터 보장처럼 영향이 큰 조건은 최종 메시지가 같아도 축약하지 않는 것을 기본으로 한다.

**입력→절차→산출물(결정표):** BR·권한표·실패 계약 → 조건 행과 결과/부작용 행 작성 → 조건의 가능한 조합을 규칙 열로 전개 → 불가능 열은 불가능한 이유·관련 BR로 제외 → 충돌·결과 미정 열 해결 → 각 가능한 열에 실제 입력·TC 연결 → 선택한 축약 전후 분모·결과 기록. Boolean 조건 n개일 때 `2^n`은 최초 조합 상한이며 실제로 불가능한 조합은 따로 표시한다.

**입력→절차→산출물(상태):** 초기 상태·이벤트·Guard·전후 조건 → 상태×이벤트 표 작성 → 초기 상태에서 목표 상태를 만드는 준비 경로 기록 → 각 적용 전이를 실행하고 목표 상태·불변조건 확인 → 금지 이벤트는 사례를 분리해 다른 오류에 가려지지 않게 검사 → 이력 위험이 있으면 전이쌍/반복 사례 추가. 산출물은 규칙표/전이표와 TC 연결이다.

**판정:** 규칙 커버리지는 `검사한 가능한 규칙 열 / 선택한 표의 가능한 규칙 열`, 전이 커버리지는 명시한 정의 전이·금지 이벤트 집합 각각으로 계산한다. 실행 누락·실패를 포함하면 검증 완료가 아니다. 불가능 열의 근거 없음, 빈 상태표 칸의 의미 미정, 만들 수 없는 상태의 준비 경로 없음은 수정 필요/판정 불가이다. 축약표의 100%를 전체 원래 조합 100%라고 쓰지 않는다.

**축약:** 조건 하나는 참/거짓 TC 목록으로 결정표를 대신할 수 있다. 상태 하나뿐인 정적 표시는 상태 모델이 해당 없음이다. 조합이 크면 T04 또는 위험 우선 실행을 선택하되 생략 열과 잔여 위험을 명시하고 전체 규칙 검증 완료로 보고하지 않는다.

## T04. 입력 조합·속성 기반·퍼징 선택

**연결·근거:** C23, C25. PDF pp.410, 413, 418은 대표값·조합·전수·무작위 선택과 필요한 테스트 범위를 다룬다. [NIST ACTS testing guidance](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/software-testing-methodology/dos-and-don-ts-of-testing)는 pairwise의 한계를 설명한다. [fast-check의 속성 기반 설명](https://fast-check.dev/docs/introduction/what-is-property-based-testing/)은 입력 생성과 반복 가능한 seed를, [LLVM libFuzzer](https://llvm.org/docs/LibFuzzer.html)는 퍼징 개념을 확인하는 근거로 읽었다. LLVM 도구를 TypeScript 사이트에 설치하라는 선택은 아니다.

| 후보 | 선택 조건 | 제외·제한 |
| --- | --- | --- |
| 유한 전수 | 역할×연산, 작은 열거·상태·결정표 등 전체 경우를 싸게 실행할 수 있음 | 무한 문자열·전체 사이트 경로는 전수라고 부를 수 없음 |
| pairwise(2-way), t-way | 여러 비교적 독립인 설정·환경·입력 차원의 조합이 많음 | 권한·쓰기 핵심 결정표, 이미 알려진 3개 이상 조건 의존 규칙을 2-way로 대체하지 않음 |
| 속성 기반 | 명세의 일반 불변조건·관계가 있음. 예: 정렬 결과의 순서 보장, 변환의 명시된 왕복 조건 | 구현 결과를 oracle로 사용하는 순환 검증, 모든 입력에서 참인지 확인하지 않은 속성 |
| 퍼징 | 파서·외부 CSV/JSON·문자 처리처럼 비정상 입력에서 예외·중단·과도한 자원 사용 위험이 있음 | 단순 색 변경에는 불필요. 무작위 실행만으로 정답·보안 전체를 증명하지 않음 |

**EDGE 기본:** T02·T03의 명세 기반 사례를 먼저 선정한다. 핵심 규칙은 유한 전수/규칙 표를 우선하고, 표시 조건·환경 조합이 커질 때 pairwise를 보충한다. 속성·퍼징은 실제 파싱/변환/규칙의 비용 대비 발견 이익이 있을 때 추가한다. “pairwise면 충분”을 기본 전제로 삼지 않는다.

**입력→절차→산출물:** 차원·값·제약·위험 → 총 가능한 조합 수와 필수 고위험 조합 목록 계산 → 전수 가능성 판단 → 조합 기법을 선택하면 상호작용 강도 t와 불가능 조합 근거 기록 → 속성 검증은 입력 생성 범위·불변조건 oracle·seed·실행 수/시간을 정함 → 퍼징은 입력 corpus·실패 정의·자원/시간 한도 설정 → 실패 입력 최소화·고정 회귀 사례로 보존. 기록은 `선택 기법 / 분모·생성 범위 / 제약 / 필수 사례 / seed·한도 / 발견 결과·미검증 범위`이다.

**판정:** 선택한 조합 강도의 적용 가능한 조합을 검사했으며 필수 고위험 사례도 통과해야 그 범위가 통과한다. 속성 실패는 재현 가능한 최소 입력과 명세 대조로 판정한다. 생성 입력이 유효 범위만 포함한 경우 비정상 입력도 검증했다고 쓰지 않는다. 퍼징에서 오류를 못 찾았다는 사실은 해당 한도 내 관찰 결과이다.

**축약:** 두 조건으로 표현되는 작은 규칙에는 별도 pairwise 도구가 필요 없다. 생성 테스트 도구가 없으면 명세 기반 수동/매개변수 사례로 먼저 검사하고 자동 생성은 미도입으로 적는다. 테스트 개수·seed·시간을 모든 기능에 같은 숫자로 고정하지 않는다.

## T05. 테스트 대역·실제 경계·실패·동시성 재현

**연결·근거:** C23, C25. PDF pp.408, 414–416의 준비/호출/assertion과 인터페이스 실패·순서 검증을 바탕으로 한다. [Martin Fowler의 Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)의 대역 종류·상태 검증/호출 검증 구별, [Playwright Mock APIs](https://playwright.dev/docs/mock)의 응답 대체, [Playwright Best Practices](https://playwright.dev/docs/best-practices)의 격리와 외부 응답 통제를 읽었다.

| 후보 | 선택 조건 | 검증 한계 |
| --- | --- | --- |
| 실제 협력 객체 | 싸고 결정적인 순수 함수·모듈, 부작용 없는 협력 | 실행 비용·외부 상태 의존이 크면 격리 필요 |
| stub | 정상·빈 응답·오류·timeout 값을 통제해 소비자 반응 검사 | 실제 제공자의 계약·가용성은 미검증 |
| fake | 작은 메모리 저장소 등 동작하는 간소 구현으로 상태 검사 | 실제 DB 제약·격리 수준·동시성 보장은 미검증 |
| spy/mock | 호출 횟수·매개변수·순서 자체가 명세의 중요한 부작용인 경우 | 내부 구현 호출을 과하게 고정하면 무관한 변경에도 깨짐 |
| 격리된 실제 저장소/제공자 | 직렬화·제약·트랜잭션·HTTP 계약·실제 연동이 검증 대상 | 승인된 접근·테스트 데이터·복구 가능 범위 필요. 로컬 대역 결과와 별도 표시 |

**EDGE 기본:** 독립 규칙에는 실제 순수 모듈, 외부 실패/비용 통제에는 stub/fake, 저장·동시성 보장에는 격리된 실제 경계를 사용한다. 대역의 계약을 실제 어댑터와 같은 인터페이스로 유지하고 결과·상태를 우선 확인한다. 실제 외부 응답 확인을 따로 하지 않았다면 그 연결은 미검증이라고 적는다.

**입력→절차→산출물:** OP 계약·쓰기/읽기·위험 → 검증할 경계를 표시 → 대역/실제 선택 → TC마다 독립 fixture(최소 데이터·역할·초기 상태) 준비 → 정상/실패를 경계에서 주입 → 응답·사용자 표시·저장 전후 상태·호출 부작용 확인 → 실패해도 teardown/finally로 테스트 소유 데이터·가짜 시간·대역·세션 복원. 산출물에 대역 위치, 주입한 사건, 실제로 검사하지 않은 경계를 적는다.

**장애와 경합의 실제 절차:** 외부 오류는 응답 코드·빈 body·잘못된 형식·지연/중단 중 계약에 적용되는 사건을 재현한다. 이미 저장됐지만 응답만 유실된 경우는 저장 결과와 중복 요청 결과를 확인한다. 동시성 TC는 같은 대상에 독립 연결/요청을 만들고 barrier·deferred promise 등으로 설계한 충돌 지점에서 두 요청을 대기시킨 뒤 함께 진행한다. 반환값뿐 아니라 최종 불변조건·중복 수·부분 저장을 확인한다. 임의 sleep이나 두 순차 호출만으로 경합 검증 완료라고 쓰지 않는다. 구현의 잠금 위치에 억지로 맞춘 테스트만 만들지 말고 외부 계약의 동시 입력도 확인한다.

**판정:** fixture가 다른 TC 실행 순서에 의존하지 않고, 선택 경계의 예상 결과·데이터 보장이 유지되며 정리 실패가 없는 경우 통과이다. 실패 TC가 실제 주입된 사건 없이 오류 메시지 mock만 확인하거나 fake로 실제 저장소 경쟁 보장을 주장하면 수정 필요이다. 재실행으로 한 번 통과했다고 불안정한 실패를 숨기지 않고 최초 실패·재현 조건을 기록한다.

**축약:** 외부 연동·쓰기 없는 단순 규칙에는 네트워크/DB fixture가 필요 없다. 임시 자원이 메모리 객체뿐이면 명시 삭제 대신 TC별 새 객체가 정리 근거가 될 수 있다. 실제 환경이 없으면 대역 검증은 가능하지만 실제 경계의 검증 완료는 보류한다. 운영 데이터 초기화나 실수 가능한 전역 삭제는 검증 방법으로 채택하지 않는다.

## T06. TDD·테스트 후작성·특성화·수동 재현

**연결·근거:** C24. PDF pp.397–399, 409, 419, 421–422의 테스트 목적·회귀·TDD를 채택한다. 특성화는 현재 동작을 관찰해 변화 여부를 기록하는 실무 방식으로 아래에 정의했으며, 관찰된 동작을 사용자 요구사항으로 승격하지 않는다.

| 후보 | 선택 조건 | 사용하지 않는 조건 |
| --- | --- | --- |
| TDD | 요구·입출력·oracle가 명확하고 빠른 테스트 경계가 있음 | 시각 배치·실험 단계처럼 예상값이 아직 확정되지 않은 경우 형식 강제 금지 |
| 테스트 후작성 | 먼저 얇은 구현/환경 연결이 필요하지만 인수 기준은 정해져 있음 | 구현의 출력 복사로 예상값을 정하면 안 됨 |
| 특성화(characterization) | 명세 없는 기존 코드의 영향 범위·보존할 관찰 결과를 알아야 함 | 확인된 결함을 올바른 동작이라고 영구 고정하면 안 됨 |
| 수동 재현 | 자동화 비용이 큰 시각·브라우저·환경 결함, 도구 없는 일회성 변경 | 재현 조건 없는 “확인했음” 기록 |

**EDGE 기본:** 재현 가능한 규칙 결함은 수정 전 실패 TC를 먼저 만들 수 있는지 판단한다. 가능하면 Red→최소 수정→Green을 사용하고, 필요한 범위의 개선 후 관련 회귀를 확인한다. 전면 리팩토링은 TDD 단계의 의무가 아니다. 새 UI 연결은 인수 조건을 먼저 쓰고 후작성/시스템 확인을 선택할 수 있다.

**입력→절차→산출물:** 사용자 요청·제공 진단·인수 기준 → 동작을 노출하는 가장 작은 준비/행동/관찰 작성 → 수정 전 실행이 허용·가능하면 실패 이유가 목표 결함인지 확인 → 최소 수정 → 같은 사례 재확인 → T07의 회귀 실행. 특성화는 별도 `관찰된 동작 / 보존 필요 여부 / 근거 미정 / 알려진 결함` 상태를 남긴다. 결과는 `수정 전 증거 / 수정 후 결과 / TC 또는 수동 단계 / 실행 제약`이다.

**판정:** TDD의 첫 실패는 목표 assertion 실패여야 한다. 문법 오류·설치 오류를 Red 증거로 삼지 않는다. 원본/환경 부재로 수정 전 결과가 없으면 “수정 전 미실행”으로 적고 실패를 꾸며내지 않는다. 사용자 진단서를 받았으면 같은 원인 분석을 처음부터 반복하지 않고 재현·수정 검증에 필요한 범위만 확인한다.

**축약:** 문구 수정은 전후 화면 관찰로 충분할 수 있다. 재현이 외부 운영 부작용을 요구하면 허용된 대역/격리 환경을 선택한다. 수정 전 테스트를 만들 수 없다는 이유로 필요 없는 프레임워크 도입·원인 재분석을 자동 수행하지 않는다.

## T07. 명세·구조 커버리지와 영향 기반 회귀

**연결·근거:** C25. PDF pp.397, 407, 413, 418–419, 422와 p.269의 검증·추적 보고를 근거로 한다. [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) §4.3의 statement/branch 구별도 확인했다. 아래 기본 목표는 EDGE가 이번 변경에 적용하는 정책이며 전체 소스의 임의 비율을 정한 것이 아니다.

| 후보 | 선택 조건 | 해석 한계 |
| --- | --- | --- |
| 요구사항·UC·규칙·분할·전이 커버리지 | 변경의 인수 기준과 필수 경로 누락 판정 | 연결률·실행률·통과율은 서로 다름 |
| 라인/statement | 새 규칙·미실행 코드 위치를 빠르게 탐색 | 실행됐어도 예상값 assertion이 없으면 동작 검증 아님 |
| branch | 조건의 참/거짓 경로·오류 처리 누락을 탐색 | 복합 조건의 모든 조합이나 동시 순서를 보장하지 않음 |
| 변경 영향 기반 회귀 | 변경 지점과 소비자·공유 계약·데이터 관계가 알려짐 | 관계를 모르면 작은 범위만 택할 근거가 부족 |
| 기존 전체 자동 suite | 빠르고 격리돼 있으며 환경이 준비됨, 영향이 넓거나 도구/공유 기반 변경 | 느린 외부 부작용 TC는 허용·환경 확인 없이 실행하지 않음 |

**EDGE 기본:** 확정 필수 인수 기준과 T02·T03에서 정한 필수 검증 단위는 누락 없이 검사한다. 구조 커버리지 수치는 보조 근거로 사용한다. 핵심 권한·쓰기 불변조건의 미검증 분기는 전체 비율이 높아도 완료를 막는 미검증 항목으로 기록한다. 전체 코드 80%·90% 등의 목표를 근거 없이 일괄 부여하지 않는다.

**입력→절차→산출물:** 변경된 모듈·계약·설정·데이터 → 직접 소비자 → 같은 계약/규칙/캐시를 사용하는 인접 흐름 → 영향받는 역할·성공/실패/경계 도출 → TC 선택 이유 기록 → 수정 확인 TC부터 영향 회귀 순서로 실행 → 관련 변경이나 결함 수정이 없으면 같은 성공 검사를 이유 없이 반복하지 않는다. 구조 측정을 사용하면 도구·버전·대상 경로·제외 파일·분모와 미검증 분기의 의미를 남긴다.

**판정:** 선택한 필수 TC가 실제 실행되고 명세/QR과 일치하며, 영향 대상 누락·필수 실패·판정 불가가 없어야 해당 범위 검증 완료이다. 기존 실패가 바깥에 있으면 `기존 / 이번 신규 / 이번 영향으로 악화`를 구분하고 전체 suite 성공으로 보고하지 않는다. 알 수 없는 영향 범위는 공유 경계/전체 기존 suite로 확대하거나 미검증 제약으로 남긴다.

**축약:** 정적 문구는 변경 화면과 공유 컴포넌트의 영향을 받는 화면만 확인할 수 있다. 공유 타입·어댑터·권한·빌드 설정 변경은 소비자 회귀를 확대한다. 성능·접근성·실환경 결과는 수행한 해당 조건에 한정해 보고한다.

## T08. 테스트 도구의 후보·선택 기준

**연결·근거:** C23, C26. PDF p.428의 “적용 가능한 방법 선정”을 도구 선택의 원칙으로 채택한다. 확인한 프로젝트 `game-dev-club-site/package.json`에는 Next.js 14.2.3·React 18·TypeScript 5·ESLint 8과 dev/build/start/lint가 있으며 테스트 러너/명령은 없다. 실제 도구 도입 시 그 시점의 lockfile·Node·설정·공식 호환 정보를 다시 대조한다.

| 후보·공식 근거 | 선택 조건 | 제외·비용·주의 |

**EDGE 기본:** 이미 채택한 러너가 있으면 우선 재사용한다. 신규 선정이 실제로 필요하면 `순수 TS/클라이언트 규칙: Vitest와 Jest`, `간단한 Node 실행 로직: node:test`, `서버 포함 사용자 흐름: Playwright와 Cypress`를 비교 후보로 잡는다. Next.js 14 공식 연동 방법, 선택 버전의 실제 실행 환경, 유지 비용을 충족하는 가장 작은 조합을 선택한다. 이 문서에서는 러너 한 개를 확정하지 않는다.

**입력→절차→산출물:** T01의 검증 대상 → 기존 설치·scripts·lockfile 확인 → 대상 실행 환경(Node/DOM/브라우저/Next 서버) 구별 → 필요한 mock·alias·TS·coverage·보고 기능 비교 → 실제 도입 작업에서 대표 TC 하나와 설정 비용으로 호환 확인 → `후보 / 요구 기능 / 기존 자산 / 지원 근거 / 비용 / 선택·기각 이유 / 버전·명령`을 기록한다. 도구 실험·설치는 해당 실제 작업 범위에 있을 때 수행한다.

**판정:** 러너가 필요한 대상과 assertion을 실행할 수 있고 종료 코드·결과를 얻을 수 있으며 변환/타입/Next 지원의 한계가 명시되면 선택 통과이다. 인기·최신이라는 이유만 있거나 지원하지 않는 Server Component 경계를 누락하면 수정 필요이다. 공식 최신 문서의 요구 버전이 현재 프로젝트와 다르면 해당 버전 문서·release 근거로 비교하고 임의 업그레이드하지 않는다.

**축약:** 일회성 표시 수정은 기존 브라우저 수동 TC를 택할 수 있다. 반복되는 규칙을 자동화하기 위한 비용이 정당화될 때 러너를 도입한다. 도구 선정 보고서·벤치마크·중복 프레임워크 설치는 필수가 아니다.

## T09. 린트·타입·빌드·정적 분석의 판정

**연결·근거:** C26. PDF pp.402, 462의 정적 분석 오탐 가능성과 분석 전후 기록을 채택한다. [ESLint Configure Rules](https://eslint.org/docs/latest/use/configure/rules)의 severity·억제 방식, [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/2/basic-types.html)의 정적 타입 검사와 변환 구별을 읽었다. 현재 ESLint 8 설정을 최신 flat config로 바꾸라는 의미가 아니다.

| 후보 | 확인 대상·선택 조건 | 검증하지 않는 사실 |
| --- | --- | --- |
| `npm run lint` | 현재 Next/ESLint 규칙의 코드·React·접근성 관련 진단 | 실행 시 실제 사용자 흐름·DB 결과 |
| `npx --no-install tsc --noEmit` | 로컬 TypeScript 설치가 있고 TS/공유 계약이 바뀔 때 | 외부 JSON 런타임 형식, 권한·부작용, 타입 검사를 생략한 변환 |
| `npm run build` | Next 컴파일·생성·배포 빌드 조건에 영향 | 실제 배포 성공·사용성·실제 인증·외부 서비스 가용성 |
| 추가 보안/품질 분석 | 기본 도구가 다루지 못하는 실제 위험·반복 결함이 있으며 역할과 유지 비용이 설명됨 | 모든 경고가 실제 결함, 또는 모든 결함이 도구로 발견된다는 주장 |
| 수동 코드 리뷰 | 도구의 진단을 계약·자료형·호출·불변조건과 대조 | 실행이 필요한 사실의 성공 보고 |

**EDGE 기본:** 현재 도구를 먼저 사용하고 검사 종류별 결과를 분리한다. 실행 위치는 `game-dev-club-site`이다. 스타일-only 경고와 실제 기능·권한·데이터 결함은 도구 severity만으로 동일 취급하지 않는다. 추가 도구는 보완할 결함 종류가 특정될 때 선택한다.

**입력→절차→산출물:** 변경 대상·기존 설정 → 필요한 검사 선택 → 기준선 결과가 있으면 변경 전후 동일 조건 대조 → `도구·규칙 / 파일·심볼 / 메시지 / 기존·신규·악화 / 실제 영향 / 조치` 분류 → 최소 확인으로 진단이 실제 규칙 위반인지 판정 → 수정 후 같은 검사 재확인. 분석 억제가 필요한 오탐은 `왜 현재 계약에서 도달 불가/잘못된 진단인지 / 최소 억제 범위 / 근거 / 재검토 조건`을 남긴다. 제공된 진단이 있으면 충돌 여부 확인 이상의 전면 재분석은 하지 않는다.

**판정:** 선택한 검사별 exit code·실행 환경·오류/경고가 있어야 실행을 판정한다. 신규 타입 오류·빌드 실패·현재 error 규칙 위반은 검사 실패이다. 확인된 권한/데이터 위험은 warn이어도 기능 완료의 미해결 결함이다. 무관한 기존 오류가 남으면 범위를 구분해 보고하고 전체 검사 성공으로 쓰지 않는다. 도구 설치·환경 오류는 코드 결함과 별개로 차단이다. 경고를 끄거나 전체 파일 제외해 성공으로 만드는 것은 허용하지 않는다.

**축약:** Markdown 지침만 바꾸는 경우 앱 lint/type/build는 앱 검증 범위에 해당하지 않는다. 관련 코드 변경에서는 영향을 받는 검사만 선택하되 타입·빌드 영향이 있으면 이를 빼고 완료라고 하지 않는다. 경고 개수 채우기나 관련 없는 스타일 정리는 하지 않는다.

## T10. UI·반응형·브라우저·접근성 검사 범위

**연결·근거:** C27. PDF pp.401, 417–418의 목적·사용자 기대·시스템 검사 범위에서 도출했다. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)의 아래 성공 기준과 전체 페이지 준수 조건, [W3C 평가 도구 선택 안내](https://www.w3.org/WAI/test-evaluate/tools/selecting/)의 자동 검사 한계를 확인했다. 지원 환경·접근성 목표의 실제 요구사항이 있으면 그것을 우선한다.

| 후보 | 선택 조건 | 판정 범위 |
| --- | --- | --- |

| 브라우저 자동 TC | 반복되는 필터·입력·이동·서버 렌더링 흐름 | locator·assertion으로 확인한 사실 |
| 이미지 비교 | 배치/테마의 반복 회귀, 안정된 데이터·OS·폰트·브라우저 baseline가 있음 | 이미지 차이는 사람이 의도/결함으로 판정. 자동 baseline 교체 금지 |
| 자동 접근성 검사 | DOM에서 찾아낼 수 있는 레이블·역할·대비 등 반복 점검 | 키보드 흐름·텍스트 의미·모든 기준은 수동 판단 추가 |

**EDGE 기본:** 변경 화면의 정상과 적용되는 빈 결과·loading·error·긴 콘텐츠 상태를 선정한다. 지원 환경이 확정돼 있으면 그 행렬을 적용한다. 미정이면 현재 작업 브라우저와 뷰포트를 명시해 검사하며 “모든 브라우저 지원”으로 확대하지 않는다. CSS/Tailwind의 실제 사용 breakpoint `b`를 찾아 `b-1,b,b+1 CSS px`와 구간 대표 폭을 확인한다. 프로젝트 전체 breakpoint를 무조건 모두 검사하지 않는다. 글자/레이아웃 변경이면 200% 텍스트 확대와 320 CSS px reflow도 관련 범위에서 점검한다.

| 폼·custom control | 3.3.1·3.3.2·4.1.2: 입력 레이블·오류의 텍스트 설명·이름/역할/값을 확인 |
| 비동기 결과·실패 메시지 | 4.1.3: 상태 메시지가 포커스 이동 없이 보조기술에 전달 가능한지 확인 |

**입력→절차→산출물:** 변경 화면·UC·CSS·지원 요구 → 영향 상태/뷰포트/입력장치/브라우저 행렬 작성 → 큰 차원은 T04로 축약하되 관련 breakpoint·키보드·실패 상태는 고정 포함 → 화면 동작·잘림·겹침·접근성 항목 실행 → `화면·상태 / 브라우저·버전 / CSS 폭·확대 / 입력 방식 / 적용 SC / 방법 / 실제 결과·근거` 기록. 이미지 비교 baseline가 없으면 이번 화면 관찰을 기존 회귀 통과라고 부르지 않는다.

**판정:** 선택한 인수 조건과 적용 SC·금지 겹침/잘림·조작 가능성을 만족해야 그 UI 범위가 통과한다. 미확인 기기·스크린리더는 미실행이다. 체크 도구가 0건을 보고해도 수동 필수 항목이 남으면 접근성 전체 완료가 아니다. 동작하지 않는 메뉴·읽을 수 없는 문구·오류 상태 숨김은 수정 필요이다.

**축약:** 단순 문구는 관련 크기·긴 텍스트 확인으로 축약할 수 있고 입력 동작 검사는 기존 의미가 변하지 않으면 생략 근거를 남긴다. custom control·폼·레이아웃 변경은 해당 키보드/레이블/폭·오류 조건을 확인한다. 디자인 개선 요청 없이 사이트 전체를 새로 꾸미지 않는다.

## T11. QA 리뷰·V&V와 완료 판정

**연결·근거:** C28. PDF pp.168–170, 269, 397–403, 416–418의 요구 검토·V&V·사용자 테스트·UC 기반 검사를 채택한다. [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) §3.2의 review 종류와 절차를 확인했다.

| 후보 | 선택 조건 | EDGE 적용·한계 |
| --- | --- | --- |
| 체크리스트 기반 자체 리뷰 | 작은 변경, 이미 명확한 판정 기준 | 작성자·대상·근거·결과 기록. 독립 peer review라고 부르지 않음 |
| walkthrough | 요구/흐름 이해·분기 누락 확인, 작성자가 UC를 따라 설명 | 역할·입력·실패 후 상태를 단계별 질문. 실행 결과와 구별 |
| 기술 리뷰·peer review | 권한·저장·공유 계약·아키텍처 결정의 반례 검토, 검토자 확보 | 다른 검토자의 실제 의견만 기록. AI/개발자가 사용자 인수 승인 대신 서명하지 않음 |
| formal inspection | 반복 중대 결함·큰 산출물·독립 검토/추적이 실제로 요구됨 | 계획·개별 검사·이슈 정리·조치·재확인과 역할 분리 비용. 기본 강제 아님 |
| 실제 사용자·운영자 Validation | 용어·업무 흐름·사용성 결정을 개발자 실행만으로 판단 불가, 사용자가 인수 검토를 요청 | 실제 참여 여부와 결과 기록. 외부 사용자 연락·새 승인 절차를 자동 추가하지 않음 |
| 프로토타입/개발자 대표 시나리오 | 아직 구현 전이거나 업무 가정을 비교할 필요 | 모델의 Validation·개발자 수행이라고 정확히 표시 |

**EDGE 기본:** 판정 기준을 사용한 자체 리뷰와 대표 UC 실행을 수행 범위로 계획한다. 위험이 큰 경계는 가능한 peer review를 더하고, 못 했다면 자체 검토와 남은 한계를 표시한다. 형식 검사 보고서·독립 QA 조직·단계별 사용자 승인은 기본 요건이 아니다.

formal inspection을 실제로 택한 경우 `작성자 / 리뷰 책임자 / 검토자 / 기록자`를 지정하고 작성자는 리뷰 책임자·기록자 역할을 맡지 않는다. 검토자는 회의 전 개별 확인으로 문제 후보를 남기고, 회의에서는 문제의 재현·근거와 담당 조치를 결정하며, 작성자의 수정 뒤 지정 검토자가 출구 기준을 다시 확인한다. 이 역할·절차를 갖추지 못한 자체 체크를 formal inspection이라고 부르지 않는다.

**입력→절차→산출물:** 이번 범위의 FR·BR·QR·UC, 설계·변경 코드·TC 결과 → 리뷰 대상/버전·기준·검토자 결정 → 정상 흐름·각 주요 실패/보장·관련 불변조건을 따라 반례 검토 → 발견한 문제·영향 ID·조치 기록 → 고친 항목 재확인 → V&V 결과를 분리하고 미실행·실패·미정 상태 대조 → 최종 보고.

**대표 시나리오 선정:** 확정 범위에 속한 각 역할의 주요 목표 기본 흐름을 포함하고, 권한 거부·실패 후 데이터 보존·외부 오류·상태 충돌 중 변경의 위험을 대표하는 Extension을 추가한다. “주요”는 사용자가 필수라고 정했거나 그 흐름 실패가 목표를 막는 경우다. 빈도 자료가 없으면 임의 인기 순위를 만들지 않는다. Verification은 FR/OP/BR/QR의 명시 결과와 비교하고, Validation은 같은 실행이 요청한 역할의 목표·운영 목적을 실제로 달성하는지 확인한다.

**판정:** [작성·판정 기준의 단계별 증거](../DEVELOPMENT_CRITERIA.md#completion), T07의 필수 검증, T12의 연결 대조를 충족해야 해당 범위 완료이다. 명세와 일치해도 사용자 목표를 못 달성하면 Validation 수정 필요이다. 실행 결과 없이 시나리오를 읽은 경우는 리뷰 완료일 수 있지만 동작 검증 완료가 아니다. 실제 사용자 검토를 요구받은 경우 받지 않은 결과는 미실시로 둔다. 설계만 요청받은 작업은 설계까지의 통과 조건으로 완료하고 구현/실행을 완료로 쓰지 않는다.

**축약:** 작은 수정은 요청→기대 상태→변경→실제 확인→남은 제약 한 기록으로 리뷰·V&V를 통합할 수 있다. 요구/권한/데이터 결정이 미정이면 그 의존 작업만 판정 불가로 남기고 확정된 범위는 계속한다.

## T12. 추적 행렬·ID 검사·이슈 연결과 버전 대조

**연결·근거:** C29. PDF pp.58, 159, 269의 양방향 추적·교차 참조·Traceability Matrix를 채택한다. 아래 저장·검사 후보는 EDGE의 규모에 맞춘 실행 방식이다. 전체 기존 사이트를 소급 문서화하지 않는다.

| 후보 | 선택 조건 | 제외·한계 |
| --- | --- | --- |
| 기능 문서 Markdown 행렬 | 변경 범위가 한 기능/일부 공유 경계이며 ID·코드·TC를 사람이 대조 가능 | EDGE 기본. 같은 규칙을 다른 파일에 복사해 독립 정의하지 않음 |
| 코드·TC의 ID와 자동 스캔 | ID가 많아 참조 누락/중복이 반복되고 기계적 검사가 이익 | 실제 요구 내용과 예상값의 일치는 수동 검토 필요. 스캔 성공은 의미 일치 증명이 아님 |
| issue/PR 링크 | 이미 업무 추적 도구를 사용하며 결정·변경·결함 논의가 그곳에 있음 | 접근·유효 버전 유지 필요. 링크만 있고 결정 내용/상태가 없으면 불충분 |
| 별도 ALM/요구 관리 도구 | 많은 팀·제품·기준선/승인 관계 때문에 기존 파일 유지 비용이 커짐 | 이번 소규모 변경에 임의 도입하지 않음 |

**EDGE 기본:** 기능 파일의 행렬을 기준 위치로 두고 `요구 ID / 출처·상태 / UC·OP·BR·QR / 설계 책임 / 실제 코드 경로·심볼 / TC·방법 / 결과·근거 / 기준 버전`을 유지한다. 관련 커밋·PR이 있으면 연결하며, 없으면 branch/HEAD와 작업 중 파일이라는 사실을 표시한다. 커밋하지 않은 상태를 커밋 SHA만으로 완전히 식별했다고 쓰지 않는다.

**입력→절차→산출물:** 작업 시작 시 기존 명세와 현재 코드 상태 대조 → 요구 추가/변경/제외 때 같은 ID의 이력·영향 연결 갱신 → 구현 시 계획 경로를 실제 경로·심볼로 변경 → TC 예상값 변경 이유를 관련 요구와 연결 → 결과에는 실행한 코드/데이터·환경 버전 기록 → 완료 전 아래 세 방향 대조 → 누락/고아 링크 목록을 조치. 기준 버전은 실제 존재하는 SHA/파일 revision/작업 상태 중 선택하고, ID 의미를 바꾸면 기존 요구 제외·새 ID 발급을 검토한다.

1. 요구사항→설계/구현/검증: 이번 확정 필수 요구에 책임·코드·방법·실제 판정이 있는가.
2. 변경된 외부 동작/규칙→요구사항: 요청 근거 없는 새 동작·정책이 생겼는가. 내부 보조 코드마다 별도 FR을 만들지는 않는다.
3. 테스트/리뷰→요구사항: TC oracle와 요구·규칙 버전이 같고, 링크와 참조 심볼이 실제 존재하는가.

**판정:** 필수 요구의 누락·끊긴 링크·다른 버전 결과를 현재 통과로 쓰는 문제가 없으면 추적 검토 통과이다. `연결됨`, `실행됨`, `통과함`은 별도 상태이다. 분모가 0이면 해당 없음, 보류/제외는 분모와 이유에서 구분한다. 삭제/이름 변경 뒤 추적 경로가 낡았으면 수정 필요이다. ID 스캔을 안 했으면 자동 검사 완료로 적지 않는다.

**축약:** 단순 수정은 요청 링크/문구·실제 파일·수동 TC·결과 한 줄로 추적 가능하다. 다수 규칙·인터페이스·여러 TC가 있으면 행렬로 확대한다. 새 플랫폼·독립 추적 보고서는 필요할 때만 도입한다.

## T13. CMMI 품질 실무의 최소 운영

**연결·근거:** C34의 품질 보증·검증·확인. PDF pp.56–62, 269에서 프로세스 개선·요구 추적·QA 산출물의 역할을 확인했다. [SEI CMMI V1.3 and Architecture-Centric Engineering](https://sei.cmu.edu/documents/3113/2011_017_001_23331.pdf)의 Validation·Verification 항목과 [SEI의 PPQA 해석 자료](https://insights.sei.cmu.edu/documents/721/2003_005_001_14264.pdf)의 공식 검색 발췌를 읽었다. 외부 두 PDF의 해당 본문 직접 읽기/렌더링은 실패해 검색에서 확인한 준비·수행·결과 분석 및 목적·객관적 평가 요지만 보조 근거로 사용했다. 버전별 모든 practice를 충족했다는 주장은 하지 않는다.

| 후보 | 채택 조건 | 이 프로젝트의 선택 |
| --- | --- | --- |
| 기능 기록에 통합한 가벼운 품질 운영 | 한 작업에서 대상·기준·결과·시정 조치·재확인 추적 가능 | 기본. T01–T12의 근거를 재사용 |
| 별도 리뷰/검증 보고 | 복수 검토자·큰 기능·실환경 결과 때문에 기능 파일이 복잡해짐 | 기존 파일에서 결과 링크, 독립 중복 정의 금지 |
| 정식 appraisal·성숙도 평가 | 조직의 별도 목표·승인·자원이 실제 존재 | 기본 제외. 이 지침 준수로 등급을 주장하지 않음 |

**EDGE 기본 운영:** VER 취지는 명세 기준의 검사·리뷰·실행 결과, VAL 취지는 역할의 목표/의도 환경 시나리오 결과, PPQA 취지는 필요한 절차·산출물이 기준을 따랐는지와 발견한 미준수의 조치 기록으로 연결한다. 테스트 한 번의 성공을 모든 품질 실무 충족으로 취급하지 않는다.

**입력→절차→산출물:** 변경 위험·단계 기준 → 검증 대상·환경·절차 선정(T01–T10) → 독립 여부를 정확히 표시한 리뷰(T11) → 결과/문제/조치/재확인 기록 → 추적성 대조(T12) → 완료 보고에 남은 미준수·미실행 범위 포함. 최소 기록은 `기준·대상 / 확인한 근거 / 결과 / 문제·영향 / 조치 / 재확인 상태`이며 담당자·검토자가 있으면 함께 적는다.

**판정:** 각 적용 기준의 증거를 찾을 수 있고 미준수/판정 불가가 통과와 섞이지 않으며 해결한 문제는 재확인 결과가 있으면 가벼운 품질 운영이 수행된 것으로 본다. 핵심 미해결 문제는 완료 판정에서 그대로 남긴다. 점수·등급·통계적 관리·조직 감사의 수행 완료를 의미하지 않는다.

**축약:** 작은 수정은 기능/작업 기록 한 문단에 통합한다. 권한·영속 쓰기·외부 장애의 영향이 크면 실제 경계와 실패/복구 검증 증거를 확장한다. 같은 사실에 대해 CMMI 전용 양식을 추가로 채우거나 사용자 단계 승인을 요구하지 않는다.
