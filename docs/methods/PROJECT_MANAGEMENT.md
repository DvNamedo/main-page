# 계획·형상·위험·개선의 실행 방법

이 문서는 [감사 목록](../GUIDELINE_AUDIT.md)의 C30-C35를 구체화한다. 자료에서 확인한 방법의 취지와 EDGE가 추가한 선택·실행·판정 규칙을 구분한다. 기능 기록·기존 이슈·PR에 내용을 통합하며 별도 조직 프로세스나 회의 체계를 강제하지 않는다. 예시 조건은 실제 사이트의 요구사항·배포 권한이 아니다.

## M01. 우선순위와 개발 순서 — C30

**후보·선택:** 요청에 이번 범위가 정해졌으면 `필수/선택/보류`를 그대로 사용한다. 날짜·예산에 맞춰 후보를 줄여야 하면 MoSCoW를 쓴다. 가치·불확실성·의존성이 순서를 좌우하면 정성 비교를 덧붙인다. RICE·WSJF 같은 점수 모델은 사용자 수·효과·소요량의 비교 가능한 근거가 있을 때만 후보이며, 지금은 숫자 입력 근거가 없어 기본으로 채택하지 않는다.

**EDGE 기본:** 이미 정해진 필수 범위를 유지하고, 의존성→중요 위험 해소→사용자 목표를 끝낼 수 있는 단위 순으로 정렬한다. 우선순위 분류와 실행 순서는 별도다. 필수 항목도 선행 계약·데이터가 없으면 먼저 착수하지 못한다.

**입력→절차→산출물:** 요청·FR/QR·제약을 읽는다 → 각 항목을 빼면 이번 목적이 성립하는지 판단한다 → MoSCoW가 필요하면 Must는 목적 불성립, Should는 중요한 불편이나 우회 가능, Could는 영향이 작은 개선, Won't는 이번 제외로 구분한다 → 같은 우선순위끼리 `기대 가치/증거 있는 위험/선행 ID/작업량의 범위`를 비교한다 → `ID/우선순위 이유/선행 ID/순서`를 남긴다. Should와 Could 경계가 애매하면 영향받는 목표와 가능한 우회의 비용을 문장으로 비교한다.

**점수 후보를 택한 경우:** RICE는 동일 기간 도달 수(R)·동일 목표 효과 척도(I)·근거 확신도(C)·동일 단위 총 작업량(E)을 정의해 `R×I×C/E`로 비교한다. WSJF는 같은 집합의 지연 비용(가치·시간 민감도·위험 감소)과 상대 작업량으로 `상대 지연 비용/상대 작업량`을 비교한다. 입력별 출처·척도·불확실성을 붙이고 입력 범위 변화에 따른 순서 변동을 확인한다. 분모가 0이거나 미정이면 계산하지 않는다. 필수 제약·사용자 범위·선행 관계를 점수로 덮지 못하며 현재는 입력 근거가 없어 기본에서 제외한다.

**판정·축약:** 이번 필수 목록과 선행 관계가 명확하고 선행 미완료를 무시한 순서가 없으면 통과한다. 모든 항목을 이유 없이 Must로 표시하거나 사용자가 정한 범위를 기술 편의로 제외하면 수정 필요다. 선택을 바꾸는 제품 정보가 없으면 [P07](PLANNING_ANALYSIS.md#p07)로 처리한다. 작은 수정은 `이번 요청 하나가 필수`와 관련 선행 조건 한 문장으로 축약한다. 점수·시간배분·회의를 의무로 만들지 않는다.

## M02. 작업 분해와 추정 — C30

**후보·선택:** 한 위치의 수정은 실행 목록, 여러 산출물·의존 관계는 WBS(결과물 기준 분해)+의존 목록, 날짜가 고정되고 병렬 자원이 실제 있으면 간단 일정표/임계 경로를 사용한다. 스토리 포인트는 비교 기준과 반복 실적이 있는 팀에서만 후보다. 알 수 없는 작업에는 짧은 기술 조사(spike)를 먼저 둔다.

**EDGE 기본:** [P01](PLANNING_ANALYSIS.md#p01)의 사용자 목표 단위를 기능별로 나누고, 필요한 분석·계약·구현·검증 작업만 붙인다. 파일 수나 코드 줄 수로 진행·작업량을 판단하지 않는다.

**절차:** 목표와 인수 기준 → 독립적으로 결과를 설명할 수 있는 작업 → 각 작업의 `산출물/완료 조건/선행 작업/미정 사항` → 여러 목표가 섞이거나 완료 판정이 불가능한 항목만 재분해한다. 추정이 필요한 요청이면 기존 유사 작업과 비교한 범위·가정·불확실성을 적는다. 실제 근거가 없는 완료 시간을 단정하지 않는다.

**조건부 후보 실행:** WBS는 목표 결과물→하위 결과물→작업으로 분해하고 말단 작업을 FR·완료 조건에 연결해 누락·중복을 대조한다. 임계 경로는 작업·기간·선행·가용 자원을 정의하고 순환을 제거한다. 종료 후 시작 관계에서는 `최조기 시작=max(선행 종료)`, `최조기 종료=시작+기간`으로 순방향, 마지막 종료에서 `최지연 종료=min(후행 시작)`, `최지연 시작=종료-기간`으로 역방향 계산한다. 두 시작 시점의 차이가 여유이며 날짜·자원 제약이 없을 때 여유 0인 연속 경로를 확인한다. 선행 지연이 후행/목표 날짜에 반영되지 않으면 수정 필요다. 자원이 겹쳐 실행 불가한 병렬 작업은 자원 제약을 반영해 다시 계산한다.

포인트는 완료된 기준 작업의 크기·불확실성과 새 작업을 비교하고 척도를 고정한다. 개인 시간·성과로 변환하지 않는다. 기술 조사는 `질문/허용 확인 범위/종료 조건/시간 제한이 있다면 그 값`을 먼저 정하고 공식 문서·작은 확인 결과를 지원/미지원/판정 불가와 실제 결정으로 반환한다. 질문에 답했거나 확인 한계가 확인되면 끝내고 조사 중 제품 기능을 임의 추가하지 않는다. 기준 작업·의존 기간 정보가 없으면 포인트·임계 경로 대신 기본 목록을 사용한다.

**판정·축약:** 모든 필수 목표에 구현과 필요한 검증 작업이 있고 선행 관계가 순환하지 않으면 통과한다. "백엔드 전부"처럼 끝을 관찰할 수 없으면 분해가 필요하다. 단순 수정에는 한 작업으로도 충분하며 계획·분석·검증을 다섯 파일로 나누지 않는다. 산출물은 기능 기록의 작업 목록 하나다.

## M03. 진척과 장애물 관리 — C30

**후보·선택:** 개인·소규모는 상태 목록, 여러 작업자가 병렬 진행하면 Kanban 보드, 실제 반복 기간과 계획량이 있는 팀이면 sprint backlog/burndown을 쓴다. Scrum 용어를 쓰려고 새 역할·회의를 만들지 않는다.

**EDGE 기본:** `대기/진행/확인 중/완료/차단/보류`와 결과 근거를 작업에 붙인다. 대기는 범위 안의 미착수, 차단은 외부 정보·접근 등 진행 조건 부재, 보류는 이번 우선순위에서 미선택이다. 구현됨과 검증됨은 별도 상태 필드로 남겨 코드가 존재한다는 이유로 완료하지 않는다.

**보드/차트 실행:** Kanban 보드는 시작·완료 지점·상태 이동 조건을 표시하고 처리 능력에 맞는 WIP 제한을 정한다. 새 작업보다 진행 작업의 완료를 우선하고 차단 원인·해제 조건을 표시한다. 시작/완료 시점으로 진행량·처리량·경과시간을 대조하며 보드만으로 Kanban 전체 준수를 주장하지 않는다. Burndown은 기간·남은 작업량 단위(작업 수/기존 추정량)를 정해 완료 정의를 만족한 작업만 차감한다. 범위 추가·제외는 따로 표시하고 검사 미실행은 완료로 차감하지 않는다. 두 후보의 상태가 실제 근거와 맞아야 통과하며 실적 없는 추세를 확정 마감일로 쓰지 않는다.

**절차·산출물:** M02 목록 → 지금 마칠 수 있는 목표 단위부터 착수 → 검사 단계는 확인 중 → [T11](TESTING_QA.md#t11)의 완료 기준으로 완료 → 새 정보·범위 변경·실패가 나오면 상태·선행 ID·남은 조치를 갱신한다. 차단에는 `부족한 조건/영향 작업/독립적으로 진행할 다음 작업`을 적는다.

**판정·축약:** 남은 필수 작업·실패·차단이 보이고 완료가 증거와 일치하면 통과한다. 검사 미실행을 숨겨 완료 비율을 높이면 수정 필요다. 일별 수치·보고서 제출을 강제하지 않으며 작은 수정은 최종 기록의 구현·검증 상태로 대체한다.

## M04. 기준선과 Git 변경 묶음 — C31

**후보·선택:** 기존 작업 브랜치 계속 사용, 짧은 topic branch, 동시 작업 간 파일 충돌·별도 실행환경이 필요할 때 worktree가 후보다. 직접 통합 브랜치 변경은 저장소의 기존 운영·사용자 요청이 허용할 때 선택한다. 장기 release 브랜치는 병행 지원 버전이 실제 필요한 경우에만 쓴다.

**EDGE 기본:** 요청한 `Namedo/Book-Management`에서 가이드를 작성한다. 이후 작업도 지정 브랜치·기존 변경을 먼저 확인한다. 새 분리가 필요할 때 이유를 남기고 기존 승인 범위에서 선택한다. 기능 파일·커밋·PR은 동일 ID 또는 목적을 참조할 수 있게 한다.

**절차:** `git status --short`, `git branch --show-current`, `git rev-parse HEAD`로 시작 기준선 확인 → 진단서가 가리킨 위치와 실제 diff로 변경 소유·범위 확인 → 목적이 같고 함께 적용해야 하는 코드·계약·명세·검증을 한 묶음으로 정리 → 의존성 변경은 manifest·해당 lockfile을 함께 관리 → 저장·공유를 요청받은 경우에만 해당 commit/PR 참조를 기록한다. 이미 존재하는 사용자 수정은 보존하고 무관한 diff를 포함하지 않는다.

**판정·축약:** 버전·이번 수정·기존 수정이 구분되고 묶음에 무관한 파일이 없으면 통과한다. 실제 커밋하지 않았으면 `미커밋 변경`으로 기록한다. 양식만으로 자동 commit/push/PR/배포를 요청한 것으로 보지 않는다. 문구 한 줄은 시작 기준선과 수정 파일 기록으로 축약한다. 공유 이력을 되돌릴 때는 M06을 적용한다.

## M05. 환경·설정·의존성 재현 — C31

**후보·선택:** 버전·설정 표는 모든 환경 차이 조사에 사용한다. 프로젝트의 lockfile·런타임 버전 고정은 패키지 재현에, 컨테이너는 OS·네이티브 도구 차이가 실제 문제일 때, feature flag는 병행 전환·차단 필요가 있고 기존 지원 방식이 있을 때만 선택한다.

**EDGE 기본:** 저장소의 package manifest·lockfile·배포 설정을 확인하고 변경한 경계에 필요한 환경 차이만 기록한다. 비밀값 대신 변수 이름·용도·필수 여부·서버/클라이언트 노출 구분·설정 출처를 적는다. 현재 스택의 버전을 그대로 확인하며 최신 문서의 동작을 기존 버전에 가정하지 않는다.

**절차:** 문제/변경이 작동할 환경 → `런타임/패키지/설정 이름/외부 접근 권한/빌드·캐시 조건` 대조 → 관련 차이를 분리 → 공개 가능한 설정 샘플과 공식 버전 문서 확인 → 승인된 실행 범위에서 같은 조건을 재현 → `환경/버전·설정 존재 여부/검사/차이·제약` 기록. 검사 권한·환경이 없으면 미검증으로 남긴다.

**조건부 산출물:** 컨테이너는 image/runtime 버전 또는 digest, 빌드·실행 명령, 설정 이름, volume·네트워크 경계, host와 다른 제약을 기록하고 선언한 조건에서 관련 검증을 재현한다. 비밀을 image에 포함하지 않는다. Flag는 기본값·평가 위치·대상·켜짐/꺼짐 계약·실패 기본값·제거 조건을 정하고 두 경로와 전환 시 보존 상태를 검증한다. 클라이언트 flag 값으로 서버 권한 규칙을 우회하지 않는다. 기존 운영 방식으로 충분하면 생략한다.

**판정·축약:** 변경에 필요한 변수·서비스·버전과 실행 위치가 설명되고 실제 비밀이 유출되지 않으며 환경 결과를 구별하면 통과한다. 로컬 빌드 통과를 운영 데이터·운영 권한 통과로 보고하면 수정 필요다. 설정 영향 없는 문구 수정은 `환경 계약 변경 없음`으로 축약한다. 지침을 작성하기 위해 설치·업그레이드를 하지 않는다.

<a id="m06"></a>

## M06. 릴리스·데이터 전환·복구 선택 — C31

**후보·선택:** 코드·설정만 바뀌고 이전 버전과 데이터가 호환되면 이전 배포로 복귀 또는 Git revert를 선택한다. 스키마/형식이 바뀌고 구·신 버전 공존이 필요하면 expand→migrate→contract를 검토한다. 덮어쓰기·삭제 등 데이터 위험에는 스냅샷/백업 복원, 이미 외부 효과가 난 경우에는 보상 작업 또는 forward fix를 검토한다. 중복 쓰기를 rollback으로 해결할 수 있다고 가정하지 않는다.

**EDGE 기본:** 배포·데이터 변경이 요청 범위일 때만 `실패를 무엇으로 탐지/어떤 버전과 데이터를 어디까지 복구`할지 결정한다. 정적 문서에는 변경을 되돌리는 diff/버전만 충분하다. 캐시와 외부 서비스 상태도 영향을 받는 경우 복구 대상에 포함한다.

**절차:** 변경 전 코드·설정·데이터 기준선 → 새/구 버전 읽기·쓰기 호환표 → 적용 순서·실패 신호·중단 지점 → 복구 후보와 잃거나 중복될 수 있는 데이터/외부 효과 비교 → 선택안·실행 책임·필요 권한·재확인 시나리오 기록. 실제 전환 작업이면 격리된 환경에서 복구가 가능한지 확인한 결과와 미확인 한계를 남긴다. 이전 버전 배포와 이전 데이터 복원은 서로 다른 작업이다.

| 선택한 후보 | 수행·확인 기준 |
| --- | --- |
| 코드/설정 복귀·revert | 복귀 버전과 현재 데이터 호환 확인→목적별 변경을 되돌림→관련 TC·캐시/환경 확인. 공유 이력을 삭제하는 reset과 새 변경으로 되돌리는 revert를 구별 |
| expand→migrate→contract | 구/신 계약 공존 지원→소비자·데이터 변환 후 식별·참조·건수/대상 규칙·중단 후 재개 확인→구 소비자 종료와 복귀 필요 종료 근거가 있을 때 구 계약 제거. 단계마다 호환·불변조건을 확인 |
| 백업/스냅샷 복원 | 대상·시점·포함 데이터·이후 유실 범위 정의→복원 자료/절차 확인→격리 환경에서 읽기/쓰기·식별/참조·필수 규칙 확인. 백업 파일 존재는 복원 성공이 아님 |
| 보상·forward fix | 완료된 외부 효과 식별→가역 효과는 보상 연산·멱등/중복·순서·보상 실패 정의, 비가역 효과는 후속 정정·사용자 결과·잔여 영향 정의→안전한 최종 상태·이력 확인. 보상은 원상복구와 동일하지 않음 |

**판정·축약:** 실패 후 복구 대상·순서·호환·한계가 있으며 실행 증거 또는 미실행 이유가 구별되면 준비 기록이 통과한다. 되돌릴 수 없는 외부 효과를 "롤백 가능"이라고 적으면 수정 필요다. 준비 통과는 배포 실행·사용자 승인 완료가 아니다. 기록 작성만으로 배포 권한이 생기지 않는다. 구현·배포가 없는 지침 작업은 해당 없음이다.

## M07. 위험 발견·평가·대응 — C32

**후보·선택:** 기본은 사건 중심 위험 목록+정성적 가능성/영향 비교다. 저장·상태·외부 연동의 실패가 서로 다른 후속 효과를 만들면 축약 FMEA를 쓴다. 공격 주체·자산·신뢰 경계가 바뀌면 [D05](DESIGN_IMPLEMENTATION.md#d05)의 권한 표와 위협 검토를 더한다. FTA는 여러 장애의 AND/OR 결합이 중요한 경우 선택한다. 발생 데이터가 없는 수치 확률 모델은 현재 후보에서 제외한다.

**EDGE 기본:** `조건이 X일 때 사건 Y로 인해 목표/데이터에 Z가 생길 수 있다`로 위험을 적는다. 현재 확인된 실패는 위험 가정과 구별해 결함으로 처리한다. 단순 문구 변경에 동시성·데이터 손실 위험을 만들어 넣지 않는다.

**발견 절차:** UC 정상·실패/OP/상태/데이터/환경 경계 → 잘못된 입력·거부 우회·중복/경합·부분 성공·외부 지연/오류·캐시 불일치·전환 실패 중 적용 항목 → 실제 근거와 영향 FR/QR/자원 연결 → 아래 정의로 평가 → 대응·잔여 조건·확인 방법을 적는다.

| 평가 축 | EDGE의 정성적 판정 정의 |
| --- | --- |
| 영향 큼 | 권한 우회·민감정보 노출·영속 데이터 손실/불변조건 위반·목표를 대체 경로 없이 막는 장애 |
| 영향 중간 | 복구/우회는 가능하지만 승인된 사용자 목표가 지연되거나 별도 운영 조치가 필요 |
| 영향 작음 | 데이터·권한을 깨지 않고 목표 달성에 영향을 주지 않는 제한된 표시/편의 문제 |
| 가능성 관찰됨 | 유사 사고·재현·로그 등 조건이 현재 실제 존재함. 확률 수치라는 의미가 아님 |
| 가능성 조건부 | 구체적 발생 조건과 경로는 확인했지만 현재 관찰되지 않음 |
| 가능성 미정 | 정보가 부족함. 낮음으로 간주하지 않고 정보 수집·보수적 제한 중 선택 |

**우선순위·대응:** 영향 큼은 가능성이 미정이어도 설계 대응 또는 명시적 미해결 처리가 필요하다. 같은 영향에서는 관찰됨→조건부 순으로 확인하고, 미정은 먼저 불확실성을 줄인다. 숫자 곱으로 심각한 위험을 낮추지 않는다. 대응 후보는 발생 제거(경로/방식 변경), 예방(검증·제약·권한), 탐지(오류·로그·지표), 완화(안전한 실패·격리), 복구(M06)이며 각 위험에 실제 가능한 조치를 연결한다. FMEA는 `연산/실패 형태/원인 조건/국소·사용자 효과/탐지/방지·복구/잔여 위험` 행으로 순차 검토하고 RPN 점수는 기본으로 쓰지 않는다.

**산출물·판정·축약:** 기능 기록의 위험 행에 근거·평가·조치·확인·잔여 위험이 있고, 큰 영향이 대응 없이 통과 처리되지 않으면 통과한다. 조치가 미실행이면 처리 계획과 완료를 구분한다. 한 위험은 한 문단으로 축약할 수 있다. 변경 밖의 위험은 후속 제안으로 기록하며 이 작업의 자동 범위로 만들지 않는다.

FTA를 선택하면 특정 최상위 실패·영향에서 원인 조건을 아래로 분해한다. 함께 발생해야 하면 AND, 하나로 충분하면 OR로 연결하고 leaf마다 코드·계약·로그 또는 가정을 적는다. 알려진 실패·반례가 논리로 설명되는지, 공통 원인을 독립으로 잘못 분리했는지 대조한다. 확인 가능한 원인 조건 또는 확인 불가 경계에서 멈추고 미정 leaf를 실패 불가능으로 간주하지 않는다. 산출물은 조건 논리·대응 위치이며 확률 계산·안전 증명이 아니다. 위험 대응 설계의 통과와 조치 실행 완료는 구별한다.

## M08. 반복·중요 결함의 원인과 재발 방지 — C33

**대상 판정:** 알려진 동일 실패 조건/규칙의 결함이 수정 후 재발했으면 반복 결함이다. 데이터 손실·권한 우회·핵심 목표 중단·대규모 잘못된 결과·긴급 복구를 필요로 한 실패는 중요 결함이다. 수치 장애 임계값은 관련 QR에서 정한 경우만 사용한다.

**후보·선택:** 제공 진단서가 있으면 그것을 1차 원인으로 삼는다. 원인이 짧은 인과 사슬이면 5 Whys, 여러 독립 후보가 있으면 fishbone/원인 범주표, 여러 연산·시점이 결합된 장애면 타임라인 기반 postmortem을 사용한다. 진단서가 있으면 추가 분석은 진단과 코드의 명백한 충돌 또는 수정 적용 불가 때 필요한 범위로 제한한다. 재발 자체를 전면 재분석 사유로 삼지 않고 기존 진단·수정·방지 조치의 해당 충돌/적용 불가 지점을 최소 확인한다.

**EDGE 기본 절차:** 재현 조건·원인 진단 참조 → 수정 위치·깨진 계약과 대응 → 재발 방지 테스트/제약/검토 규칙 중 직접 효과 있는 조치 → 예상 결과와 실제 재확인 → 잔여 조건 기록. 5 Whys는 각 답에 코드·로그·계약 증거를 붙이고 조치 가능한 원인에 닿으면 멈춘다. 질문을 다섯 번 채우거나 근거 없는 원인을 사실로 적지 않는다. Fishbone은 코드/데이터/경계·의존/환경/절차 등 적용 범주에서 후보를 적고 관찰과 충돌하는 후보를 제거한다. Postmortem은 영향·시점·발생/탐지/복구·기여 원인·조치를 한 기록에 연결한다.

**판정·축약:** 수정과 방지가 원인 조건을 직접 차단하거나 탐지하고, 확인 결과 또는 미실행이 분명하면 기록 통과다. "주의한다"만 있는 조치나 제공된 진단을 이유 없이 처음부터 재분석하면 수정 필요다. 테스트 하나의 통과가 미래 재발 불가능을 증명하지는 않는다. 경미한 첫 결함은 결함 재현·수정·회귀 기록으로 충분하고 분석 보고서를 추가하지 않는다.

## M09. CMMI 실무를 기존 작업 증거로 운영 — C34

**후보·선택:** 강의의 전체 프로세스 평가표, 별도 조직 프로세스, 기존 개발 산출물에 실무를 통합하는 방식 중 마지막을 채택한다. 평가표/성숙도 등급은 인증·조직 평가를 사용자가 별도 요청할 때만 범위를 새로 정한다. 아래는 강의가 다룬 실무 취지의 적용이며 특정 최신 CMMI 버전 전체 요구를 충족한다는 선언이 아니다.

| 실무 취지 | 실제 실행 방법 | 남기는 증거·판정 |
| --- | --- | --- |
| 요구사항 관리·양방향 추적 | P05/P06 → 변경 시 M10 → T12 | 출처·FR·설계·코드·TC가 유효 버전을 참조. 빈칸·잘못된 링크는 미완료 |
| 계획·진행 관리 | M01-M03 | 이번 필수 범위·선행·차단·남은 확인과 완료 근거 |
| 형상 관리 | M04-M06 | 시작 버전·이번 diff·설정/lockfile·전환/복구의 해당 증거 |
| 품질 보증·검증·확인 | T07·T09·T11-T13 | 기준에 따른 회귀/검사/리뷰/목표 확인과 발견 문제·조치·재확인 |
| 위험 관리 | M07 + 관련 D05-D09 | 실제 위험·판정 근거·예방/탐지/복구·잔여 조건 |
| 원인 분석·개선 | 반복·중요 결함에 M08 | 원인→수정→방지→확인. 제공 진단 우선 |

**절차·축약:** P02로 변경 분류 → 필요한 실무를 기존 기능 기록에서 참조 → 작업 중 관련 결정/실패가 바뀌면 해당 행 갱신 → 완료 시 증거가 현재 변경을 가리키는지 대조한다. 해당 실무가 없는 작은 변경은 `해당 없음+범위 이유`로 처리한다. 동일 증거를 복사해서 여섯 보고서로 만들지 않는다. 모든 관련 실무에 유효한 근거 또는 공개된 미완료 상태가 있어야 기록 통과이며 등급 점수화는 하지 않는다.

## M10. 결정·변경·AI 작업 맥락의 수명 관리 — C35

**후보·선택:** 작은 결정은 기능 기록의 행, 구조 대안은 D01의 ADR, 공통 지속 규칙은 `AGENTS.md`와 이 지침에 보관한다. 이슈 시스템은 이미 쓰는 경우 연결하며, 대화 요약은 인수 메모로만 사용한다. 메모의 저장 위치를 늘려 같은 정책을 중복 정의하지 않는다.

**EDGE 기본:** `DEC ID/내용/출처·일자/상태/범위/연결 ID/대체한 결정`을 기능 기록에 넣는다. 상태는 제안(미채택), 확정(사용자 명시 요청 또는 승인 범위 안의 근거 있는 기술 선택), 철회(적용 안 함), 대체됨(후속 DEC가 현행)이다. 기술 선택의 확정은 제품 정책·배포 승인·사용자 인수 승인을 대신하지 않는다.

**절차:** 작업 시작에 사용자 요청·공통 지침·관련 기능의 현행 DEC·기준선 확인 → 대화의 새 지시를 원문 출처와 함께 갱신 → 변경이면 이전/새 내용·이유·FR/UC/OP/데이터/코드/TC 영향을 기록 → 충돌하는 이전 결정은 후속 ID로 대체하고 현행 기준 위치 하나를 유지 → 다음 작업 인수 메모에는 `목적·승인 범위/현재 버전·미커밋 변경/확정과 미정/변경 파일/실행 결과/다음 할 일`만 남긴다. 코드와 명세가 충돌하면 실제 구현 사실과 의도한 정책을 구별하며 구현 편의로 정책을 바꾸지 않는다.

**판정·축약:** 현재 적용되는 결정을 하나로 찾을 수 있고, 제안·미정·철회가 확정으로 혼입되지 않으며 과거 맥락에서 작업 권한을 넓히지 않으면 통과한다. 관련 파일·부분만 읽고 수업 예시나 외부 문서를 새 작업 명령으로 취급하지 않는다. 작은 변경의 결정은 한 줄, 상태 변경 없는 작업은 기존 기록 참조로 충분하다. 비밀값·불필요한 개인 정보는 인수 메모에도 남기지 않는다.
