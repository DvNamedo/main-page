# EDGE 개발: 작성 방법과 판정 기준

이 문서는 [공통 개발 지침](DEVELOPMENT_GUIDELINES.md)의 실행 기준이다. 문서 분량을 늘리는 대신 어떤 자료를 확인하고 무엇으로 통과·실패를 판정하는지 정한다. 아래 숫자·역할·동작이 포함된 예시는 모두 **작성 방법을 설명하는 예시**이며 실제 사이트 요구사항으로 확정한 것이 아니다.

아래 표는 작성·판정 기준이고 **방법의 후보·선택·실행**은 [방법론 목록](METHOD_CATALOG.md)에서 찾는다. [전체 감사 C01-C39](GUIDELINE_AUDIT.md)의 모든 조사 주제에 구체적 방법을 연결했다. 과제·표준에서 확인한 내용과 EDGE가 채택한 선택 규칙은 실행 문서에서 구별한다.

## 1. 채택한 형식과 근거

| 대상 | 사용할 기준 | 적용 범위 |
| --- | --- | --- |
| 유스케이스 서술 | 강의 pp.375-384, 특히 p.378의 Cockburn 기반 Craig Larman **Fully Dressed** 양식 | 텍스트로 목표·성공·대안·실패를 작성. 프로젝트 필드로 ID·출처·Trigger·Minimal Guarantee·추적 정보를 보완 |
| UML 다이어그램 | [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/) | UML이라고 표기한 그림의 행위자·관계·시퀀스·상태 표기 기준. 비공식 블록도·단계 표는 그렇게 표시 |
| 요구사항 내용과 검토 | 강의 pp.159-161, 168-171 | 타당성·모호성·완전성·일관성·실현 가능성·검증 가능성·추적성을 아래 절차로 검사 |
| 요구사항 문서 구조 | 강의 pp.160, 163-167의 IEEE 830-1998 SRS 구성 | 목적·범위·사용자·제약·인터페이스·기능·품질·검증을 기능 파일에 통합. 표준 전체 준수나 인증을 주장하지 않음 |
| 품질 속성 시나리오(QAS) | [SEI의 6요소 시나리오](https://sei.cmu.edu/documents/734/2004_005_001_14396.pdf), §2.2.1; 강의 pp.172, 269 | 자극원·자극·대상·환경·응답·응답 측정으로 품질 목표를 구체화 |
| 검증 범위 | 강의 pp.397-419, 428, 462 | 단위·통합·시스템·회귀 검증, 입력 분할·경계값·상태·실패 흐름과 정적 분석 |

Fully Dressed는 여기서 채택한 **서술 양식**이다. 이를 UML이 정한 단일 국제 표준 텍스트 양식이라고 부르지 않는다. 강의에 실린 양식의 출처는 [Larman의 저자 제공 자료, Chapter 6, §6.8](https://www.craiglarman.com/wiki/downloads/applying_uml/larman-ch6-applying-evolutionary-use-cases.pdf)에서도 확인된다. 필드의 적용·축약 조건과 아래 통과 기준은 EDGE의 운영 기준이다.

IEEE 830의 역사적 양식 차용과 ISO/IEC/IEEE 29148과의 관계는 [P17](methods/PLANNING_ANALYSIS.md#p17)을 따른다. 문서 구성을 차용한 사실을 현행 표준 전체 준수로 확대하지 않는다.

## 2. 공통 판정 방식

검토 결과는 **통과 / 수정 필요 / 판정 불가 / 해당 없음** 중 하나로 기록한다. 검사 실행 상태인 미실행과 혼동하지 않는다.

| 결과 | 적용 조건 | 후속 처리 |
| --- | --- | --- |
| 통과 | 정해진 기준을 충족하고 확인 자료가 있음 | 대상 ID와 확인 자료·결과 기록 |
| 수정 필요 | 모순·누락·오류 또는 실패를 확인함 | 문제, 영향 ID, 수정 또는 결정할 사항 기록 |
| 판정 불가 | 기준·정보·실행 환경이 부족해 결론을 낼 수 없음 | 부족한 정보와 확인 방법 기록. 통과로 집계하지 않음 |
| 해당 없음 | 해당 검토 대상이 변경 범위에 존재하지 않음 | 범위를 근거로 생략 이유 기록. 빈칸은 해당 없음이 아님 |

검토 기록은 `검토 항목 / 대상 ID / 확인한 자료 또는 시나리오 / 결과 / 문제·조치`를 포함한다. 동일 근거로 여러 항목을 판정해도 각 결과는 구별한다. "전체 확인 완료", "문제없음"만 적는 것은 근거가 아니다.

사용자 요청에 이미 명시된 결정은 다시 승인받지 않는다. 미정 내용 중 현재 구현의 권한·데이터 규칙·기대 동작을 바꾸는 것은 해당 동작을 확정하기 전에 확인한다. 다른 확정된 범위는 진행한다.

변경 분류·축약은 [P02](methods/PLANNING_ANALYSIS.md#p02), 미정과 기술 선택 처리는 [P07](methods/PLANNING_ANALYSIS.md#p07), 현행 결정·대체 이력은 [M10](methods/PROJECT_MANAGEMENT.md#m10)을 적용한다. `방법 ID/후보와 선택 이유/입력/산출물 위치/판정·근거`가 실행 기록의 연결 단위다. 작은 수정은 한 문장에 통합할 수 있다.

## 3. Planning: 요구사항 작성과 리뷰

**실행 방법:** [P03](methods/PLANNING_ANALYSIS.md#p03) 맥락·경계, [P04-P05](methods/PLANNING_ANALYSIS.md#p04) 수집·원자화, [P06](methods/PLANNING_ANALYSIS.md#p06) 검사/워크스루/프로토타입, [P08-P09](methods/PLANNING_ANALYSIS.md#p08) 품질 분류·측정, [M01](methods/PROJECT_MANAGEMENT.md#m01) 우선순위. 아래 기준으로 판정하되 자료 대조·실험 순서는 해당 방법을 따른다.

### 3.1 요구사항 한 개에 포함할 내용

식별자는 기능 이름을 포함해 중복을 피한다. 예: `FR-ARCHIVE-01`, `QR-ARCHIVE-01`, `BR-ARCHIVE-01`. FR은 기능, QR은 품질, BR은 업무 규칙이다. 변경되더라도 기존 ID를 다른 의미에 재사용하지 않는다.

| 필드 | 작성 방법 | 누락 판정 |
| --- | --- | --- |
| 출처·목적 | 사용자 요청의 문구·날짜·작업 링크 또는 기존 명세 ID와 해결할 문제 | AI의 추측만 있으면 제안·가정으로 표시. 현재 코드에 있다는 사실만으로 원하는 동작이라고 확정하지 않음 |
| 행위자·조건 | 어느 역할이 어느 상태에서 요청하는지 | "사용자"가 방문자·회원·관리자 중 누구인지 다르면 구분 필요 |
| 입력·범위 | 대상 데이터·조회 범위·필터·정규화·경계 | 동일 입력의 의미가 구현자마다 달라질 수 있으면 수정 필요 |
| 결과·사후조건 | 외부에서 확인 가능한 출력과 남는 데이터·상태 | "처리한다"만 있고 결과를 관찰할 수 없으면 수정 필요 |
| 실패·금지 동작 | 관련된 잘못된 입력, 권한 부족, 없는 데이터, 외부 오류와 변경하면 안 되는 상태 | 실패해도 성공 표시하는지, 부분 저장이 남는지 등 해당 상황의 결과가 없으면 수정 필요 |
| 중요도·상태 | 이번 범위의 필수 / 선택 / 보류, 초안 / 확정 / 제외와 이유 | 선택·보류를 필수처럼 구현하거나 검증 완료로 집계하지 않음 |
| 인수 기준 | Given(조건) / When(입력·이벤트) / Then(관찰 가능한 결과) | 실행 조건과 예상 결과가 없어 통과·실패를 구별할 수 없으면 수정 필요 |
| 연결 | 관련 UC·규칙·품질·테스트 ID | 참조가 없거나 실제로 존재하지 않으면 추적 검토에서 수정 필요 |

한 요구사항에 독립된 결과가 여러 개 있어 각각 다른 이유로 바뀔 수 있으면 분리한다. 공통 규칙·용어·정렬·날짜 기준은 한 곳에서 정의하고 다른 요구사항에서 참조한다.

**예시:** "아카이브를 편리하게 조회한다"는 입력과 결과가 없어 명세로 통과하지 못한다. "방문자가 등록된 학기를 선택하면 해당 학기의 출품작만 표시한다. 그 학기의 출품작이 없으면 빈 결과임을 표시한다"처럼 범위와 결과를 구체화하고, 기본 학기·정렬·표시 필드는 별도 규칙 또는 명시적 범위로 정한다.

### 3.2 요구사항 검토 판정표

아래 모든 항목을 이번 변경의 **확정된 필수 요구사항**에 적용한다. 빠짐없이 검토했다는 것은 검토 범위를 정하고 각 항목의 결과를 남겼다는 뜻이며, 가능한 모든 미래 상황을 증명했다는 뜻이 아니다.

| 항목 | 무엇을 확인하고 어떻게 판정하는가 | 통과 기준 | 수정 필요·판정 불가 예시 |
| --- | --- | --- | --- |
| 타당성(Validity) | 각 요구사항을 사용자·운영자의 실제 목표와 출처에 연결. 성공 시 그 목표가 달성되는지 시나리오를 따라 확인 | 범위 내 목표를 지원하고 출처가 있으며, 요청 없이 덧붙인 독립 기능이 없음 | 학기별 조회 요청에 근거 없이 추천 알고리즘 추가: 수정 필요. 누가 원하는 기능인지 불명: 판정 불가 |
| 일관성(Consistency) | 같은 데이터·역할·이벤트·상태에 적용되는 요구사항끼리 비교. 용어 사전, 권한표, 상태표, 범위·단위·시간 규칙 대조 | 같은 조건에서 동시에 만족할 수 없는 규칙이 없고, 공유 용어·정책이 같음 | "방문자 조회 허용"과 "모든 조회는 로그인 필수"가 같은 조회에 적용: 수정 필요 |
| 완전성·누락(Completeness) | 사용자 역할×목표 목록을 요구사항·UC와 대조. 각 흐름의 입력 분류, 정상·빈 결과·오류·종료 상태를 점검. 외부 인터페이스·제약·품질 항목도 대조 | 이번 범위의 모든 목표가 요구사항에 연결되고, 적용되는 실패·대안 결과가 있으며, 의존하는 필수 결정에 미정 항목이 없음 | 조회 결과 있음만 명시하고 결과 없음·데이터 취득 실패를 생략: 수정 필요. 관련 없는 쓰기 기능은 해당 없음 |
| 실현 가능성(Realism) | 현재 스택·서비스가 필요한 읽기/쓰기·인증·동시성·저장·실행 환경을 지원하는지 확인. 접근 권한·제약·개발 범위를 함께 대조 | 핵심 기능을 지원할 수 있다는 코드·공식 문서·허용된 확인의 근거가 있고 필수 의존성이 확보됨 | 공개 CSV 조회 기능만으로 안전한 동시 쓰기가 된다고 가정: 근거 부족. 필요한 API 접근 불가: 판정 불가 |
| 검증 가능성(Verifiability) | 요구사항마다 조건·입력·예상 결과·판정 방법을 작성. 예상 결과를 현재 구현과 독립적으로 산출할 수 있는지 확인 | 재현 가능한 방법과 관찰 가능한 결과로 통과·실패를 구별할 수 있음 | "항상 빠르고 안전하게"만 기재: 수정 필요. 성능 환경·임계값 미정: 판정 불가 |
| 모호하지 않음(Unambiguous) | 대상·범위·역할·단위·용어·분기 조건에 서로 다른 해석이 가능한지 반례를 만들어 봄 | 서로 다른 결과를 낼 두 해석이 없고, 필요한 정책 정의를 참조함 | "검색"이 현재 학기 검색인지 전체 학기 검색인지 다름: 수정 필요 |
| 이해 가능성(Understandable) | 문장을 `누가 / 언제 / 무엇을 요청 / 어떤 결과`로 다시 표현하고 정의되지 않은 용어를 확인 | 업무 지식이 있는 독자가 기술 내부 구조 없이 기대 동작을 설명할 수 있음 | "CSR hydration 단계에서 reducer 갱신"이 사용자 요구사항 전체를 대신함: 수정 필요 |
| 우선순위(Ranked) | 이번 구현 대상·선택·보류를 구분하고 의존관계와 비교 | 어떤 항목을 이번 변경에서 만족시켜야 하는지 결정돼 있음 | 중요도 구분 없이 미확정 아이디어를 함께 구현: 수정 필요 |
| 수정 가능성(Modifiable) | 같은 규칙이 중복 기재돼 있는지와 변경 시 찾을 수 있는 참조 구조를 확인 | 정책의 기준 위치가 하나이고 참조 ID로 영향 범위를 찾을 수 있음 | 정렬 기준이 여러 문서에 서로 다른 문장으로 독립 정의됨: 수정 필요 |
| 추적 가능성(Traceable) | 요구사항 ID·출처와 관련 UC·설계·검증 ID가 존재하는지 대조 | 결정 출처와 이후 산출물을 연결할 수 있음 | 출처 없는 확정 항목, 존재하지 않는 테스트 ID: 수정 필요 |

검토표에서 발견한 모순·누락은 문장을 고치거나 결정을 확인한 뒤 관련 항목을 다시 판정한다. 모순을 개발자가 임의로 우선순위 처리해 통과시키지 않는다.

### 3.3 완전성 확인에 사용할 분류

각 항목에 대해 `적용 / 해당 없음과 이유`를 표시하고, 적용 항목은 요구사항·UC 또는 테스트 ID에 연결한다.

- **역할:** 이번 기능의 방문자·회원·관리자·외부 서비스 등 실제 행위자와 허용/거부되는 목표.
- **입력·데이터:** 정상 값, 빈 값·누락, 형식 오류, 경계 밖, 없는 대상, 중복 대상, 필요한 페이지·정렬·검색 범위.
- **상태:** 초기·진행·성공·실패·취소 및 해당 업무 상태에서 허용/거부되는 이벤트.
- **외부 의존:** 정상 응답, 빈 응답, 오류, 시간 초과, 잘못된 데이터. 쓰기면 결과 불확실·부분 성공·재시도도 확인.
- **동시성:** 둘 이상의 요청이 같은 자원을 바꿀 때 충돌·중복·순서 문제가 있는 경우만 적용.
- **종료·금지 사항:** 성공 후 데이터, 실패 후 보존할 데이터, 거부 시 변경되지 않아야 할 데이터.
- **운영 제약:** 해당 기능의 권한·개인정보·캐시·배포 환경·사용성·품질 요구사항.

단순 정적 문구 변경에 DB·동시성 검토를 요구하지 않는다. 서버에 쓰기가 있는 기능에서 "해당 없음"으로 생략하려면 영향받는 상태와 저장소가 없다는 근거가 필요하다.

### 3.4 품질 목표를 QAS로 작성하는 방법

성능·신뢰성·보안·사용성 등의 이름만 적지 않는다. 품질 동작이나 아키텍처 선택이 관련된 변경에는 아래 6요소를 채운다. 작은 수정의 품질 기준은 한 문장에 6요소를 통합할 수 있다.

| 요소 | 적을 내용 | 판정 기준 |
| --- | --- | --- |
| 자극원(Source) | 사용자 역할·외부 서비스·운영자 등 | 어느 주체의 행동·장애를 다루는지 특정됨 |
| 자극(Stimulus) | 요청·실패·변경 이벤트 | 재현 가능한 사건으로 기술됨 |
| 대상(Artifact) | 화면·연산·저장소·서비스 등 | 측정하거나 확인할 경계가 특정됨 |
| 환경(Environment) | 운영 상태, 데이터량, 장치·네트워크, 캐시, 부하 등 관련 조건 | 다른 환경에서 나온 결과를 같은 검증으로 섞지 않도록 정의됨 |
| 응답(Response) | 사용자 또는 운영자가 관찰할 시스템 행동 | "견고하게 처리" 대신 표시·저장·거부·복구 결과가 명시됨 |
| 응답 측정(Response measure) | 지표·단위·통과 기준·측정 시작/끝·측정 방법 | 독립적으로 통과·실패를 계산·관찰할 수 있음 |

성능 수치를 채택할 때는 대상 환경, 표본 수·부하, 측정 시작/끝, cold/warm cache, 사용할 통계(예: p95)와 한계를 함께 정한다. 수치가 미정이면 품질 검토는 판정 불가이다. 미정 수치를 AI가 사이트의 확정 기준으로 만들지 않는다.

**수치가 필요 없는 예시 QAS:** 비관리자가 운영 중인 관리자 쓰기 연산에 유효한 데이터를 보내면, 서버는 권한 부족으로 거부하고 저장소를 변경하지 않는다. 응답·저장소 전후 비교로 확인한다. 대상 역할·연산은 기능에서 실제로 정의된 목록으로 지정해야 한다.

**실패 예시:** "API가 빠르다"는 자극·환경·시간 경계·통과 기준이 없어 판정할 수 없다. "오류가 나도 괜찮다"는 어떤 데이터를 보존하고 어떤 결과를 알려야 하는지 없어 판정할 수 없다.

## 4. OOA: 유스케이스와 분석 모델

**실행 방법:** [P10](methods/PLANNING_ANALYSIS.md#p10) UC 목표·보장, [P11](methods/PLANNING_ANALYSIS.md#p11) 개념·데이터 사전, [P12](methods/PLANNING_ANALYSIS.md#p12) 외부 이벤트→SSD/OP, [P13](methods/PLANNING_ANALYSIS.md#p13) DFD·처리 명세, [P14](methods/PLANNING_ANALYSIS.md#p14) FSM, [P15-P16](methods/PLANNING_ANALYSIS.md#p15) 관점·모델 선택. 표/그림의 적용·생략 조건을 먼저 선택한다.

### 4.1 유스케이스를 도출하는 절차

1. 이번 범위의 행위자를 역할로 나열하고 역할별 목표를 적는다. React 컴포넌트·DB 테이블처럼 시스템 내부 요소는 행위자로 넣지 않는다.
2. 목표를 동사형 이름으로 만든다. 예: "학기별 출품작을 조회한다". "페이지", "버튼", "DB 호출"은 목표 이름을 대신하지 않는다.
3. 목표 하나를 달성하는 흐름을 UC 하나로 정의하고 관련 요구사항 ID를 연결한다. 넓은 "사이트를 관리한다"는 목표는 실제로 완료 여부를 판단할 수 있는 하위 목표로 나눈다.
4. 기본 성공 흐름을 먼저 쓴 뒤 입력·권한·데이터·외부 실패·상태에 따른 분기를 찾는다. 각 분기의 종료 또는 복귀 지점을 명시한다.
5. 역할×목표 목록과 UC 목록을 대조한다. 범위 내 목표인데 연결된 UC가 없으면 누락, UC인데 출처·목표가 없으면 범위 초과 또는 제안이다.

### 4.2 어떤 양식을 언제 사용하는가

- **Brief:** 아직 구현 대상으로 선택하지 않은 후보 목표를 한 문단으로 조사할 때만 사용한다.
- **축약 양식:** 이번 변경이 단순 조회·표시이고 쓰기·권한 변경·업무 상태 변경·복잡한 실패 분기가 없으면 사용한다. ID·출처·목표·행위자·범위·전제·성공/최소 보장·기본 흐름·적용되는 예외·인수 기준은 유지한다.
- **Fully Dressed:** 쓰기·권한·상태·외부 연동 동작을 바꾸거나, 축약하면 분기·보장 사항을 잃는 경우 사용한다. [유스케이스 양식](templates/USE_CASE.md)을 채운다.

축약은 필드를 숨겨서 검토를 피하는 뜻이 아니다. 예외가 없으면 "없음"의 범위를 설명한다. 다이어그램 하나만 작성하고 유스케이스 명세를 완료했다고 판정하지 않는다.

### 4.3 필드별 작성 규칙

| 필드 | 무엇을 작성하는가 | 검토 기준 |
| --- | --- | --- |
| ID·이름·목표 | `UC-<feature>-NN`, 동사형 목표, 성공의 가치 | 목표와 범위가 다른 UC와 구별됨 |
| Scope·Level | EDGE 사이트 또는 명시적 부분 시스템; 기본은 user-goal | 시스템 내부 처리와 사용자 목표 수준이 섞이지 않음 |
| Primary / Supporting Actors | 목표를 요청하는 역할 / 서비스를 제공하는 외부 주체 | 역할별 책임과 실제 경계가 일치함 |
| Stakeholders and Interests | 영향을 받는 당사자와 보존할 관심사 | 결과·보장 사항과 연결됨 |
| Trigger | UC를 시작시키는 요청·사건 | 초기 상태에서 시작 이벤트를 특정할 수 있음 |
| Preconditions | 시작 시 이미 참이라고 가정할 사실 | 이후 확인할 입력 유효성이나 불안정한 외부 서비스 정상 상태를 전제로 숨기지 않음 |
| Success Guarantee | 성공 종료 시 출력·데이터·상태 | 기본 성공 흐름의 마지막 결과로 달성됨 |
| Minimal Guarantee | 실패·취소를 포함한 종료에서 반드시 보존할 조건 | 오류 메시지뿐 아니라 변경 금지·데이터 보존 범위가 명시됨 |
| Main Success Scenario | `1, 2, 3…`의 번호, 행위자 요청과 시스템 책임 | 명시적 반복을 제외하면 하나의 성공 경로이며 분기는 Extensions로 이동 |
| Extensions | `3a, 3b, *a` 등 연결할 단계·조건·처리·종료/복귀 | 실패 입력마다 결과가 정의되고 참조하는 단계가 존재함 |
| Special Requirements | 적용 QR·BR·관련 제약 ID | 유스케이스 밖에서 찾을 수 있는 실제 기준으로 연결됨 |
| Variations / Frequency / Open Issues | 데이터·기술 변형, 알려진 빈도·미정 결정 | 추정치를 사실로 적지 않고, 이번 흐름에 영향 없으면 해당 없음으로 기록 |

**전제조건과 권한 검사:** "관리자가 인증돼 있다"를 전제로 명세하더라도 서버의 인증·권한 검사를 생략하는 근거로 사용하지 않는다. 허용되지 않는 호출은 시스템 계약·검증에서 따로 확인한다.

**Extensions 예시:** `3a. 요청한 학기에 출품작이 없다 → 시스템은 빈 결과임을 알리고 성공적으로 종료한다.` `3b. 데이터 취득이 실패한다 → 시스템은 조회 실패임을 알리고 실패 종료한다.` `3b`는 빈 결과 성공과 구분한다. `다시 시도한다`를 쓸 경우 자동/사용자 요청 여부와 반복 제한·복귀 단계를 실제 요구사항으로 정의한다.

### 4.4 유스케이스 완료 판정

모든 UC에 대해 다음을 확인한다.

- 출처·목표가 범위 내 요구사항과 연결되고, 행위자·Trigger·시스템 경계가 특정돼 있다.
- 전제조건에서 기본 흐름을 따라가면 성공 보장을 달성하며, 각 단계에 누가 무엇을 하는지 적혀 있다.
- 적용되는 예외·대안에 조건과 종료/복귀가 있고, 실패 시 최소 보장을 깨뜨리지 않는다.
- 사용자에게 보여야 하는 오류·거부·빈 결과를 시스템 내부 실패와 연결할 수 있다.
- 내부 모듈·SQL·컴포넌트 호출을 제거해도 사용자 목표와 기대 결과가 설명된다. 내부 설계가 UC를 대신하지 않는다.
- 핵심 동작을 바꾸는 Open Issue가 남아 있으면 해당 시나리오는 판정 불가로 둔다. 정상 흐름만 완성하고 예외를 통과로 처리하지 않는다.

### 4.5 도메인·데이터·시스템 연산의 구체적 내용

| 분석 산출물 | 필요한 필드 | 통과 기준 |
| --- | --- | --- |
| 도메인·용어 표 | 용어, 업무 의미, 식별 기준, 속성 의미, 관계·다중성, 수명·불변조건 | 동일 개념에 여러 정의가 없고 관련 UC의 데이터·규칙을 설명할 수 있음 |
| 데이터 사전 | 필드, 의미, 자료형·단위, 허용 범위, 필수/nullable, 정규화, 출처·사용처 | `없음/null/빈 문자열/0` 같은 값의 의미를 구분하고 인터페이스가 같은 정의를 참조함 |
| 시스템 연산 표 | OP ID, UC 단계, 요청 행위자, 연산명, 입력·결과, 사전·사후조건, 실패 | 이번 UC의 외부 요청마다 대응 연산이 있고 권한·업무 규칙을 잃지 않음 |
| SSD | 관련 UC 경로, 외부 행위자, 블랙박스 시스템, 요청·응답 순서 | UC의 외부 이벤트와 일치. DB·서비스 내부 호출은 상세 설계 시퀀스로 분리 |

연산은 사용자 의도로 이름 붙인다. 예: `selectSemester(semesterId)`는 목적을 드러내지만 `onClickButton3()`는 UI 구현 이름이다. 연산 하나가 반드시 HTTP 엔드포인트 하나인 것은 아니다.

### 4.6 모델 선택과 검사 기준

아래 조건이면 해당 내용을 **그림 또는 명시적인 표**로 작성한다. 단순한 경우 그림과 표를 모두 만들 필요는 없다.

| 상황 | 필요한 표현 | 검사 방법 |
| --- | --- | --- |
| 행위자·외부 서비스 경계가 바뀜 | 시스템 경계도 또는 경계·인터페이스 표 | 내부·외부 책임, 데이터 이동, 신뢰·권한 경계를 대조 |
| 엔티티·관계·영속 데이터 의미가 바뀜 | 도메인 관계표, 설계에서는 필요한 ERD | 식별·다중성·참조·삭제/보존 규칙과 불변조건 확인 |
| 업무 상태와 이벤트의 조합에 따라 동작이 달라짐 | 상태 전이표 또는 FSM | 각 `현재 상태×이벤트`를 허용 전이/거부/무시로 정함. Guard 중복·공백·도달 불가·복구 없는 상태 확인 |
| 여러 변환·집계·저장소를 거치는 데이터 처리 | 흐름 표 또는 DFD와 데이터 사전 | 각 입력·출력의 출처·소비자, 단계 간 타입·의미 일치 확인. 계층 DFD는 상위·하위 경계 흐름 대조 |
| 여러 모듈·외부 연동·쓰기가 협력함 | 설계 시퀀스 또는 호출 단계 표 | 성공·실패·복구·동시 요청 시 부작용 순서와 책임 확인 |

상태 전이 표의 필드는 `현재 상태 / 이벤트 / Guard / 행동·부작용 / 다음 상태 / 실패 결과 / 관련 BR·TC`이다. Guard가 동시에 참이면 우선순위를 정의하거나 모순으로 판정한다. 오류 후 복구나 의도적 종료가 없으면 막힌 상태로 기록한다.

## 5. OOD: 설계와 인터페이스 판정

**실행 방법:** [D01-D03](methods/DESIGN_IMPLEMENTATION.md#d01) 구조·표현·책임, [D04-D05](methods/DESIGN_IMPLEMENTATION.md#d04) 계약·권한, [D06-D09](methods/DESIGN_IMPLEMENTATION.md#d06) 데이터·경합·외부 실패·캐시, [D10-D12](methods/DESIGN_IMPLEMENTATION.md#d10) 원칙·재사용·영향. 선택안이 충족할 FR/QR을 정하고 실현 가능한 대안과 비교한다.

### 5.1 설계에서 빠뜨리지 않을 정보

- **책임 표:** 관련 OP·FR, 담당 모듈·함수·경로, 입력/결과, 호출하는 모듈·외부 서비스. 후보 위치와 이미 존재하는 파일을 구분한다.
- **인터페이스 계약:** 입력 필드·타입·정규화·범위, 결과 구조·빈 결과, 오류 종류, 인증·권한, 사전·사후조건, 부작용. HTTP가 있다면 상태 코드·오류 형식도 정의한다.
- **쓰기 계약:** 성공/실패 시 남는 상태, 원자적으로 바뀔 데이터, 중복·동시 요청 처리, 결과를 알 수 없는 실패에서 복구·재시도 규칙. 단순 읽기라면 쓰기 항목은 해당 없음으로 기록한다.
- **외부 연동 계약:** 응답 형식, 실패·시간 초과 처리, 캐시·갱신 조건, 중복 요청·재시도 안전성. 비밀값은 기록하지 않는다.
- **설계 결정:** 해결할 요구사항·품질 제약, 기존 방안과 선택안, 선택 이유, 비용·제약, 영향을 받는 코드·테스트. 구조를 바꾸는 결정은 유지 방안과 실현 가능한 대안도 비교한다.

재시도는 오류마다 일괄 적용하지 않는다. 읽기인지 쓰기인지, 실패 전에 변경이 완료됐을 가능성이 있는지, 중복 처리를 막는 계약이 있는지 확인한 뒤 적용한다.

### 5.2 추상 설계 원칙을 코드에서 판정하는 방법

| 원칙 | 확인할 사실 | 통과 기준 |
| --- | --- | --- |
| 책임·응집도 | 함수·모듈의 목적을 한 문장으로 적고 각 동작을 관련 요구사항에 연결 | 동작들이 그 책임에 필요한 것임. 하나의 모듈에 무관한 업무 규칙이 섞이면 분리 필요성 검토 |
| 낮은 결합도·정보 은닉 | 호출자가 다른 모듈의 내부 상태·저장 형식·외부 API 세부사항을 직접 알아야 하는지 확인 | 정한 인터페이스로 사용 가능하고 구현 세부 변경이 무관한 소비자 변경을 강요하지 않음 |
| 단일 책임(SRP) | 서로 다른 업무 정책이 바뀔 때 동일 모듈을 수정해야 하는 이유 확인 | 무관한 변경 이유가 결합돼 있으면 필요한 범위만 분리. 줄 수로 판정하지 않음 |
| OCP·DIP | 실제 변형·외부 의존성이 요구되는지, 소비자가 필요한 계약만 사용하는지 확인 | 변형·대체 필요가 명세에 있는 경우에만 확장점·추상화를 검토. 미래 추측만으로 계층 추가하지 않음 |
| LSP·ISP | 상속/대체 구현의 입력·출력·불변조건, 소비자가 사용하는 인터페이스 확인 | 대체 구현이 계약을 깨지 않고 필요 없는 연산을 강요하지 않음. 해당 구조가 없으면 해당 없음 |
| 패턴 선택 | 실제 문제, 단순한 기존 방안, 패턴 사용 시 이익·비용 대조 | 개선할 요구사항·중복·변형 지점이 특정돼 있음. 패턴 이름만으로 정당화하면 수정 필요 |

리뷰는 변경한 경계에 적용한다. 기준을 만족시키려는 목적으로 관련 없는 모듈 전체를 재작성하지 않는다.

### 5.3 설계 통과 조건

모든 확정 FR·BR·QR의 담당 책임을 찾을 수 있고, OP마다 계약과 호출 경로가 있으며, UC의 정상·예외·보장 사항이 설계에서도 유지돼야 한다. 데이터·타입·권한·오류 의미가 경계 양쪽에서 같아야 한다. 설계로 해결되지 않은 동시성·부분 실패·필수 품질 항목은 판정 불가 또는 수정 필요로 기록한다.

## 6. 테스트·정적 분석의 작성과 선택

**실행 방법:** [테스트·QA 실행 방법](methods/TESTING_QA.md)의 기법·수준·대역·개발 순서·회귀·검사·UI 선택 절차를 따른다. 예상 결과, 실행 상태, 검토 결과, 완료 상태는 서로 다른 필드다.

### 6.1 테스트 케이스 한 개의 필드

`TC ID / 관련 FR·BR·QR·UC 경로 / 목적 / 수준 / 환경·준비 데이터 / 입력·행동 / 예상 응답·상태·금지 부작용 / 실행 방법 / 실제 결과 / 판정·근거`를 기록한다.

예상 결과는 명세·업무 규칙에서 도출한다. 실제 구현 결과를 그대로 예상값으로 복사하지 않는다. 고정된 외부 응답을 사용하는 테스트는 "외부 서비스 자체의 실제 가용성까지 검증했다"고 보고하지 않는다.

### 6.2 변경에 따라 필요한 테스트 수준

| 변경 대상 | 필요한 확인 | 통과 기준 |
| --- | --- | --- |
| 문구·정적 스타일 | 관련 화면·크기·상태의 수동 확인. 동작·저장 규칙 변화가 없다면 단위 테스트 추가 불필요 | 요청한 표시·배치와 같고 관련 화면의 잘림·겹침·기능 접근 문제가 없음 |
| 필터·정렬·계산·검증·업무 규칙 | 관련 정상·비정상 입력과 경계를 검증하는 단위 테스트 | 명세의 결과와 같고 금지 부작용이 없음 |
| 저장소·서버·외부 어댑터 계약 | 성공·오류·빈 데이터와 입력/출력·권한·상태를 보는 통합 테스트 또는 동등한 실행 검증 | 계약 양쪽의 타입·오류·데이터·부작용이 맞음 |
| 사용자 흐름 | UC 기본 성공 및 해당 대안·예외의 시스템 확인 | 사용자의 목표와 성공/최소 보장 달성. API 단독 통과를 화면 흐름 통과로 대체하지 않음 |
| 권한 변경 | 역할×연산의 허용/거부 목록, 클라이언트 우회 호출 확인 | 허용 동작은 성공, 거부 동작은 비밀·데이터 노출과 쓰기 부작용 없이 거부 |
| 상태·동시 쓰기 | 전이·Guard와 관련 경합·중복 시나리오 | 불변조건이 깨지지 않고 계약된 결과·최종 상태가 됨 |
| 품질 요구사항 | QAS에 명시한 환경·측정·통과 기준 | 같은 조건으로 측정한 결과가 QR의 기준 충족 |

서로 같은 사실을 검사하는 여러 수준의 테스트를 개수만 채우려고 추가하지 않는다. 반대로 단위 테스트만으로 실제 경계·사용자 흐름의 위험을 확인했다고 주장하지 않는다.

### 6.3 입력·상태에서 테스트를 도출하는 규칙

- **동등 분할:** 명세상 처리 결과가 같은 입력군을 나누고 각 군의 대표값을 선택한다. 정상·빈 값·형식 오류·범위 밖·없는 대상·권한 부족 중 실제 적용되는 군을 적는다.
- **경계값:** 순서가 있는 범위는 실제 자료형에서 경계 바로 안·경계·바로 밖을 선택한다. 예: 정수 허용 범위가 1..N이면 0, 1, N, N+1. 이것은 예시이며 사이트 제한값 N을 임의로 정하지 않는다.
- **조건·업무 규칙:** 복수 조건이면 결정표로 조건과 행동을 정하고 실행 가능한 규칙 열마다 검증한다. 같은 결과인 다른 조건 조합도 포함한다. 불가능한 열은 제약 근거, don't-care 병합은 조건이 결과·부작용에 영향을 주지 않는 근거를 남긴다. 출력 종류의 개수를 규칙 커버리지로 세지 않는다. 조건 충돌도 별도 사례로 둔다.
- **상태:** 상태 전이표의 정의된 전이와 거부되는 이벤트를 검사한다. 관련 상태를 만들 수 없으면 전제·도달 경로의 누락을 확인한다.
- **실패:** 시스템 경계에서 시간 초과·오류·잘못된 데이터 등을 재현하고 사용자 결과와 저장소 전후 상태를 확인한다. 지원하지 않는 복구를 테스트 설명에만 만들지 않는다.
- **회귀:** 변경 모듈의 소비자·공유 인터페이스·공유 데이터·캐시·권한 영향으로 대상을 고른다. 관련 없는 화면 전부를 매번 확인할 필요는 없다.

### 6.4 사용할 도구와 실행 기록

구현 시작 시 `package.json`과 기존 도구를 확인한다. 현재 프로젝트의 `npm run lint`, `npm run build`, 로컬 TypeScript가 설치된 경우 `npx --no-install tsc --noEmit`은 각각 린트·배포 빌드·타입 검사이다. 이것만으로 사용자 흐름을 검증한 것으로 보지 않는다. 실행 위치는 `game-dev-club-site`이다.

테스트 러너는 실제 기능·실행 환경·기존 의존성에 맞게 선택하고 명령·설정·사용 이유를 기능 기록에 남긴다. 이 지침을 작성하면서 새 러너나 DB·인증 서비스를 선택한 것은 아니다.

검사 결과는 `검사 종류 / 명령 또는 수동 단계 / 환경·대상 / 실행 여부 / exit code 또는 관찰 결과 / 실패·경고 / 근거`로 기록한다. 외부 서비스·프로덕션 데이터는 승인된 접근 범위에서 검사한다.

정적 분석 문제는 `도구·규칙 / 파일·위치 / 재현된 문제 / 수정 또는 남겨둔 이유 / 재검사 결과`로 정리한다. 기존 오류와 이번에 추가된 오류를 구분하고, 검사 비활성화로 성공을 만들지 않는다.

## 7. 단계 통과, 추적성과 완료 판정

**실행 방법:** [테스트·QA 실행 방법](methods/TESTING_QA.md)의 리뷰·대표 시나리오·추적 유지·완료 절차로 아래 증거를 대조한다. 반복·중요 결함 대응은 [M08](methods/PROJECT_MANAGEMENT.md#m08)을 적용한다.

### 7.1 단계별 필요한 증거

| 단계 | 통과에 필요한 내용 | 통과할 수 없는 상태 |
| --- | --- | --- |
| Planning | 범위·출처·역할·우선순위, FR·BR·QR와 인수 기준, §3.2 검토 결과 | 의존하는 핵심 결정 미정, 같은 조건의 규칙 충돌, 통과 기준 부재 |
| OOA | 역할별 목표→UC, 도메인·규칙, 외부 이벤트→OP, 필요한 상태·데이터 모델 | 목표 누락, 실패 종료·보장 부재, 데이터·상태 의미 불일치 |
| OOD | 요구사항→담당 책임, OP 계약, 필요한 호출·데이터·실패 설계 | 책임 없는 요구사항, 계약 충돌, 처리 주체 없는 실패·부분 저장 |
| 구현·테스트 | 명세대로 구현한 변경, §6에 해당하는 검증과 결과 | 코드 생성·빌드만 확인하고 동작 완료 주장, 적용되는 테스트 미실행·실패 |
| QA | 추적 연결 확인, Verification·Validation 결과, 회귀·관련 QR 확인, 남은 제약 | 누락·실패·판정불가 항목을 숨기거나 예시를 검증 증거로 사용 |

작은 변경은 같은 짧은 기록에서 이 내용을 만족시켜도 된다. 통과 기준은 작업 단위마다 적용하며, 다음 단계 검토에서 문제가 발견되면 필요한 이전 내용을 갱신한다.

### 7.2 추적 표와 누락 판정

추적 표의 필드는 `요구사항 ID / UC·OP·BR·QR / 설계 책임 / 코드 경로·심볼 / TC·검증 방법 / 실제 결과·근거`이다. 설계·코드가 없는 단계에서는 계획과 미구현 상태를 표시하며, 존재하지 않는 경로를 완료한 구현처럼 쓰지 않는다.

다음 세 방향으로 대조한다.

1. **요구사항→구현·검증:** 이번 범위의 확정 요구사항마다 담당 코드와 실제 검증 결과가 있는지 확인한다.
2. **구현→요구사항:** 변경된 외부 동작·업무 규칙에 근거 요구사항이 있는지 확인한다. 단순 내부 보조 코드에는 별도 사용자 요구사항을 만들지 않아도 된다.
3. **검증→요구사항:** 테스트 예상 결과가 연결된 명세·규칙과 같고, 변경 후에도 유효한지 확인한다.

보고할 필요가 있을 때 요구사항 연결률은 `구현과 검증 방법이 연결된 대상 요구사항 수 / 이번 범위 확정 대상 요구사항 수`, 시나리오 실행률은 `실제로 실행한 필수 시나리오 수 / 정의한 필수 시나리오 수`로 계산한다. 분모·제외 항목·미실행 이유를 함께 적는다. 연결됐다는 것과 통과했다는 것은 다르다. 분모가 0이면 비율 대신 해당 없음이라고 기록한다.

필수 시나리오 누락·미실행·실패가 없고 관련 검사·품질 기준을 충족해야 **검증 완료**로 보고한다. 전체 코드 커버리지 목표는 여기서 임의로 고정하지 않는다. 위험이 큰 규칙의 미검증 경로는 커버리지 비율과 관계없이 검토 대상이다.

### 7.3 Verification과 Validation의 구체적 구별

- **Verification:** `FR의 조건에서 실제 출력이 예상값과 같은가`, `BR 불변조건이 유지되는가`, `OP 계약과 권한·오류·데이터가 맞는가`, `QR 측정이 기준을 만족하는가`를 코드·테스트·리뷰 근거로 확인한다.
- **Validation:** `요청한 역할이 요청한 목표를 대표 시나리오로 끝낼 수 있는가`, `결과가 요청 범위·운영 목적과 맞는가`를 사용 흐름으로 확인한다. 사람이 사용해 본 결과가 필요하면 자동 테스트와 구분한다.

개발자·AI가 수행한 시나리오 확인을 사용자 인수 승인으로 기록하지 않는다. 사용자 검토가 요청된 작업은 그 결과를 별도 기록하고, 아직 받지 않은 승인은 미실시로 둔다.

## 8. CMMI·위험·변경 관리의 최소 실행 기준

**실행 방법:** [M01-M03](methods/PROJECT_MANAGEMENT.md#m01) 계획·진척, [M04-M06](methods/PROJECT_MANAGEMENT.md#m04) 형상·환경·복구, [M07-M08](methods/PROJECT_MANAGEMENT.md#m07) 위험·원인 개선, [M09-M10](methods/PROJECT_MANAGEMENT.md#m09) 실무·결정 관리. 위험 등급·FMEA 선택·복구 후보는 해당 방법의 정의를 사용한다.

아래 기록은 기능 명세·이슈·커밋·PR 등 기존 위치에 통합한다. 매 작업마다 별도 평가 보고서를 만들지 않는다.

| 실무 | 최소 기록 | 언제 확인·갱신하는가 | 완료 판정 |
| --- | --- | --- | --- |
| 요구사항 관리 | ID·출처·상태·변경 이유·영향 ID·검증 연결 | 요청이 추가·변경·제외될 때 | 이전·새 결정이 구분되고 관련 명세·코드·테스트가 같은 결정 참조 |
| 계획·진행 | 이번 범위·우선순위·순서·필수 의존·현재 상태·장애물 | 구현 단위를 고를 때, 범위·의존성이 바뀔 때 | 남은 필수 작업과 막힌 작업을 식별할 수 있고 미완료를 완료로 표시하지 않음 |
| 형상 관리 | 브랜치·기존 변경, 목적별 수정 파일·설정·의존성, 저장한 커밋/PR이 있다면 참조 | 작업 시작, 변경 묶음 정리, 배포 준비 시 | 사용자 변경을 보존하고 변경 출처·버전을 찾을 수 있음. 지침만으로 자동 커밋·푸시·배포 권한을 만들지 않음 |
| 품질 보증 | 리뷰 대상·기준·결과·문제·조치·재확인 | 단계 통과·완료 보고 시 | 필요한 기준의 결과가 있고 수정 필요·판정 불가가 통과로 섞이지 않음 |
| 위험 관리 | 위험 사건·조건, 데이터/사용자 영향, 근거, 방지·탐지·복구, 남은 제약 | 권한·쓰기·외부 연동·환경·아키텍처 영향 발견 시 | 관련 위험에 실행할 대응이 있거나 미해결로 명시. 존재하지 않는 위험을 양식 채우려고 만들지 않음 |
| 원인 분석·개선 | 재현 조건, 원인·제공된 진단, 수정 위치, 방지 테스트/규칙, 재확인 | 반복·중요 결함을 수정할 때 | 원인과 수정·재발 방지가 연결됨. 제공된 진단과 충돌하지 않으면 재분석 반복하지 않음 |

위험은 근거가 있는 다음 조건으로 구별한다. 정적 표시 수정처럼 쓰기·권한·공유 계약 영향이 없는 변경은 낮은 영향으로 기록할 수 있다. 영속 쓰기·권한·공유 인터페이스·외부 응답 처리에는 통합·실패 검증을 적용한다. 되돌리기 어려운 데이터 변환·외부 부작용·여러 요청의 상태 충돌에는 복구·재시도·동시성 계약을 추가한다. 추측만으로 발생 확률이나 점수를 만들지 않는다.

요구사항 변경 기록에는 `이전 내용 / 새 내용 / 출처·이유 / 영향을 받는 UC·OP·데이터·코드·테스트 / 갱신 결과`를 적는다. 구현에 맞춰 요구사항을 조용히 바꾸지 않는다. 배포·데이터 변경을 실제 수행하는 작업이면 `적용 순서 / 이전 버전·데이터와 호환 여부 / 실패 탐지 / 복구 방법과 복구 불가능한 범위 / 실행 확인`을 기록한다.
